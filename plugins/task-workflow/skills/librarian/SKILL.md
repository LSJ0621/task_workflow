# 사서

지식 베이스에 쓰는 일은 전부 사서가 한다. 지식 베이스는 사용자에 대한 맥락(일, 생활, 취향, 상황)을 쌓는 곳이다. 사서는 기록하고 정리하고 분류만 한다. 규칙을 만들거나 제안하지 않는다. 규칙은 맥락 분석(`analyze-context`)에서 사용자가 정한다. 평소에는 **쪽지**(메모 한 줄, 가벼움), 하루 한 번 **정리**(메모 → 정식 기록, 무거움). 이 본문은 쪽지 모드와 상황판이다. 정리 모드는 [정리 절차](references/shelving.md)에 있고, 정리를 요청받았거나 급한 메모가 있을 때만 읽는다. 매번 읽으면 메모 한 줄에 정리 절차 전체가 딸려 와서 낭비라서다.

## 지식 베이스 찾기

1. `$KNOWLEDGE_BASE_DIR`이 있으면 그곳.
2. 없으면 현재 폴더가 지식 베이스인지 본다. `INDEX.md`와 `raw/journal/`이 있는 git 저장소면 맞다. 지식 베이스 저장소에서 연 세션이 이 경우다.
3. 둘 다 아니면 아무것도 쓰지 않고 `setup-knowledge-base` 스킬로 지식 베이스를 만들거나 연결하라고 안내한다.

## 규칙이 있는 곳

규칙과 틀은 모두 이 스킬 폴더 안에 있다. 지식 베이스에는 기록만 있고 규칙은 없다. 아래 경로는 이 스킬 폴더 기준이다.

- 메모 형식: 이 파일 아래 쪽지 모드
- 상황판: 이 파일 아래 상황판 절
- 정리 절차: `references/shelving.md`
- 구조 변경 브랜치 머지: `references/merging.md`
- 기록 형식(두 가지 문서, 불변 조건, 승인 범위, 식별자, 파일명, 머리말, 규칙별 사례표, 카드): `references/records.md`
- 사례·결정·맥락 틀: `references/templates/`
- 글쓰기: `references/writing.md`

## 쪽지 모드

메모는 "나중에 사서가 정리할 재료"다. 지금 틀을 채우거나 요약 문서를 고치지 않는다. 그 비용을 정리 때로 미루는 게 이 설계의 핵심이다.

1. 메모 파일과 형식을 확인한다. 메모는 지식 베이스 `raw/journal/YYYY-MM-DD.md`에 날짜별 한 파일로 쌓는 원본이다. 한 줄 형식은 이렇다.
   ```
   HH:MM | feedback|decision|context | 작업 또는 맥락 | 내용 (사용자 말은 그대로) | 관련 id 또는 -
   ```
   메모에는 틀을 채우지 않는다. 정식 기록은 정리 모드가 만든다.
2. 종류를 정한다.
   - `feedback`: 사용자가 에이전트의 결과·행동·판단을 고쳤다. 사용자 말을 **그대로** 인용한다. 이 말이 나중에 맥락 분석에서 규칙의 재료가 된다.
   - `decision`: 뭘 하기로 정했다. 결정과 이유를 한 줄에. 선택지가 있었으면 버린 쪽도 짧게.
   - `context`: 사용자 본인, 상황, 선호, 제약에 대한 새 사실. 일만이 아니라 생활과 취향도 들어간다.
3. 적는 때를 고른다. 프롬프트마다 적지 않는다. **주제 하나가 끝날 때 한 줄**이다. 고치는 말이 오가는 동안은 적지 않는다. 결론이 나면 결론과 사용자 말 한마디를 한 줄로 적는다. 같은 주제의 연속 피드백은 한 줄로 묶는다. "다음 답은 짧게 해 줘"처럼 그 답 하나에만 해당하는 말은 적지 않는다. 앞으로도 계속 적용할 말일 때만 남긴다. 예외로 바로 적는 것: 사용자가 "메모해"라고 했을 때, `urgent`일 때.
   오늘 날짜 파일이 없으면 만든다. 머리말 없이 줄만 쌓는 파일이다. 위 형식대로 **한 줄** 덧붙인다. 글은 `references/writing.md`를 따른다. 관련 기록 id가 있으면 넣고, 없으면 `-`.
4. 급한지 본다. 오늘 다음 작업이 이 결정에 바로 걸리면 줄 끝에 ` | urgent`를 붙이고, 정리 절차를 읽어 **그 한 건만** 즉시 정리한다. 아니면 하루 한 번 정리에 맡긴다.
5. 커밋한다. 메모는 추가만 하는 원본이라 main에 바로 간다. 먼저 `git pull --ff-only`. push 안 된 로컬 커밋이 있어 ff-only가 안 되면 `git pull --rebase`. 그다음 `git add` 해당 파일, 커밋 메시지는 "메모: <종류> <요지>". pull이 충돌하면 커밋만 남기고 알린다.
   push는 하지 않는다. 밀린 메모 커밋은 정리 절차 9단계의 push가 한꺼번에 올린다. 메모마다 push하면 과해서다.
   예외로 바로 push하는 것: `urgent` 메모, 사용자가 "메모해"라고 한 메모.
6. 한 줄로 알린다. "메모 남김: `raw/journal/YYYY-MM-DD.md` (종류)". 두 줄 보고는 쓰지 않는다. 메모는 작업이 아니라 작업의 부산물이라서다.

## 상황판

지식 베이스 `wiki/board.md`는 프로젝트마다 지금 어디까지 왔는지 적는 곳이다. 프로젝트 하나에 `## <프로젝트 이름>` 묶음 하나다.

- 프로젝트에서 작업 단위 하나가 끝나면 그 일을 한 세션이 **자기 프로젝트 묶음만** 고친다. 다른 프로젝트 묶음은 건드리지 않는다. 여러 세션이 같은 파일을 고쳐도 충돌하지 않게 하기 위해서다.
- 묶음에는 네 줄만 둔다.
  ```markdown
  ## <프로젝트 이름>
  - 어디까지: 끝낸 것 한두 문장
  - 다음 할 일: 한두 문장
  - 막힌 것: 사용자 답이나 외부 사정으로 멈춘 것. 없으면 "없음"
  - 고친 날짜: YYYY-MM-DD
  ```
- 묶음이 없는 프로젝트면 새로 만든다. 프로젝트 이름은 `wiki/projects/`의 카드 이름과 맞춘다.
- 상황판은 덮어써도 되는 요약이다. 지난 진행 내용은 git 이력과 메모에 남는다.
- 커밋은 메모와 같다. `git pull --ff-only`(안 되면 `git pull --rebase`) 뒤 main에 "상황판: <프로젝트> <요지>"로 커밋하고 push는 하지 않는다. 정리 9단계가 함께 올린다.
- 하루 한 번 정리는 7일 넘게 고치지 않은 묶음을 보고에 적는다.

## 하지 말 것

- 메모 줄을 고치거나 지우지 않는다. 잘못 적었으면 정정 줄을 하나 더 쓴다. 원본은 추가만 한다.
- 메모 단계에서 틀을 채우거나, 규칙별 사례표·카드·색인을 고치지 않는다. 정리 모드의 일이다. 상황판의 자기 프로젝트 묶음만 예외다.
- 한 사건에 두 줄 넘게 쓰지 않는다. 길어지면 정리할 때 기록이 된다.
- 비밀값, 자격 정보, 고객 인프라 식별자를 적지 않는다. 지식 베이스는 원격 저장소에 올라간다.
- 사용자가 고친 말을 요약하거나 다듬지 않는다. 그대로가 재료다.
- 규칙(스킬, 전역 지침, 응답 양식)을 만들거나 고치거나 제안하지 않는다. 맥락 분석의 일이다.
