# 기록 규칙

지식 베이스에 정식 기록을 쓸 때 따르는 규칙이다. 사서 정리 모드가 처음에 한 번 읽는다. 틀은 같은 폴더의 `templates/`에 있고, 글쓰기 규칙은 같은 폴더의 `writing.md`에 있다.
지식 베이스에는 기록(맥락·데이터)만 두고, 기록을 어떻게 쓰는지는 이 파일에 둔다.

## 두 가지 문서

| 종류 | 폴더 | 성격 | 누가 언제 읽나 |
| :- | :- | :- | :- |
| 원본 | `raw/` | 추가만 한다. 고치지 않는다 | 판단이 애매할 때, 요약 문서를 다시 만들 때 |
| 요약 문서 | `wiki/` | 원본에서 만들어져서 언제든 다시 만들 수 있다. 규칙별 사례표, 프로젝트 카드 | 작업 중, 맥락 분석 때 |
| 상황판 | `wiki/board.md` | 프로젝트마다 지금 어디까지 왔는지. 덮어쓴다. 지난 내용은 git 이력에 있다 | 작업을 이어 갈 때 |

새 정보는 **항상 원본에 먼저** 들어간다. 요약 문서에 직접 새 사실을 적지 않는다.
사용자 피드백은 사례(`C-`), 정한 것은 이유와 함께 결정(`D-`), 사용자에 대한 새 사실은 맥락(`X-`)이 된다.
요약 문서의 모든 항목은 자기가 나온 원본을 가리킨다.
상황판은 예외다. 진행 상황은 원본에서 만들지 않고, 그 프로젝트에서 일한 세션이 자기 묶음을 직접 고친다(사서 `SKILL.md` 상황판 절).

## 불변 조건

구조를 어떻게 바꾸든 이 다섯 가지는 지킨다. 리팩토링이 끝나면 이 목록으로 스스로 점검한다. 스크립트 점검은 `../scripts/check_invariants.py`.

1. 요약 문서의 모든 항목은 원본(사례·결정·맥락) 하나 이상을 가리킨다. 규칙별 사례표에는 모든 사례가 한 줄 이상 있다.
2. 모든 결정에는 날짜와 이유가 있다.
3. 기록은 지우지 않는다. `status: superseded`와 `superseded_by`만 표시하고 새 기록을 가리킨다.
   원본 파일에서 고쳐도 되는 건 이 두 필드뿐이다.
4. 같은 사실은 한 곳에만 있다. 두 문서가 다른 말을 하면 그게 할루시네이션의 시작이다.
5. 식별자와 파일명은 한 번 정하면 바꾸지 않는다.

## 승인 범위

- 원본에 추가하는 것은 에이전트가 알아서 한다. 정식 기록(사례·결정·맥락)은 main에 바로 커밋하고 push한다. 메모(`raw/journal/`)와 상황판은 쪽지 모드 규칙을 따른다(main에 커밋만 하고 정리 절차 9단계가 함께 push한다. urgent와 "메모해" 메모는 바로 push).
- 규칙을 만들거나 고치는 것은 사서가 하지 않는다. 사례를 규칙별 사례표에 분류해 적기만 하고, 규칙은 맥락 분석(`analyze-context` 스킬)에서 사용자가 정해 스킬이나 전역 지침에 넣는다.
- 파일을 옮기거나 합치는 **구조 변경**은 묻지 않는다. 별도 로컬 브랜치 `proposal/structure-YYYYMMDD`에 올리고, 만든 세션이 바로 main에 머지한다(`merging.md`). 내용이 바뀌지 않는 일이라서다. 대신 보고에 무엇을 어디로 옮겼는지 적는다.
- 대체됨 표시(`status: superseded`와 `superseded_by`)는 사서가 승인 없이 한다. 대신 보고에 무엇을 무엇으로 대체했는지 적는다. 이미 정한 결정의 뒤처리라 따로 승인받으면 사용자 검토만 늘어나서다.
  - 새 기록이 예전 기록을 전부 바꿀 때만 표시한다. 예전 기록에 `status: superseded`와 `superseded_by: <새 id>`, 새 기록 머리말에 `supersedes: <예전 id>`.
  - 예전 기록의 일부만 바뀌었으면 대체됨 표시를 하지 않는다. 새 기록 본문에 "예전 기록 <id>의 이 부분을 바꾼다"고 적고 바뀐 부분을 쓴다.
- 비밀값, 자격 정보, 고객 인프라 식별자는 어디에도 적지 않는다. 지식 베이스는 GitHub에 있고 다른 세션도 읽는다.

## 식별자

`<종류>-<YYYYMMDD>-<NN>` 형식. 같은 날 같은 종류 안에서 NN은 01부터 올라간다. 손으로 세지 말고 `../scripts/next_id.py <지식 베이스> <접두>`로 받는다.

| 종류 | 접두 | 폴더 |
| :- | :- | :- |
| 실수 사례 | `C` | `raw/cases/` |
| 결정 | `D` | `raw/decisions/` |
| 맥락 | `X` | `raw/context/` |

예전 구조에서 쓰던 다른 접두(예: `R`, `B`)의 지난 기록은 그대로 둔다. 새로 만들지 않을 뿐이고, 점검 스크립트는 지난 id 참조를 계속 인식한다.
지난 기록에 나오는 `P-`로 시작하는 id는 없어진 기준 문서의 항목 이름이다. 지난 기록이라 고치지 않고, 점검 스크립트도 없는 id로 보지 않는다.

## 파일명

`<식별자>-<짧은-영문-슬러그>.md`. 예: `D-20250101-01-storage-as-git-markdown.md`
한 번 정한 파일명은 바꾸지 않는다. 슬러그가 마음에 안 들어도 그대로 둔다. 링크가 깨진다.

## 머리말

모든 `raw/` 파일(메모 `raw/journal/` 제외)은 맨 위에 YAML 머리말을 둔다. 나중에 검색 색인과 필터가 되는 부분이라 빠뜨리지 않는다.

```yaml
---
id: D-20250101-01
type: decision          # case | decision | context
title: 지식 베이스 저장 방식
date: 2025-01-01
domain: common          # common 또는 도메인 이름. 소문자
status: active          # active | superseded | rejected
supersedes:             # 이 기록이 대체한 이전 기록의 id. 없으면 비움
superseded_by:          # 이 기록을 대체한 새 기록의 id. 없으면 비움
tags: [knowledge-base, storage]
related: []             # 관련 기록 id 목록
---
```

- `status`와 `superseded_by`는 원본 파일에서 고쳐도 되는 유일한 필드다.
- `domain`은 지식 베이스 `INDEX.md`의 도메인 목록에 있는 이름만 쓴다. 새 도메인은 목록에 먼저 추가하고 그 사실을 보고에 적는다.

## 규칙별 사례표

`wiki/rule-cases.md`. 사례가 어느 규칙과 이어지는지 모아 둔 요약 문서다. 사서가 정리 때 사례를 만들 때마다 줄을 더하고(`shelving.md` 4단계), 맥락 분석이 이 표를 규칙별로 묶어 본다. 사서는 분류만 하고 규칙을 판단하거나 제안하지 않는다.

```markdown
# 규칙별 사례표

사례(`C-`)마다 관련 규칙과, 사례가 그 규칙과 다른 방향인지 적는다. 사서가 정리 때 줄을 더한다.
규칙을 정하는 건 맥락 분석(`task-workflow:analyze-context`)이다. 사례 원본은 `raw/cases/`에 있다.

| 사례 | 관련 규칙 | 거스름 |
| :- | :- | :- |
| C-20250101-01 | `librarian/SKILL.md` 쪽지 모드 | 아니오 |
| C-20250101-02 | 전역 지침 보고 | 예 |
| C-20250101-03 | 없음 | 새 규칙 후보 |
```

- **사례**: 사례 id 하나. 사례를 만든 순서대로 표 끝에 더한다.
- **관련 규칙**: 사례와 같은 일을 다루는 규칙이 있는 곳. 한 줄에 한 군데. 플러그인 스킬이면 `<스킬 이름>/<파일>` 뒤에 절 이름(예: `` `verify-work/SKILL.md` 보고와 수정 ``), 전역 지침이면 `전역 지침 <절 이름>`, 응답 양식이면 `응답 양식 <파일 이름>`. 찾지 못했거나 확실하지 않으면 `없음`.
- **거스름**: 셋 중 하나.
  - `예`: 사용자가 고친 방향이 그 규칙과 다르다. 규칙대로 했는데 고쳐졌거나, 규칙과 반대로 하라고 했다.
  - `아니오`: 사용자가 고친 방향이 그 규칙과 같다. 에이전트가 규칙을 어겼거나 규칙이 모자랐다. 그 규칙의 근거가 된다.
  - `새 규칙 후보`: 관련 규칙이 `없음`일 때만 쓴다.
- 한 사례가 규칙 여러 개에 걸리면 규칙마다 한 줄씩 쓴다.
- 요약 문서라 잘못 적은 줄은 고쳐도 된다. 사례 원본은 고치지 않는다.

## 문서를 나눌지 합칠지

기준은 책임이 아니라 **읽는 시점에 필요한가**다.

| 한 문서에 넣는다 | 링크로 뺀다 |
| :- | :- |
| 그 문서를 읽을 때마다 필요하다 | 특정 상황에서만 필요하다 |
| 짧다 | 길다 (예시, 절차 상세, 과거 사례) |
| 안 읽으면 작업이 틀어진다 | 안 읽어도 되고 읽으면 더 낫다 |
| 본문과 같이 바뀐다 | 바뀌는 주기가 다르다 |

규칙은 본문에, 상세는 링크에. 링크로 뺄 때는 "이럴 때 이 문서를 열어라"는 조건을 본문에 같이 쓴다.

## 프로젝트 카드

`wiki/projects/<slug>.md`. 프로젝트마다 한 장, 20줄 안. 요약 문서라 사서 정리 모드가 원본에서 만든다. 사람이 직접 쓰지 않는다.
들어가는 것: 뭐 하는 프로젝트인지 한 줄, 기간, 문서와 저장소 위치(경로·주소), 이 프로젝트에서 나온 결정과 사례 id.
진행 상황(어디까지, 다음 할 일, 막힌 것)은 카드에 넣지 않고 상황판(`wiki/board.md`)의 그 프로젝트 묶음에 둔다. 카드는 하루 한 번 정리 때만 바뀌어서 진행 상황을 담으면 금방 낡는다.
코드 저장소가 있는 프로젝트의 설계·경위 세부는 그 저장소 안 문서에 둔다. 카드는 위치만 가리킨다.
