# 정리 절차 (사서 정리 모드)

메모를 정식 기록으로 옮기고, 맥락 요약과 카드를 갱신하고, 회귀 질문을 더한다. 하루 한 번 예약 작업이나 사용자 요청으로 하고, 급한 메모가 있으면 그 한 건만 즉시 한다.
정리는 비싸다. 그래서 한 세션에서 몰아 한다. 틀과 규칙을 한 번 읽고 여러 건을 처리하기 위해서다.

## 사서가 하는 것과 하지 않는 것

| 한다 (main에 커밋) | 하지 않는다 |
| :- | :- |
| 원본 추가(사례·결정·맥락), 맥락 요약(`wiki/context.md`)·카드 갱신, 원본 머리말의 분류 정보(`scope`, 맥락 `domain`, `snapshot`) 바로잡기, 회귀 질문 추가, 메모 파일에 "정리됨" 줄, 대체됨 표시(`status`/`superseded_by`, 9단계 보고에 적는다) | 사례를 규칙별 사례표에 분류하기. 규칙(스킬, 훅, 전역 지침, 응답 양식)을 만들거나 고치기. 파일 이동·합치기·이름 바꾸기 |

왼쪽은 추가거나 원본에서 다시 만들 수 있거나 내용이 바뀌지 않는 것이라 틀려도 복구된다.
사례 분류와 규칙 고치기는 자가 발전(`analyze-context` 스킬)이 한다. 사례를 규칙과 잇는 일과 규칙을 고치는 일은 같은 판단이라 한 곳에서 한다.
파일을 옮기거나 합치는 일은 주 1회 [구조 점검](structure.md)이 한다.

## 순서

아래 명령의 `<사서 폴더>`는 이 스킬 폴더(이 파일의 한 단계 위 폴더)다.

1. **읽기.** 지식 베이스를 원격 main의 최신 상태로 맞춘다.
   - main 브랜치에서 `git pull --ff-only`. push 안 된 자기 커밋(메모 등)이 있어 안 되면 `git pull --rebase`. 쪽지 모드 5단계와 같다. HEAD가 브랜치에 붙어 있지 않으면 정리하지 말고 보고한다.
   그다음 이 파일과 같은 폴더의 `records.md` 전체, `templates/`의 틀, `writing.md`를 읽는다. 형식은 전부 거기서 나온다. 지식 베이스에는 규칙 문서가 없다.
2. **대상 고르기.** `raw/journal/`에서 끝에 `정리됨:` 줄이 없는 날짜 파일. 급한 한 건이면 그 줄만.
3. **줄마다 정식 기록 만들기.**
   - 식별자는 스크립트로 받는다. 손으로 세면 겹친다.
     ```bash
     python3 "<사서 폴더>/scripts/next_id.py" "$KNOWLEDGE_BASE_DIR" C   # C|D|X
     ```
   - `feedback` → 사례(`C-`) 틀. 사용자 말은 그대로. 메모에 관련 id가 있으면 `related`에.
   - `decision` → 결정(`D-`) 틀. 선택지가 메모에 없으면 "미확인"이라고 적는다. 이유를 지어내지 않는다.
     내용이 `맥락 분석:`으로 시작하는 메모는 예전 맥락 분석이 남긴 결과다. 제목은 "맥락 분석 YYYY-MM-DD", 태그에 `context-analysis`를 넣는다. 결정 절에 "분석 범위"와 "넣은 곳"을 메모 그대로 옮긴다. 자가 발전이 처음 돌 때 이 기록에서 어디까지 봤는지를 이어받는다. 지금은 이런 메모를 새로 남기지 않는다.
   - `context` → 맥락(`X-`) 틀. 유효 기간은 메모에 없으면 "변할 수 있음".
     맥락에는 오래 맞는 사실만 만든다. 그날의 상태(작업이 어디까지 됐나, 지금 무엇이 켜져 있나)는 맥락으로 만들지 않는다. 그런 메모 줄은 정식 기록 없이 넘어간다. 진행 상황은 그 프로젝트 세션이 상황판에 적는다.
   - 메모의 관련 칸이 점검 보고서 파일 이름(`raw/reviews/…html`)이면 `related`에 그대로 넣는다. 사용자가 그 보고서를 보고 한 말이라는 표시다. 자가 발전이 이 표시로 보고서와 이어 읽는다.
   - **scope**: 정식 기록마다 머리말에 `scope`를 정한다. 사용자 전체에 걸리면 `me`, 한 프로젝트에만 걸리면 `project:<카드 이름>`. 메모의 "작업 또는 맥락" 칸이 프로젝트 이름이면 그 프로젝트로 본다. 맥락이면 `domain`도 `work`·`life`·`taste`·`tools` 중 하나로 정한다. 뜻은 `records.md` 머리말 절.
   - 새 기록이 예전 기록을 바꾸면 `records.md` 승인 범위 절에 적힌 대로 한다. 전부 바꾸면 대체됨 표시를 하고, 일부만 바꾸면 표시 없이 새 기록에 "예전 기록 <id>의 이 부분을 바꾼다"고 적는다. 대체됨 표시를 한 쌍(예전 id → 새 id)은 9단계 보고용으로 적어 둔다.
   - 사례·결정 머리말의 `domain`은 `INDEX.md`의 도메인 목록에 있는 것만. 없는 도메인이 필요하면 목록에 먼저 추가하고 그 사실을 보고에 적는다.
   - 새 사례를 규칙별 사례표(`wiki/rule-cases.md`)에 적지 않는다. 자가 발전이 다음 차례에 분류한다.
4. **요약 갱신과 상황판 보기.** 형식은 `records.md`의 맥락 요약 절과 프로젝트 카드 절이다.
   - scope가 `me`인 새 맥락이나 결정이 생겼으면 `wiki/context.md`의 해당 절(맥락은 그 `domain` 절, 결정은 "나 전체 결정" 절)에 `한 줄 (id)`을 더한다. 파일이 없으면 그 절의 형식으로 만든다. `snapshot: true`인 맥락은 올리지 않는다.
   - scope가 `project:<이름>`인 새 기록이 생겼거나 메모에 프로젝트가 등장했으면 `wiki/projects/<이름>.md`를 원본에서 다시 쓴다. 새 결정은 "유효한 결정" 절에, 새 사례와 맥락 id는 관련 기록 줄에 넣는다. 없던 프로젝트면 새로 만든다.
   - 3단계에서 대체됨 표시를 했으면 예전 id를 `wiki/context.md`와 카드에서 빼고 새 id로 바꾼다.
   - 고친 요약 파일 수(`context.md`와 카드)를 9단계 보고용으로 센다.
   상황판(`wiki/board.md`)은 고치지 않는다. 묶음마다 "고친 날짜"를 보고, 7일 넘게 안 고친 묶음을 9단계 보고용으로 적어 둔다.
5. **회귀 질문.** 새 결정마다 `tests/regression.md`에 질문 한 줄. "왜 X를 Y로 정했나?" 꼴이 기본이다.
6. **불변 조건 점검.** 유효한 결정·맥락이 요약에 빠졌으면 여기서 실패로 나온다.
   ```bash
   python3 "<사서 폴더>/scripts/check_invariants.py" "$KNOWLEDGE_BASE_DIR" --skip-rule-cases
   ```
   `--skip-rule-cases`는 "모든 사례가 규칙별 사례표에 있다"는 검사만 건너뛴다. 방금 만든 사례는 자가 발전이 분류하기 전이라 표에 없는 게 맞아서다. 표 머리와 표에 있는 줄의 형식은 그대로 점검한다.
   문제가 나오면 커밋 전에 고친다. 고칠 수 없는 것은 보고에 적고 넘어간다.
7. **메모 파일 마감.** 처리한 날짜 파일 끝에 `정리됨: <만든 id들>` 한 줄. 메모 줄은 건드리지 않는다.
8. **커밋·push.** main에 "사서 정리 YYYY-MM-DD: 사례 n, 결정 n, 맥락 n, 요약 n". 지식 베이스 저장소 push는 미리 허락된 것이다. 쪽지 모드와 상황판에서 커밋만 해 둔 메모·상황판 커밋도 이 push로 함께 올라간다.
   정리하는 동안 원격 main이 앞서 가서 push가 거부되면 `git pull --rebase origin main`을 한 번 하고 다시 push한다. 리베이스가 충돌하면 멈추고 커밋만 남긴 채 보고한다.
9. **보고.** 사용자가 폰에서도 볼 수 있는 두 줄.
   - **완료**: 정리한 메모 n줄 → 사례 n, 결정 n, 맥락 n, 요약 갱신 n(`context.md`와 카드 중 고친 파일 수). 커밋 해시. 대체됨 표시를 했으면 쌍마다 무엇을 무엇으로 대체했는지 한 줄씩 적는다. 예: "D-20250101-03(주간 보고)을 D-20250301-02(격주 보고)로 대체". 대체됨 표시는 승인 없이 하는 대신 이 보고가 사용자가 알 수 있는 유일한 곳이다.
   - **확인할 것**: 7일 넘게 안 고친 상황판 묶음이 있으면 프로젝트 이름과 고친 날짜. 6단계에서 고치지 못한 문제. 없으면 "없음".

## 하지 말 것

- 스킬, 훅, 전역 지침, 응답 양식을 고치거나 고치자고 제안하지 않는다. 규칙은 자가 발전이 고친다.
- 규칙별 사례표에 줄을 더하지 않는다. 사례 분류는 자가 발전이 한다.
- 지식 베이스에 규칙 문서를 만들지 않는다.
- 지식 베이스 체크아웃의 브랜치를 바꾸지 않는다.
- 원본 파일의 본문을 고치지 않는다. 머리말의 `status`, `superseded_by`, `scope`, 맥락 `domain`, `snapshot`만 예외.
- 파일을 옮기거나 합치거나 이름을 바꾸지 않는다. 구조 점검 절차(`structure.md`)에서 한다.
- 메모에 없는 이유·선택지·맥락을 지어 넣지 않는다. 없으면 "미확인".
- 실패한 push를 그대로 되풀이하지 않는다. 8단계의 리베이스 한 번 뒤에도 안 되거나 충돌이면 커밋만 남기고 보고한다.
- 상황판 묶음을 고치지 않는다. 그 프로젝트에서 일한 세션이 고친다.
