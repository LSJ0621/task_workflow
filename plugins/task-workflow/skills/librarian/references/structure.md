# 구조 점검 절차 (사서)

지식 베이스의 문서 구조를 분석해 문서를 나눌지 합칠지 옮길지 판단하고, 바꿀 게 있으면 바꾼다. 주 1회 예약 작업이나 사용자 요청으로 한다.
정리 절차와 따로 둔 이유는 하는 일이 달라서다. 정리는 메모를 기록으로 옮기는 일이고, 구조 점검은 쌓인 기록이 찾기 쉬운지 보는 일이다.

아래 명령의 `<사서 폴더>`는 이 스킬 폴더(이 파일의 한 단계 위 폴더)다.

## 순서

1. **읽기.** 지식 베이스를 찾아 최신으로 맞춘다. 찾는 방법은 사서 [SKILL.md](../SKILL.md) "지식 베이스 찾기" 절이고, 맞추는 방법은 [정리 절차](shelving.md) 1단계와 같다.
   그다음 같은 폴더의 `records.md`와 `writing.md`를 읽는다. 판단 기준은 `records.md`의 "문서를 나눌지 합칠지" 절이다. 기준을 여기에 다시 쓰지 않는다.
   지식 베이스에서는 `INDEX.md`, 폴더와 파일 목록, `wiki/`의 요약 문서, `tests/regression.md`를 읽는다.
2. **분석.** 찾기 어려워진 곳이 있는지 본다.
   - 색인(`INDEX.md`)이 실제 폴더·파일과 다른 곳이 있는가.
   - 요약 문서에서 필요한 줄을 찾기 어려워진 곳이 있는가. 읽을 때마다 필요하지 않은 내용이 한 문서에 섞여 있는가.
   - 같은 사실이 두 곳에 있는가.
   - 회귀 질문 몇 개를 골라 색인에서 시작해 답을 실제로 찾아 본다. 찾는 길이 막히는 곳이 고칠 곳이다.
   파일 수나 줄 수만으로 정하지 않는다. 많아도 잘 찾아지면 그대로 둔다.
3. **바꿀 게 없으면 끝낸다.** 보고에 "바꿀 것 없음"이라고 적는다. 억지로 나누지 않는다. 옮길 때마다 링크와 색인이 흔들리기 때문에, 바꾸는 쪽이 이유를 대야 한다.
4. **바꾼다.** 파일 이동·합치기·나누기·이름 바꾸기는 별도 로컬 브랜치 `proposal/structure-YYYYMMDD`에서 한다. 지식 베이스 체크아웃은 main에서 옮기지 않는다. 사용자와 대화 중인 다른 세션이 같은 폴더의 main에 메모를 커밋하고 있을 수 있어서다. 그래서 임시 작업 폴더(worktree)에서 고친다.
   이 절차의 임시 worktree는 사용자와 정한 방식이라 확인받지 않고 쓴다. 지식 베이스 체크아웃의 브랜치를 바꾸지 않으려는 것이다.
   ```bash
   wt="$(mktemp -d)/proposal"
   git -C "$KNOWLEDGE_BASE_DIR" worktree add -b proposal/structure-YYYYMMDD "$wt" main
   # 같은 이름 브랜치가 이미 있으면(같은 날 두 번째 점검) -b 없이: worktree add "$wt" proposal/structure-YYYYMMDD
   # "$wt"에서 파일을 옮기고 커밋한다. 커밋 첫 줄은 "구조 변경 제안: <한 문장>"
   git -C "$KNOWLEDGE_BASE_DIR" worktree remove "$wt"
   ```
   - 옮긴 파일을 가리키는 색인(`INDEX.md`)과 회귀 질문의 "답 위치"도 같은 브랜치에서 고친다.
   - 원본(`raw/`)의 본문, 식별자, 파일명은 바꾸지 않는다(`records.md` 불변 조건).
   - 커밋 메시지에 무엇을 어디로 왜 옮겼는지 적는다. 점검 보고(`review-report` 스킬)가 이 커밋을 읽어 사용자에게 보여 준다. 다른 곳에 따로 적지 않는다.
   - 구조 변경이 아닌 수정을 이 브랜치에 섞지 않는다.
5. **머지한다.** 커밋을 마치면 묻지 않고 바로 main에 머지하고 push한다. 방법은 `merging.md`다.
6. **머지 뒤 확인.**
   - 회귀 질문(`tests/regression.md`)을 하나씩 본다. 답 위치에 적힌 기록이나 문서가 여전히 찾아지는지 확인한다.
   - 불변 조건을 점검한다. 사례 분류는 이 절차의 일이 아니라서 그 검사는 건너뛴다.
     ```bash
     python3 "<사서 폴더>/scripts/check_invariants.py" "$KNOWLEDGE_BASE_DIR" --skip-rule-cases
     ```
   - 찾아지지 않는 답이나 점검 문제가 구조 변경 탓이면 색인이나 답 위치를 고쳐 main에 커밋하고 push한다. 고치지 못하면 보고의 "확인할 것"에 적는다.
7. **보고.** 두 줄.
   - **완료**: "바꿀 것 없음" 또는 무엇을 어디로 왜 옮겼는지와 머지 커밋 해시. 바꿀지 말지가 갈렸던 곳이 있으면 그대로 둔 이유도 한 줄 적는다. 회귀 질문 n개 중 답이 찾아진 수. 점검 스크립트 결과.
   - **확인할 것**: 머지 충돌로 남긴 브랜치, 찾아지지 않는 회귀 질문, 고치지 못한 점검 문제. 없으면 "없음".

## 하지 말 것

- 숫자 기준(파일이 몇 개면 나눈다 같은 것)을 만들어 쓰지 않는다. 그때의 문서를 읽고 판단한다.
- 파일을 main에서 직접 옮기거나 합치지 않는다. 구조 브랜치에서 하고 머지한다.
- 지식 베이스 체크아웃의 브랜치를 바꾸지 않는다. 작업은 worktree에서 한다.
- 원본의 본문을 고치거나 기록을 지우지 않는다.
- 규칙(스킬, 훅, 전역 지침, 응답 양식)을 고치지 않는다. 자가 발전(`analyze-context` 스킬)의 일이다.
- 사용자에게 묻지 않는다. 구조 변경은 내용이 바뀌지 않는 일이라 묻지 않고 한다(`records.md` 승인 범위 절).
