"메모해", "기록해 둬", "이건 기억해" 같은 말이 없어도 그런 일이 생기면 쓴다. 프로젝트의 작업 단위가 끝나 상황판을 고칠 때와, 상황판에 쌓인 그 프로젝트의 지침 후보를 프로젝트 지침으로 옮길 때도 쓴다. 메모를 원본 기록으로 만드는 일은 write-records가, 요약 문서에 올리거나 문서 구조를 점검하는 일은 librarian이 한다. 지식 베이스를 읽기만 할 때는 쓰지 않는다.

# 메모 남기기

지식 베이스에 적는 것은 사용자와 일하는 세션이다. 원본 기록은 새벽에 기록 단계(`write-records`)가 만든다.
이 스킬은 적는 쪽의 일 세 가지다. 메모 한 줄, 상황판의 자기 묶음, 프로젝트 지침 후보 가져가기.
메모는 "새벽에 기록을 만들 때 어디를 볼지 알려 주는 표지"다. 기록 단계는 메모에 적힌 세션 id로 세션 기록을 찾아 그 대화를 그대로 뽑는다. 그래서 메모는 짧아도 되지만 세션 id와 사용자 말은 정확해야 한다.
지금 틀을 채우거나 요약 문서를 고치지 않는다. 기록은 새벽에만 만든다.

## 지식 베이스 찾기

1. `$KNOWLEDGE_BASE_DIR`이 있으면 그곳.
2. 없으면 현재 폴더가 지식 베이스인지 본다. `INDEX.md`와 `raw/journal/`이 있는 git 저장소면 맞다.
3. 둘 다 아니면 아무것도 쓰지 않고 `setup-knowledge-base` 스킬로 지식 베이스를 만들거나 연결하라고 안내한다.

## 메모 한 줄

1. **형식을 읽는다.** [메모 형식](../librarian/references/memo-format.md)이다. 짧은 파일이다. 종류(`feedback`, `decision`, `context`, `notfound`), 내용 칸을 나누는 표시(`사용자 말:`, `풀이:`), 세션 id 칸(`session:`)이 거기 있다. 형식은 그 파일에만 있다.
2. **적는 때를 고른다.** 프롬프트마다 적지 않는다. 주제 하나가 끝날 때 한 줄이다.
   - 고치는 말이 오가는 동안은 적지 않는다. 결론이 나면 한 줄로 적는다. 같은 주제의 연속 피드백은 한 줄로 묶는다.
   - 사용자가 고친 말이 화면 모양, 글의 양, 말투처럼 사용자의 취향을 드러내면 `feedback` 줄과 함께 그 취향을 적은 `context` 줄도 남긴다. `feedback`은 실수 사례가 될 뿐이고, 화면 작업 같은 스킬이 읽는 취향 요약(`wiki/context.md`의 `taste` 절)에는 `context`로 남긴 것만 오르기 때문이다. 예: 버튼을 모두 둥글게 만들었다가 "버튼은 각지게 해 줘"라는 말을 들었으면, 둥글게 만든 일은 `feedback`, 버튼은 각진 모양을 좋아한다는 것은 `context`로 적는다.
   - "다음 답은 짧게 해 줘"처럼 그 답 하나에만 해당하는 말은 적지 않는다. 앞으로도 계속 적용할 말일 때만 남긴다.
   - 바로 적는 것: 사용자가 "메모해"라고 했을 때, 급한 메모(`urgent`)일 때, 못 찾은 것(`notfound`)일 때.
3. **세션 id를 구한다.** 환경 변수 `CLAUDE_CODE_SESSION_ID`의 값이다.
   ```bash
   echo "${CLAUDE_CODE_SESSION_ID:--}"
   ```
   값이 있으면 줄 끝 칸에 `session:<그 값>`, 없으면 `session:-`라고 적는다. 지어내거나 다른 세션의 id를 적지 않는다. 틀린 id보다 `-`가 낫다. `-`면 기록 단계가 사용자 말로 세션을 찾는다.
   다른 세션의 id를 적지 않는다는 것은 낮의 작업 세션에 해당하는 말이다. 새벽 3단계(`analyze-context`)가 예전 세션에서 찾은 말을 메모로 덧붙일 때는 그 말이 나온 세션의 id를 적고 내용 칸 맨 앞에 `그때: YYYY-MM-DD HH:MM`을 둔다. 형식은 메모 형식의 "예전 세션의 말을 가리키는 메모" 절이다.
4. **한 줄 덧붙인다.** 오늘 날짜 파일이 없으면 만든다. 글은 사서의 [글쓰기 규칙](../librarian/references/writing.md)을 따른다. 한 사건에 두 줄 넘게 쓰지 않는다. 자세한 것은 새벽에 세션 기록에서 뽑으니 메모에 다 담지 않는다.
5. **급한지 본다.** 오늘 다른 세션의 작업이 이 메모에 바로 걸리면 줄 끝에 ` | urgent`를 붙인다. 바로 기록으로 만들지는 않는다. 기록은 새벽에만 만든다. 다른 세션은 정리 전 메모를 `raw/journal/`에서 직접 읽는다. `urgent`는 그 세션이 읽을 수 있게 바로 push한다는 뜻이다.
6. **커밋한다.** 먼저 `git pull --ff-only`. push 안 된 로컬 커밋이 있어 안 되면 `git pull --rebase`. 그다음 그 파일만 커밋한다. 메시지는 "메모: <종류> <요지>". pull이 충돌하면 커밋만 남기고 알린다.
   push는 하지 않는다. 밀린 메모 커밋은 새벽 정리의 push가 한꺼번에 올린다. 바로 push하는 것은 `urgent` 메모와 사용자가 "메모해"라고 한 메모뿐이다.
7. **이해한 뜻을 보여 준다.** 답 끝에 두 줄로 알린다.
   ```
   메모 남김: `raw/journal/YYYY-MM-DD.md` (종류)
   이렇게 이해했습니다: <메모의 `풀이:`에 적은 문장>
   ```
   묻는 것이 아니라 보여 주는 것이다. 사용자가 아무 말 안 하면 맞는 것으로 둔다. 사용자가 뜻이 다르다고 하면 그 자리에서 `정정:` 줄을 하나 더 적는다.
   이 한 줄을 두는 이유: 메모에 붙인 풀이가 사용자 뜻보다 좁으면 그 풀이가 사례에 남고 규칙을 고칠 때 참고가 된다. 사용자가 틀린 풀이를 볼 수 있는 때는 적는 그 순간뿐이다.
   풀이가 없는 메모(사용자 말이 없는 사실 기록, `notfound`)는 첫 줄만 쓴다.

## 못 찾은 것 (`notfound`)

지식 베이스에서 작업에 필요한 것을 찾았는데 쓸 만한 답이 없었을 때 남긴다. 지식 베이스에 무엇이 비어 있는지, 있는데 왜 못 찾는지를 새벽 분석이 알 수 있게 하기 위해서다.

- 남기는 때: 색인(`INDEX.md`) → 요약(`wiki/`) → 원본(`raw/`) 순서로 찾았는데 답이 없었거나, 있는데 부족했을 때. 셋을 다 보기 전에는 남기지 않는다.
- 남기지 않는 때: 찾아서 답을 얻었을 때. 지식 베이스에 있을 일이 아닌 것(코드의 동작, 프로젝트 문서에 있는 것)을 찾았을 때.
- 적는 것: 무엇이 필요했는지, 어떤 파일을 열어 봤는지, 없었는지 부족했는지. 형식은 메모 형식의 `notfound` 절이다.
- 정말 없는지는 판단하지 않는다. "지식 베이스에 없다"고 단정해 적지 않고 찾아본 곳까지만 적는다. 있는데 못 찾은 것인지는 새벽 분석이 가린다.
- 못 찾아서 사용자에게 물었고 답을 들었으면, 그 답은 새로 알게 된 사실이다. `context`나 `decision` 줄로 따로 남긴다.

## 상황판

지식 베이스 `wiki/board.md`는 프로젝트마다 지금 어디까지 왔는지 적는 곳이다. 프로젝트 하나에 `## <프로젝트 이름>` 묶음 하나다.

- 프로젝트에서 작업 단위 하나가 끝나면 그 일을 한 세션이 **자기 프로젝트 묶음만** 고친다. 다른 프로젝트 묶음은 건드리지 않는다. 여러 세션이 같은 파일을 고쳐도 충돌하지 않게 하기 위해서다.
- 묶음에는 다섯 줄을 둔다.
  ```markdown
  ## <프로젝트 이름>
  - 어디까지: 끝낸 것 한두 문장
  - 다음 할 일: 한두 문장
  - 막힌 것: 사용자 답이나 외부 사정으로 멈춘 것. 없으면 "없음"
  - 지침 후보: 없음
  - 고친 날짜: YYYY-MM-DD
  ```
- 묶음이 없는 프로젝트면 새로 만든다. 프로젝트 이름은 `wiki/projects/`의 카드 이름과 맞춘다.
- 위 네 줄(어디까지, 다음 할 일, 막힌 것, 고친 날짜)은 덮어써도 되는 요약이다. 지난 진행 내용은 git 이력과 메모에 남는다.
- "지침 후보" 줄은 덮어쓰지 않는다. 아래 절대로 다룬다. 예전 묶음에 이 줄이 없으면 `- 지침 후보: 없음`을 더한다.
- 커밋은 메모와 같다. pull 뒤 main에 "상황판: <프로젝트> <요지>"로 커밋하고 push는 하지 않는다.
- 자가 발전이 플러그인을 고친 것도 작업 단위다. 자가 발전은 플러그인 프로젝트의 묶음을 이 절의 형식대로 고친다. 새벽 실행에서는 커밋만 하고 push는 4단계 정리(안 도는 날은 메인 세션)가 한다. 사용자가 불러 돈 실행만 바로 push한다(`analyze-context` 스킬 순서 3단계 "지식 베이스 커밋을 올리는 때").

## 프로젝트 지침 후보

자가 발전(`analyze-context`)은 한 프로젝트에만 걸리는 규칙을 찾아도 그 프로젝트의 지침을 직접 고치지 않는다. 사용자가 작업 중일 수 있고, 그 프로젝트의 지금 상황은 그 프로젝트 세션이 가장 잘 알기 때문이다.
대신 상황판의 그 프로젝트 묶음 "지침 후보" 줄 아래에 후보를 적어 둔다.

```markdown
- 지침 후보:
  - 화면에 소개·안내 문구를 넣지 않는다 | C-20250101-03, C-20250102-01 | 적은 날 2025-01-03
```

그 프로젝트에서 일한 세션은 상황판을 고칠 때 후보를 본다.

1. 후보마다 근거 사례(`raw/cases/`)를 열어 사용자 말을 읽는다.
2. 그 프로젝트의 지금 상황에 맞으면 프로젝트 지침(`CLAUDE.md`나 `AGENTS.md`, 없으면 그 프로젝트가 지침을 두는 문서)에 넣고 후보 줄을 지운다. 문장을 그대로 옮기지 않고 그 프로젝트의 말로 쓴다.
3. 맞지 않으면 후보 줄을 지우고, 상황판 커밋 메시지에 지운 이유를 한 줄 적는다. 자가 발전이 같은 후보를 다시 올리지 않게 하기 위해서다.
4. 판단이 안 서면 그대로 둔다.
5. 후보가 하나도 안 남으면 `- 지침 후보: 없음`으로 돌린다.

프로젝트 지침을 고치는 것은 그 프로젝트 저장소의 커밋이다. 그 프로젝트의 커밋 규칙을 따른다.

## 하지 말 것

- 메모 줄을 고치거나 지우지 않는다. 잘못 적었으면 정정 줄을 하나 더 쓴다.
- 정식 기록의 틀을 채우거나 맥락 요약·카드·색인을 고치지 않는다. 기록은 새벽의 기록 단계(`write-records`)가, 요약은 사서 정리가 한다. 급한 메모도 바로 기록으로 만들지 않는다. 규칙별 사례표도 고치지 않는다. 자가 발전의 일이다.
- 다른 프로젝트의 상황판 묶음과 지침 후보를 건드리지 않는다.
- 사용자가 한 말을 요약하거나 다듬어 `사용자 말:`에 넣지 않는다. 그대로가 재료다.
- 규칙(스킬, 훅, 전역 지침, 응답 양식)을 만들거나 고치지 않는다. 자가 발전의 일이다. 사용자가 대화 중에 규칙을 정하면 `analyze-context` 스킬의 "사용자가 대화 중에 규칙을 정했을 때" 절을 따른다.
- 세션 id를 지어내지 않는다. 모르면 `session:-`다. 낮의 작업 세션은 자기 세션이 아닌 id를 적지 않는다.
- 지식 베이스에 정말 없다고 단정하지 않는다. `notfound`에는 찾아본 곳까지만 적는다.
- 비밀값, 자격 정보, 고객 인프라 식별자를 적지 않는다.
