# 기록 쓰기

메모는 작업 세션이 한 번 해석해서 줄인 글이다. 메모를 원본으로 삼으면 메모가 틀렸을 때 그 위의 기록, 요약, 규칙이 전부 틀린다.
그래서 원본은 세션 기록에서 뽑는다. 메모는 "어느 세션의 어느 때쯤"을 가리키는 표지로만 쓴다.
이 스킬은 그 일을 한다. 메모 줄마다 세션 기록에서 범위를 고르고, 스크립트로 뽑아 발췌 파일과 기록 파일에 넣고, 요지를 쓴다.
여기서 만든 기록은 `status: draft`다. 기록 확인(2단계)을 통과해야 `active`가 된다.

## 지식 베이스 찾기

1. `$KNOWLEDGE_BASE_DIR`이 있으면 그곳.
2. 없으면 현재 폴더가 지식 베이스인지 본다. `INDEX.md`와 `raw/journal/`이 있는 git 저장소면 맞다.
3. 둘 다 아니면 아무것도 쓰지 않고 `setup-knowledge-base` 스킬로 지식 베이스를 만들거나 연결하라고 안내한다.

## 먼저 읽을 것

형식은 사서 폴더(`../librarian/`)에 있다. 지식 베이스에는 규칙 문서가 없다.

- 메모 형식: `../librarian/references/memo-format.md`
- 기록 형식(머리말, 불변 조건, 승인 범위): `../librarian/references/records.md`
- 틀: `../librarian/references/templates/`의 `case.md`, `decision.md`, `context.md`
- 글쓰기 규칙: `../librarian/references/writing.md`

## 스크립트

`scripts/session_extract.py`(이 스킬 폴더 기준). 세션 기록을 읽는 일은 전부 이 스크립트로 한다. 세션 기록 파일을 직접 열어 옮겨 적지 않는다. 손으로 옮기면 빠지거나 바뀐 곳을 아무도 알 수 없어서다.
세션 기록은 세션 id로 전체에서 찾는다. 세션이 폴더를 옮기면 기록 위치도 바뀌기 때문이다.

| 명령 | 언제 쓰나 |
| :- | :- |
| `pending <지식 베이스>` | 대상을 고를 때. 정리 안 된 메모 줄이 있는 파일과 줄 수, `draft` 기록의 경로를 찍는다. 마지막 줄은 `합계`, `메모 n`, `draft n`이다 |
| `find --text "<글>" [--date YYYY-MM-DD]` | 메모에 세션 id가 없을 때. 사용자 말에 그 글이 들어 있는 줄을 모든 세션에서 찾는다. 먼저 `--date` 없이 찾는다. 줄마다 세션 id, uuid, 날짜와 시각(`YYYY-MM-DD HH:MM`), 첫 80자가 나온다 |
| `list --session <id> [--around HH:MM] [--window 분] [--date YYYY-MM-DD]` | 범위를 고를 때. 묶음마다 번호(세션 기록 파일의 줄 번호), 시각(`MM-DD HH:MM`), 누구(사용자/에이전트/도구), 첫 80자, uuid가 나온다. `--window`의 기본은 앞뒤 30분이다. 여러 날에 걸친 세션은 `--date`로 하루만 본다 |
| `extract --session <id> --from <uuid> --to <uuid> [--omit <uuid> ...] --save <지식 베이스> [--replace]` | 고른 범위를 뽑는다. 뽑은 글 전체는 발췌 파일에 적고, 기록에 넣을 글은 표준 출력에 찍는다 |
| `verify <기록 파일> [--knowledge-base <지식 베이스>]` | 기록 파일에 넣은 뒤. 머리말의 `session`·`range`·`omitted`로 다시 뽑아 표시 사이와 발췌 파일의 그 범위 묶음을 글자 단위로 비교한다. 지식 베이스를 안 주면 기록 파일의 위쪽 폴더에서 찾는다. `source: memo`인 기록은 댈 세션 기록이 없어 대조 없이 통과한다. `source: agent`인 기록은 대상이 아니라 코드 1로 거절한다 |

- 출력의 칸은 탭으로 나뉜다. 시각은 이 컴퓨터의 시간대다. 결과는 표준 출력에, 오류 글은 표준 오류에 나온다.
- 세션을 이어서 열면 같은 uuid의 줄이 여러 세션 기록 파일에 들어 있을 수 있다. uuid는 늘 세션 id와 함께 쓴다. `find`가 같은 줄을 여러 세션으로 내면 메모의 `session:` 칸과 같은 세션을, 그 칸이 없으면 그중 하나를 골라 그 세션 id로 `list`와 `extract`를 돌린다.
- `confirm`은 이 단계에서 돌리지 않는다. 확정은 기록 확인을 통과한 뒤 메인 세션이 한다.

### 뽑은 글이 들어가는 두 곳

뽑은 글의 형식은 이 절에만 적는다. 기록 확인(`record-checker`)도 이 절을 본다.

**발췌 파일** `raw/sessions/<세션 id>.md`. 세션마다 파일 하나다. 뽑은 글 전체(발췌 전문)가 여기에 범위마다 묶음 하나로 한 번만 들어간다. 여러 기록이 같은 대화를 통째로 품지 않게 하기 위해서다.

- 묶음은 `<!-- range:start <첫 줄 uuid>..<끝 줄 uuid> -->` 줄과 `<!-- range:end -->` 줄 사이다. 뺀 줄이 있으면 시작 줄에 `omitted:<uuid>,<uuid>`가 붙는다.
- 스크립트만 적는다. 손으로 고치지 않는다. 같은 범위를 다시 뽑으면 다시 적지 않는다.
- `--omit`을 더 주고 같은 범위를 다시 뽑으면 덜 뺀 묶음은 스크립트가 지운다. 뺀 줄이 파일에 남지 않게 하기 위해서다.
- 있는 묶음이 다시 뽑은 것과 다르면 코드 5로 멈춘다. 스크립트가 고쳐져서 달라진 것일 때만 `--replace`를 주어 바꾼다.

**기록의 표시 사이.** `extract --save`가 표준 출력에 찍는 글이다. 발췌 전문에서 아래만 남긴 것이다.

- 첫 줄은 발췌 위치다. `발췌: raw/sessions/<세션 id>.md <첫 줄 uuid>..<끝 줄 uuid>` 꼴이다.
- 그 아래에 **사용자** 묶음 전부와, **도구** 묶음 가운데 `Skill`과 `Read` 줄이 순서대로 나온다. 남는 줄이 없는 도구 묶음은 빠진다.
- 에이전트의 말과 그 밖의 도구 줄은 기록에 없고 발췌 파일에만 있다. 그래서 `## 요지`를 쓸 때와 범위를 고를 때는 발췌 파일의 그 범위 묶음을 본다.

발췌 전문은 이렇게 생겼다.

- 묶음은 `**사용자** (HH:MM)`, `**에이전트** (HH:MM)`, `**도구** (HH:MM)` 머리줄로 시작한다. 말은 `> ` 인용 줄로, 도구 호출은 `- ` 줄로 나온다.
- 묶음은 세션 기록의 한 줄마다 따로 찍힌다. 에이전트가 한 줄에서 도구를 여럿 불렀으면 `**도구**` 묶음 하나에 `- ` 줄이 여럿 나온다. 다른 줄에서 불렀으면 머리줄이 다시 나와 `**도구**` 묶음이 여러 개 이어진다.
- 도구마다 싣는 칸이 정해져 있다. Skill은 스킬 이름, Read·Edit·Write는 파일 경로, Bash는 `description`, Agent는 `subagent_type | description`, 그 밖은 도구 이름만이다. 명령어 본문, 도구 결과, 생각 과정은 싣지 않는다.
- 사용자가 넣은 그림은 `[이미지]`로 실린다. 에이전트가 일하는 중에 사용자가 친 글도 사용자 말로 실린다. 시스템이 끼워 넣은 알림과 훅 출력은 빠진다.
- 서브에이전트 안에서 오간 말과 도구 호출은 읽지 않는다. 메인 세션이 서브에이전트를 부른 줄(`Agent:`)만 실린다.
- 뺀 줄(`--omit`)은 `> [비밀값이 있어 뺌]`으로 나온다. 길어도 자르지 않는다.

예전 기록은 표시 사이에 발췌 전문이 통째로 있다. `--save` 없이 뽑던 때의 꼴이다. 고치지 않고 그대로 두며 `verify`도 그대로 통과한다. 새 기록은 늘 `--save`로 뽑는다.

종료 코드마다 할 일이 정해져 있다.

| 코드 | 뜻 | 할 일 |
| :- | :- | :- |
| 0 | 성공 | 다음으로 간다 |
| 1 | 사용법 오류 | 명령을 고쳐 다시 돌린다 |
| 2 | 세션이나 uuid를 못 찾음 | 세션 id가 틀렸을 수 있으니 `find --text`로 한 번 찾는다. 그래도 없으면 `source: memo`로 만든다 |
| 3 | 모르는 형식 | 뽑지 못한다. 아래 "모르는 형식이 나왔을 때"를 따른다 |
| 4 | 비밀값 모양 | 같이 나온 uuid를 `--omit`에 넣어 다시 뽑는다. 그 uuid를 머리말 `omitted`에 적는다 |
| 5 | 불일치 | `verify`에서는 표시 사이나 발췌 파일의 범위 묶음이 다시 뽑은 것과 다르거나, 발췌 파일이나 그 묶음이 없다. 다시 뽑아 그대로 넣는다. `extract --save`에서는 발췌 파일에 있는 같은 범위의 묶음이 다시 뽑은 것과 다르다. 스크립트가 고쳐져 달라진 것이면 `--replace`로 바꾼다 |

## 순서

1. **지식 베이스를 최신으로 맞추고 대상을 고른다.**
   - main 브랜치에서 `git pull --ff-only`. push 안 된 자기 커밋이 있어 안 되면 `git pull --rebase`. HEAD가 브랜치에 붙어 있지 않으면 기록하지 말고 보고한다.
   - 대상은 둘이다. `raw/journal/`의 날짜 파일마다 마지막 `정리됨:` 줄 뒤에 있는 메모 줄, 그리고 `raw/` 아래 `status: draft`로 남아 있는 기록.
     - `정리됨:` 줄이 없는 파일은 메모 줄 전부가 대상이다. 한 파일에 `정리됨:` 줄이 여러 개 있을 수 있다. 기록한 뒤에 메모가 더 붙은 파일이다. 마지막 `정리됨:` 줄보다 앞의 메모 줄은 이미 기록된 것이라 다시 만들지 않는다.
     - 어느 파일에 몇 줄이 남았고 어느 기록이 `draft`인지는 `pending "$KNOWLEDGE_BASE_DIR"`로 본다.
     - `source: agent`인 기록은 에이전트가 스스로 정한 구조 결정을 직접 쓴 것이다(`records.md` "구조 결정 기록" 절). 사용자 말이 없어 처음부터 `active`다. 이 단계는 그런 기록을 만들지도 고치지도 않는다.
   - 둘 다 없으면(`합계` 줄이 `메모 0`, `draft 0`) 할 일이 없다고 보고하고 끝낸다.
2. **메모 줄마다 세션 기록에서 그 일을 찾는다.**
   - `session:` 칸에 세션 id가 있으면 `list --session <id> --around HH:MM --date YYYY-MM-DD`로 그 시각 근처를 본다. 시각은 메모 줄의 시각, 날짜는 메모 파일의 날짜다. 메모는 일이 끝난 뒤에 적으니 메모 시각보다 앞쪽을 본다.
     - 메모는 한꺼번에 몰아서 적히기도 한다. 그래서 그 말이 나온 때가 메모 시각보다 훨씬 앞이거나 전날일 수 있다. 메모 시각 근처에 그 말이 없으면 `--window`를 넓히거나 전날 날짜로 본다.
   - 내용 칸이 `그때: YYYY-MM-DD HH:MM`으로 시작하는 메모는 그 말이 나온 때가 메모를 적은 때와 다른 메모다. 3단계가 예전 세션에서 찾은 말을 적어 둔 것이다(`memo-format.md` "예전 세션의 말을 가리키는 메모" 절). 메모 시각과 메모 파일의 날짜가 아니라 `그때:`의 날짜와 시각으로 `list`를 본다. 머리말 `memo`에는 그 메모 줄의 날짜와 시각을 그대로 적는다.
   - `session:-`이거나 `session:` 칸이 없는 예전 줄이면 `find --text`로 `사용자 말:`의 한 구절을 찾는다. 문장 전체가 아니라 다른 데 안 나올 짧은 구절로 찾는다.
     - 먼저 `--date` 없이 찾는다. 그 말이 메모를 적은 날보다 앞선 날에 나왔을 수 있어서다. 메모 날짜를 주면 그런 말을 못 찾는다.
     - 여러 곳이 나오면 메모 시각보다 앞이면서 가장 가까운 것을 고른다.
   - `--date` 없이도 못 찾았을 때만 `source: memo`로 만든다(아래 절).
3. **범위를 정한다.** 기준은 아래 "범위를 정하는 기준" 절이다. `list` 출력에서 첫 줄과 끝 줄의 uuid를 고른다.
4. **뽑아서 기록 파일을 만든다.**
   - 식별자는 스크립트로 받는다. 손으로 세면 겹친다.
     ```bash
     python3 "<사서 폴더>/scripts/next_id.py" "$KNOWLEDGE_BASE_DIR" C   # C|D|X
     ```
   - `extract`에 `--save "$KNOWLEDGE_BASE_DIR"`를 주어 뽑는다. 발췌 전문은 스크립트가 발췌 파일에 적는다. 표준 출력은 파일로 받는다. 그 파일은 `mktemp -d`로 만든 임시 폴더에 둔다. 지식 베이스나 스킬 폴더에 두지 않는다.
   - 받은 글을 `<!-- extract:start -->`와 `<!-- extract:end -->` 사이에 그대로 넣는다. 다시 타이핑하지 않고, 줄이지 않고, 고치지 않는다.
   - 머리말을 채운다. `status: draft`, `source: session`, `session`, `range: <첫 줄 uuid>..<끝 줄 uuid>`, `omitted`, `memo: YYYY-MM-DD HH:MM`(이 기록이 나온 메모 줄). `date`는 메모 파일의 날짜다.
   - `## 요지`를 쓴다. 발췌 전문(발췌 파일의 그 범위 묶음)에 있는 것만 가지고 쓴다. 메모에만 있고 뽑은 글에 없는 내용은 요지에 넣지 않는다. 꼭 필요한 내용이 빠졌으면 요지에 보태지 말고 범위를 넓혀 다시 뽑는다.
   - 종류별로 쓰는 것, `scope`, `related`, 대체됨 표시는 아래 "종류별로 만드는 법" 절을 따른다.
   - `verify <기록 파일>`을 돌려 0이 나오는지 본다. 그 뒤에 `## 요지`나 머리말을 고쳤으면 커밋 전에 그 기록의 `verify`를 다시 돌린다.
5. **`draft` 기록을 다시 만든다.** 대상에 `draft` 기록이 있을 때다(아래 절).
6. **메모 파일을 마감하고 커밋한다.**
   - 처리한 날짜 파일 끝에 `정리됨: <만든 id들>` 한 줄을 덧붙인다. 만든 기록이 없으면 `정리됨: 없음`. 앞에 `정리됨:` 줄이 이미 있는 파일에도 끝에 새로 한 줄을 더한다. 있던 `정리됨:` 줄과 메모 줄은 건드리지 않는다.
   - 커밋하기 전에 불변 조건을 점검한다. 사례 분류와 요약은 뒤 단계의 일이라 그 두 검사는 건너뛴다. 이번에 만든 기록에서 나온 문제(머리말에 빠진 칸, 겹친 식별자, 표시)는 고친다. 그 밖의 문제는 고치지 않고 보고의 "확인할 것"에 적는다.
     ```bash
     python3 "<사서 폴더>/scripts/check_invariants.py" "$KNOWLEDGE_BASE_DIR" --skip-rule-cases --skip-summary
     ```
   - main에 "기록 YYYY-MM-DD: 사례 n, 결정 n, 맥락 n"으로 커밋한다. 이번에 만들거나 고친 파일만 커밋한다. 스크립트가 적은 발췌 파일(`raw/sessions/`)도 함께 커밋한다. 빠지면 기록 확인의 `verify`가 통과하지 못한다.
   - push는 하지 않는다. 4단계 정리나 메인 세션이 올린다.
7. **보고한다.** 형식은 아래 "보고" 절이다.

## 범위를 정하는 기준

범위는 필요한 만큼만 잡는다. 다만 원인이 될 행동이 빠지면 뒤 단계가 원인을 따질 수 없다. 모자란 것보다 조금 넓은 쪽이 낫다.

- **지적(`feedback`)**: 지적받은 답을 내기까지의 흐름 전체다. 그 요청, 그 사이 도구 호출, 그 답, 사용자의 지적, 결론이 난 곳까지.
  - 지적의 원인이 될 행동(읽은 파일, 부른 스킬)이 범위 앞에 잘리지 않게 한다. 지적받은 답이 앞선 요청에서 읽은 것에 기대고 있으면 그 요청부터 잡는다.
  - 고치는 말이 여러 번 오갔으면 마지막 결론까지 넣는다.
  - 사용자가 그 지적을 거둔 말("내가 착각했어", "내가 검수를 잘못했어" 같은 것)이 뒤에 있으면 그 말까지 넣는다.
- **결정(`decision`)·맥락(`context`)**: 그 말이 나온 앞뒤다. 사용자가 그렇게 말하게 된 질문이나 제안부터, 정해졌다는 것이 드러나는 답까지.
- **못 찾음(`notfound`)**: 그것이 필요해진 요청부터, 지식 베이스를 찾아본 도구 호출, 못 찾고 어떻게 했는지가 드러나는 답까지.
- 범위는 에이전트의 글에서 시작해도 된다. 사용자의 말이 에이전트의 제안에 대한 답이면 그 제안부터 잡는다.
- 한 대화에서 메모가 여러 줄 나왔으면 기록마다 범위를 따로 잡는다. 범위가 겹쳐도 된다.

## 종류별로 만드는 법

메모의 종류 칸이 틀을 정한다. 메모의 `사용자 말:`은 사실이고 `풀이:`는 메모를 적은 에이전트의 추정이다. 풀이를 사용자 말처럼 적지 않는다. 표시가 없는 예전 메모는 따옴표 안의 말만 사용자 말로 보고, 나머지는 풀이로 본다.

메모 한 줄은 기록 하나로 만든다. 한 줄에 사실이 둘이어도 나누지 않는다.

### `feedback` → 사례(`C-`)

- 제목은 에이전트가 한 일로 적는다. 풀이를 제목으로 쓰지 않는다.
- `## 요지`에 `### 어떤 작업에서`(작업 설명 한 줄)와 `### 에이전트가 한 것`(한두 문장. 판단 없이)을 쓴다.
- `## 분석`에는 "아직 없음"이라고 둔다. 3단계가 채운다. 원인이나 관련 규칙을 여기서 적지 않는다.
- 메모에 `풀이:`가 있으면 `## 분석` 아래 `### 메모의 풀이`로 그대로 옮겨 둔다. 에이전트의 추정이라는 표시다. 풀이가 없으면 이 절을 두지 않는다.
- 사용자가 그 지적을 거둔 말이 있으면 머리말 `tags`에 `retracted`를 넣는다. 자가 발전이 이 표시로 재발에서 뺀다.
- 메모에 관련 id가 있으면 `related`에 넣는다.
- `정정:`으로 시작하는 메모 줄은 앞선 메모의 풀이를 사용자가 바로잡은 것이다.
  - 같은 날 아직 기록이 안 된 메모를 바로잡으면 한 사례로 합친다. 범위에 바로잡는 말까지 넣고, `### 메모의 풀이`에는 바로잡은 뜻을 쓴다. `memo`에는 처음 줄의 시각을 적는다.
  - 이미 기록이 된 것을 바로잡으면 새 사례를 만들고 `related`에 그 id를 넣는다.

### `notfound` → 사례(`C-`)

- 머리말 `tags`에 `notfound`를 넣는다.
- 제목은 에이전트가 한 일로 적는다. 예: "배포 순서를 지식 베이스에서 찾지 못했다".
- `## 요지`에 `### 찾던 것`과 `### 찾아본 곳`을 쓴다. `### 어떤 작업에서`와 `### 에이전트가 한 것`은 쓰지 않는다.
- `## 분석`은 "아직 없음". 정말 없는 것인지, 있는데 못 찾은 것인지는 여기서 가리지 않는다. 3단계가 가린다.

### `decision` → 결정(`D-`)

- `## 요지`에 `### 결정`, `### 이유`, `### 버린 선택지`를 쓴다. 버린 선택지가 뽑은 글에 없으면 "미확인"이라고 적는다. 이유를 지어내지 않는다. 이유가 없으면 이유도 "미확인"이다.
- `## 분석` 절은 두지 않는다.
- 내용이 `맥락 분석:`으로 시작하는 메모는 예전 맥락 분석이 남긴 결과다. 지금은 이런 메모를 새로 남기지 않는다. 남아 있으면 `source: memo`로 만든다. 제목은 "맥락 분석 YYYY-MM-DD", 태그에 `context-analysis`. `### 결정`에 "분석 범위"와 "넣은 곳"을 메모 그대로 옮긴다.

### `context` → 맥락(`X-`)

- `## 요지`에 `### 사실`과 `### 유효 기간`을 쓴다. 유효 기간이 뽑은 글에 없으면 "변할 수 있음". 기한이 날짜로 드러나 있으면 머리말 `valid_until`에도 적는다. 지나면 점검 스크립트가 알린다.
- `## 분석` 절은 두지 않는다.
- `domain`을 `work`·`life`·`taste`·`tools` 중 하나로 정한다. 뜻은 `records.md` 머리말 절이다.
- 맥락에는 오래 맞는 사실만 만든다. 그날의 상태(작업이 어디까지 됐나, 지금 무엇이 켜져 있나)는 맥락으로 만들지 않는다. 그런 메모 줄은 기록 없이 넘어가고 보고에 적는다. 진행 상황은 그 프로젝트 세션이 상황판에 적는다.

### 세 종류에 다 걸리는 것

- **scope**: 기록마다 머리말에 `scope`를 정한다. 모든 프로젝트에 걸리면 `me`, 한 프로젝트에만 걸리면 `project:<카드 이름>`. 뜻은 `records.md` 머리말 절이다.
  - 사례는 어느 프로젝트에서 났는지가 아니라 어디서 다시 날 수 있는지로 정한다. 그 프로젝트의 정책이나 디자인에만 걸리는 지적이면 그 프로젝트다. 다른 프로젝트에서도 같은 종류의 일을 하면 날 실수면 `me`다. 이때 `### 어떤 작업에서`에 일의 종류(화면 만들기, 커밋, 설명하기 같은 것)도 적는다. 자가 발전이 그 종류를 보고 규칙을 둘 곳을 가른다.
  - 결정과 맥락은 메모의 "작업 또는 맥락" 칸이 프로젝트 이름이면 그 프로젝트로 본다.
  - 그 칸이 프로젝트 이름이 아니면 내용으로 정한다. 내용이 한 프로젝트에만 걸리면 그 프로젝트다. 같은 주제의 기존 기록이 있으면 그 기록의 `scope`를 따른다. 정하기 어려우면 `me`다. 판단이 갈렸으면 보고에 적는다.
- **domain**: 사례·결정의 `domain`은 `INDEX.md`의 도메인 목록에 있는 것만 쓴다. 없는 도메인이 필요하면 목록에 먼저 추가하고 그 사실을 보고에 적는다.
- **tags**: 주제 태그를 두세 개 넣는다. 기존 기록에서 쓰는 태그가 있으면 그것을 먼저 쓴다. 구조(스킬, 서브에이전트, 훅, 스크립트, 예약 작업의 단계, 지식 베이스의 폴더와 형식)를 바꾼 결정에는 `structure`를 넣는다. `retracted`와 `notfound`는 위 종류별 규칙대로 넣는다.
- **related**: 메모의 관련 칸에 있는 id를 넣는다. 요약 문서(`wiki/context.md`, 해당 프로젝트 카드)에서 같은 주제를 다룬 기존 기록이 보이면 그 id도 넣는다. 관련 칸이 점검 보고서 파일 이름(`raw/reviews/…html`)이면 그대로 넣는다. 사용자가 그 보고서를 보고 한 말이라는 표시다. 자가 발전이 이 표시로 보고서와 이어 읽는다.
- **대체됨 표시**: 새 기록이 예전 기록을 바꾸면 `records.md` 승인 범위 절의 1단계 몫대로 한다. 전부 바꾸면 새 기록 머리말에 `supersedes: <예전 id>`만 적고, 일부만 바꾸면 `## 요지`에 "예전 기록 <id>의 이 부분을 바꾼다"고 적는다. 예전 기록은 건드리지 않는다. 바꾼다는 판단은 메모의 `바꾸는 것:` 표시나 발췌 전문에 그렇게 볼 말이 있을 때만 한다. 주제가 같다는 것만으로는 `related`에만 넣는다. `supersedes`를 적은 쌍(예전 id → 새 id)은 보고에 적는다.
- **비밀값**: 요지와 제목에 비밀값, 자격 정보, 고객 인프라 식별자를 적지 않는다.
- 새 사례를 규칙별 사례표(`evolve/rule-cases.md`)에 적지 않는다. 요약 문서(`wiki/context.md`, 카드)에도 올리지 않는다. 확정된 뒤에 3단계와 4단계가 한다.

## `source: memo`로 만드는 경우

세션 기록에서 뽑을 수 없을 때만 메모에서 옮긴다. 아래 중 하나다.

- 세션 id가 없고 `find --text`를 `--date` 없이 돌려도 못 찾았다. 사용자 말이 없는 메모라 찾을 글이 없는 경우도 여기다.
- 세션 id는 있는데 그 세션 기록이 없다(종료 코드 2). 다른 기기에서 한 세션이거나 기록이 지워진 경우다.
- 세션 기록은 있는데 메모가 말한 일이 그 안에 없다.

만드는 법은 이렇다.

- 머리말: `source: memo`, `session: -`, `range: -`, `omitted: []`. `status: draft`와 `memo`는 같다.
- `## 있었던 일`: 메모의 있었던 일 문장과 `사용자 말:`을 그대로 옮긴다. 표시(`<!-- extract:start -->`, `<!-- extract:end -->`)는 두지 않는다. 메모에 없는 말을 보태지 않는다. 발췌 파일은 만들지 않는다.
- `## 요지`와 `## 분석`은 위 종류별 규칙과 같다. 메모에 없는 것은 "미확인"이다.
- `verify`는 이런 기록을 대조 없이 통과시키고, `confirm`도 `active`로 바꾼다. 댈 세션 기록이 없어서다. 그래서 기록 확인은 메모 줄과 `## 있었던 일`이 같은지를 본다. 메모의 문장을 고치거나 줄이지 않고 옮긴다.
- 왜 못 찾았는지를 보고에 적는다.

## 모르는 형식이 나왔을 때

`extract`가 종료 코드 3을 내면 그 범위에 스크립트가 모르는 줄이 있다는 뜻이다. 건너뛰고 뽑으면 빠진 것을 모르게 되니 뽑지 않는다. `source: memo`로 바꿔 만들지도 않는다. 스크립트를 고치면 세션 기록에서 뽑을 수 있어서다.

- 기록 파일은 `status: draft`, `source: session`으로 만들고 `session`과 `range`를 채운다. 표시 두 개는 두되 사이는 비운다. `## 요지`에는 "아직 없음"이라고 둔다.
- 보고의 "종료 코드 3" 줄에 기록 id와 스크립트가 낸 종류 이름을 적는다. 3단계가 스크립트를 고치고, 다음 새벽에 이 단계가 다시 뽑는다.

## `draft` 기록을 다시 만드는 경우

`draft`로 남은 기록은 둘 중 하나다. 기록 확인이 돌려보낸 것이거나, 앞선 새벽에 뽑지 못한 것이다.

- 기록 확인의 판정을 받았으면 그대로 고친다. 같은 파일을 같은 id로 고쳐 쓴다. 새 id를 받지 않는다.
  - `범위 불일치`: 판정이 말한 대로 범위를 고쳐 다시 뽑고, `range`와 `## 요지`를 맞춘다. 발췌 파일이나 그 묶음이 없다는 판정이면 같은 범위로 `extract --save`를 다시 돌린다.
  - `요지 불일치`: 판정이 짚은 문장을 발췌 전문에 있는 것만 남게 고친다. 뽑은 글은 건드리지 않는다.
  - `비밀값`: 판정이 짚은 줄을 `--omit`에 넣어 다시 뽑고 `omitted`에 적는다. 덜 뺀 묶음은 스크립트가 발췌 파일에서 지운다. 요지나 제목에 있었으면 그 말을 뺀다.
- 판정 없이 남아 있는 `draft`는 머리말의 `session`과 `range`로 `extract`를 다시 돌려 본다. 뽑히면 표시 사이를 채우고 요지를 쓴다. 또 종료 코드 3이면 그대로 두고 보고에 적는다.
- `스크립트 불일치`로 남은 `draft`는 스크립트가 고쳐진 뒤에 다시 뽑는다. 같은 범위로 `extract --save`를 돌려 표시 사이를 바꾸고 `verify`를 본다. 발췌 파일의 묶음이 달라 코드 5가 나오면 `--replace`를 준다.
- `draft`를 지우지 않는다. 식별자는 한 번 정하면 바꾸지 않는다.

## 보고

두 줄이다.

- **완료**: 메모 n줄 → 사례 n, 결정 n, 맥락 n. 커밋 해시. 그 아래에 다음을 적는다.
  - 만든 기록의 id와 파일 경로(지식 베이스 기준). 사례, 결정, 맥락으로 나눠 적는다. 다시 만든 `draft`는 따로 적는다. 이 목록이 기록 확인으로 넘어간다.
  - `source: memo`로 만든 기록의 id와 이유. 없으면 "없음".
  - 비밀값 때문에 뺀 줄 수.
  - 종료 코드 3(모르는 형식): 뽑지 못한 기록의 id와 스크립트가 낸 종류 이름. 이 기록은 위 목록에 넣지 않는다. 뽑은 글이 없어 기록 확인이 볼 것이 없어서다. 없으면 "종료 코드 3: 없음".
  - 다르게 정할 수도 있었던 판단을 줄마다 하나씩. 메모 한 줄을 어느 종류로 만들었는지가 갈렸던 것, `scope`를 `me`와 프로젝트 중 무엇으로 정했는지와 이유, 기록을 만들지 않고 넘긴 메모 줄과 이유, 풀이가 불명확하다고 적힌 메모를 어떻게 옮겼는지, 범위를 메모가 말한 것보다 넓게 잡은 이유다. 형식은 `<기록 id 또는 메모 시각>: <정한 것>. <이유>`. 뻔한 것은 적지 않고, 없으면 "판단이 갈린 것 없음".
  - `supersedes`를 적었으면 쌍마다 한 줄. 예: "D-20250301-02(격주 보고)가 D-20250101-03(주간 보고)을 대체". 대체됨 표시는 승인 없이 하는 대신 보고로 사용자에게 알린다.
- **확인할 것**: 고치지 못한 문제(충돌, 다시 만들어도 못 고친 `draft`, 점검에서 나온 그 밖의 문제). 없으면 "없음".

## 하지 말 것

- 표시 사이(`<!-- extract:start -->`부터 `<!-- extract:end -->`까지)와 발췌 파일을 손으로 고치지 않는다. 오타도, 줄바꿈도, 긴 글을 줄이는 것도 안 된다. 바꿀 것이 있으면 범위나 `--omit`을 바꿔 다시 뽑는다.
- 세션 기록 파일을 직접 읽어 옮겨 적지 않는다. 스크립트 출력만 쓴다.
- `## 요지`에 발췌 전문에 없는 것을 쓰지 않는다. 메모의 풀이를 요지에 섞지 않는다. 없는 이유·선택지·유효 기간은 "미확인"이나 "변할 수 있음"이다.
- `## 분석`에 원인, 근거, 관련 규칙을 적지 않는다. 3단계의 일이다.
- `status`를 `active`로 바꾸지 않는다. `confirm`을 돌리지 않는다. 확정은 기록 확인을 통과한 뒤 메인 세션이 한다.
- `active`가 된 기록의 `## 있었던 일`과 `## 요지`를 고치지 않는다. 바로잡을 것이 있으면 새 기록을 만든다.
- 예전 기록에 `status: superseded`와 `superseded_by`를 적지 않는다. 새 기록에 `supersedes`만 적는다. 예전 기록의 표시는 4단계 정리가 한다.
- 메모 줄을 고치거나 지우지 않는다. `정리됨:` 줄만 더한다.
- 요약 문서(`wiki/context.md`, 카드), 색인, 규칙별 사례표, 상황판을 고치지 않는다. 회귀 질문도 더하지 않는다.
- 규칙(스킬, 훅, 전역 지침, 응답 양식)과 스크립트를 고치지 않는다. 스크립트가 틀린 것 같으면 보고에 적는다.
- 지식 베이스 체크아웃의 브랜치를 바꾸지 않는다. push하지 않는다.
- 비밀값, 자격 정보, 고객 인프라 식별자를 기록에 남기지 않는다. 세션 기록의 내용을 보고에 옮기지 않는다. 보고에는 id와 개수만 적는다.
