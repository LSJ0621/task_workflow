# 결과 검증

요구사항을 실제로 만족하는지 확인하고, 사용자가 결과와 핵심 동작을 설명할 수 있게 돕는다.
분석·협업 스킬, 특정 테스트 도구, 이전 계획 파일 없이도 주어진 자료와 실제 결과에서 시작한다.

## 검증 기준과 범위

- 사용자가 지정한 요구·설계·계획과 현재 산출물을 확인한다. 이미 명확한 조건은 반복 질문하지 않는다.
- 프로젝트 기록이 있으면 [공통 읽기 규칙](../maintain-work-notes/references/reading.md)에 따라 관련 요구사항·설계·계획의 현재 내용을 확인한다. 기록·참조가 없으면 제공된 자료로 독립 수행하고, 특정 버전을 지정했으면 그 요청을 따른다. 기준을 확인할 수 없는 항목은 이전 대화의 기억이나 테스트 통과만으로 충족 처리하지 않고 미확인으로 보고한다.
- 기준이 충돌하면 근거를 드러내고, 판단할 수 없는 부분은 미확인으로 남긴다. 구현 내용에 맞춰 요구사항을 낮추지 않는다.
- 각 중요한 요구를 관찰 가능한 결과와 연결하고, 필수 조건·핵심 로직·통합 경로·실패 가능성이 큰 예외부터 검사한다.
- 코드 외 산출물도 요청에 맞는 방법으로 검증한다. README·문서의 주장과 실제 동작·현재 코드가 다른지도 확인한다.
- 자료·대화에서 요구하지 않은 보안 감사나 전면 리팩터링으로 범위를 확대하지 않는다.

## 근거 수집

- 기존 검사 명령과 테스트를 우선 사용하고, 입증하려는 주장에 맞는 최소한의 검증을 실행한다.
- 단순한 코드 재서술 테스트를 추가하지 않는다. 사용자가 구현·수정도 요청한 범위에서 핵심 제약·경계·회귀를 검증할 필요가 있을 때 의미 있는 테스트를 보완한다. 도구의 파일 쓰기 가능 여부를 사용자 수정 요청으로 해석하지 않는다.
- 테스트·빌드 성공을 요구사항 전체 충족으로 확대 해석하지 않는다. UI, 데이터 경로, 실제 로직은 필요한 관찰이나 검사를 별도로 한다.
- 최적화·추천·계산은 데이터가 허용하는 것과 가정을 확인한다. 유효성 검사, 작은 사례의 예상 결과, 기준 방식과의 비교가 적절하면 활용한다. 휴리스틱 결과를 증명 없이 최적해로 부르지 않는다.
- 명령, 대상 버전·변경 상태, 결과와 필요한 로그 위치를 남긴다. 같은 상태에서 이미 확보한 유효한 근거를 이유 없이 반복 생성하지 않는다.
- 에이전트 보고는 출처를 표시하고 변경과 주요 근거를 확인한다. 코드를 바꾼 뒤 오래된 검사 결과를 현재 결과로 취급하지 않는다.
- 실제 검증을 실행하지 못했거나 일부만 확인한 경우 범위를 명확히 밝힌다.

## 보고와 수정

결과는 통과, 실패, 미실행·미확인으로 구분한다.
문제는 영향이 큰 것부터 기대 동작, 실제 동작, 재현 방법, 관련 파일·함수나 자료 위치를 제시한다.
검증만 요청받으면 제품 코드·테스트·설계 파일을 추가하거나 수정하지 않는다. 기존 검사·테스트로 확인하고, 새 테스트가 필요하면 검증 공백과 필요한 보완을 보고한다. 사용자가 구현·수정도 요청한 작업이면 관련 범위만 고치고 영향받는 검증을 다시 수행한다.
허가된 실행의 일상적인 수정과 사용자 결정이 필요한 설계 변경을 구분한다.

## 구현 이해

사용자가 만든 결과를 이해해야 하는 상황이면 핵심 입력부터 결과까지 한 경로를 짧게 설명한다.
실제 컴포넌트·함수·API·데이터 형식을 확인해 연결하고, 계획상의 이름을 실제 구현처럼 제시하지 않는다.
중요한 설계 이유와 보장하지 못하는 조건도 연결한다.
필요하면 핵심 질문 한두 개로 사용자가 직접 설명해볼 기회를 주되, 긴 강의나 필수 퀴즈로 만들지 않는다.
사용자가 AI 없이 답해야 하는 별도 평가 단계에는 개입하지 않고, 허용된 준비·작업 범위에서만 돕는다.

채팅에는 중요한 결과·문제·남은 한계부터 제시하고, 긴 로그와 상세 근거는 필요한 위치로 연결한다.
