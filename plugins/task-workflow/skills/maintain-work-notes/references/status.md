# STATUS 생성·갱신·완료 정리

진행 상황을 여러 작업·세션에 걸쳐 보존할 필요가 있을 때 사용한다. 만드는 조건은 [공통 원칙](../SKILL.md#공통-원칙) 2를 따른다.
기존 기록 위치를 우선하고 없으면 `docs/work-notes/`를 후보로 한다. 프로젝트 기록 루트의 STATUS 하나를 사용하고 INDEX에서 연결한다. 작업·세션마다 파일을 따로 만들면 어느 것이 최신인지 알 수 없기 때문이다. 기존 STATUS는 그 위치에 둔다.

## 내용과 갱신

현재 단계, 완료한 주요 작업, 다음 작업, 진행을 막는 항목과 주제 문서 링크를 짧게 유지한다. 작업 일지, 기획서 내용, 미정 정책의 상세는 주제 문서에 둔다(원칙 3).

```markdown
# 현재 작업 상태

상태: 진행 중
현재 단계: 예약 입력 검증 구현
완료한 주요 작업: 요청 형식 합의
다음 작업: 오류 응답 검증
진행을 막는 항목: 없음
관련 문서: [예약 정책](booking-policy.md)
```

- 중요한 진행 변화나 다른 세션에 영향을 주는 요구사항·정책·결정·검증 기준 변경 시 갱신한다. 상세는 주제 문서에, STATUS에는 짧은 변경 요약과 해당 문서·절의 링크를 둔다. 구현 진척이 없는 문서 변경도 다른 세션에 영향을 주면 알린다.
- 저장 전 최신 상태 확인은 [공통 읽기 규칙](reading.md)의 STATUS 확인 절차를 따른다. 다른 세션의 변경을 보존하고 충돌 시 작성자를 조정한다. 저장 후에는 기록한 내용에 대응하는 해시로 세션의 기억을 갱신한다.
- 변경 번호·계산한 해시·읽음 표시는 문서나 별도 파일에 적지 않는다. 변경 확인은 해시 계산으로 충분하고, 적어 둔 값은 내용과 따로 놀며 낡기 때문이다. 이미 있는 수동 번호는 허가된 기록 수정 때 내용 보존을 확인하며 제거한다.
- STATUS 읽기·변경 확인만 요청받았을 때는 원칙 1을 따른다.

## 완료와 재사용

1. 현재 추적하는 작업 전체에 미완료 작업·필요한 검증·미해결 장애가 없을 때만 완료로 표시한다. 이번 요청이나 한 단계만 끝났거나 대기·중단·실패 상태라면 진행 중으로 둔다.
2. 이후에도 필요한 결정·근거·검증 결과를 주제 문서에 보존하고 링크를 확인한다. 지난 내용을 비우기 전에 원칙 5로 원문 보존을 확인한다. 방법은 [Git 이력 규칙](history.md)의 원문 정리 절에 있다.
3. 보존이 확인되면 완료한 목록·지난 다음 작업 등을 비우고 아래 최소 내용과 파일·INDEX 링크를 유지한다. 다음 작업은 같은 파일을 진행 중으로 갱신한다.

```markdown
# 현재 작업 상태

상태: 완료
현재 진행 중인 작업 없음
```

이 정리에 필요한 커밋은 원칙 7을 따른다.
