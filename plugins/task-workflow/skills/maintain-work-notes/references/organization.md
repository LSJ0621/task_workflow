# 문서 구조와 참조 규칙

이 문서의 규칙은 [공통 원칙](../SKILL.md#공통-원칙)을 전제로 한다.

## 문서 역할과 기록 내용

기존 기록의 위치·현재 상황을 먼저 파악해야 하면 [공통 읽기 규칙](reading.md)을 적용한다. 아래는 허가된 작성·정리에 필요한 규칙이다.

작성할 내용은 다음 기준으로 선별한 뒤 기록 위치를 정한다.

- **맥락성:** 일반 지식이나 현재 자료만으로 신뢰성 있게 복원할 수 없는, 이 프로젝트에서 형성된 정보인가?
- **지속 가치:** 이후 선택의 이유·전제·작업 범위를 이해하거나 결정을 재검토하는 데 필요한가?
- **보존 의도:** 사용자가 남기려는 내용과 상세 수준에 맞는가? 명시한 보존·제외 의사를 우선한다.

이 내용을 생략하면 다음 세션이 무엇을 추정해야 하는지 확인한다. 일반적인 선택이라도 이 프로젝트에서 채택한 이유와 적용 조건에는 기록 가치가 있다. 대화 전체를 옮기기보다 판단을 복원하는 데 필요한 내용을 선별한다.
코드·테스트·설정을 읽으면 알 수 있는 내용(함수가 하는 일, 파일 구조)은 옮겨 적는 대신 저장소 상대경로와 심볼 이름으로 연결한다. 코드가 바뀌면 옮겨 적은 설명만 낡기 때문이다.

| 위치 | 소유하는 내용 |
| --- | --- |
| INDEX | 문서별 상대경로 링크·목적·다루는 범위·읽어야 할 상황만 안내하는 목차 |
| STATUS | 필요한 경우 현재 작업 진행의 짧은 요약과 주제 문서 링크 |
| 주제별 문서 | 요구사항·확정 정책·결정 이유·미정 항목의 상세와 증거 |
| 프롬프트 | 이번 세션의 구체적인 요청·추가 지시 |

- 출처와 상태는 원칙 4에 따라 나눠 적는다.
- 기록은 중요한 결정, 단계 전환, 인계 전, 기록 요청 때 관련 부분만 반영한다. 매번 전체를 다시 쓰면 바뀐 곳이 묻히고 원문이 흔들리기 때문이다.
- 계속 필요한 진행 정보는 프롬프트가 아니라 문서에 둔다. 문서에 옮긴 과거 요청의 실행 여부는 원칙 1을 따른다.
- 원문 보존 요구와 제출 양식을 우선한다. 내용을 줄일 때 수치·인터페이스·제출 조건·결정 상태는 원문 그대로 유지한다.
- 원문 축약·제거와 과거 결정의 보존 경계는 [Git 이력 규칙](history.md)에 따른다. 다른 세션에 영향을 주는 진행 정보의 생성·갱신 판단은 아래 [진행 기록](#진행-기록)을 따른다.

### 결정 기록 형식

중요한 결정은 주제 문서에 다음 형식으로 적는다. 근거가 없는 칸은 미확인으로 적는다(원칙 4).

```markdown
### <결정 이름>
- 결정: 무엇을 골랐나
- 이유: 왜 골랐나 (근거 위치)
- 버린 선택: 무엇을 왜 고르지 않았나 (쓰던 기간이 있으면 함께)
- 전제: 이것이 바뀌면 이 결정을 다시 검토한다
```

결정이 바뀌면 이전 결정을 "버린 선택"으로 옮기고 바뀐 이유를 적는다. 다음 작업자가 버린 선택을 다시 제안하지 않게 하기 위해서다.
"버린 선택"이 길어지면 지금도 다시 제안될 만한 것만 남긴다. 덜어낸 원문은 원칙 5로 보존을 확인한 뒤 Git 출처로 연결한다.

## 파일·폴더 판단

| 작업 | 기준 |
| --- | --- |
| 기존 문서에 추가 | 같은 질문을 다루며 함께 읽어야 의미가 통하는 내용 |
| 별도 파일로 분리 | 독립적인 조회·수정 목적이 있고 다른 내용까지 읽을 필요가 없는 주제 |
| 하위 폴더 생성 | 관련 문서들이 여러 개 생겼고 안정적인 공통 주제로 묶으면 탐색 범위를 줄일 수 있음 |
| 과거 원문 정리 | 현재 문서에는 중요한 결정 요약·이유를 유지하고, 상세 원문은 실제 보존 상태에 따라 Git 출처 또는 기존 보존 문서로 연결 |

나눌지는 줄 수나 파일 수가 아니라 따로 읽을 이유가 있는지로 정한다. 항상 함께 읽어야 의미가 통하면 한 문서로 둔다. INDEX·STATUS·주제 문서는 역할이 달라 이 판단과 관계없이 따로 둔다.
폴더와 INDEX를 새로 만드는 조건은 원칙 2, 정리 범위는 원칙 6을 따른다.
코드·데이터·외부 제출물은 문서 정리의 범위 밖이라 그 자리에 둔다.
과거 원문을 축약하거나 분할·병합해 출처가 모호해질 때는 [이력 읽기·보존·커밋 규칙](history.md)도 확인한다.

## INDEX

루트와 하위 폴더의 INDEX는 문서 안내 목차로만 사용한다. 다음처럼 문서별 상대경로 링크·목적·다루는 내용·읽어야 할 상황을 안내한다. 표 모양은 기존 관례에 맞춰도 된다.

| 문서 | 목적 | 다루는 내용 | 언제 읽는가 |
| --- | --- | --- | --- |
| 상대경로 링크 | 문서가 필요한 이유 | 주제·범위의 안내 | 이 문서가 답할 수 있는 질문 |

INDEX에는 위 표의 네 칸만 쓴다. 서비스 정의, 확정 정책, 결정 내용, 현재 단계, 다음 작업, 미해결 쟁점의 상세, 새 세션의 작업 순서는 STATUS나 주제 문서에 두고 INDEX는 그 위치만 가리킨다. 짧은 내용이라도 같다. INDEX에 본문을 두면 원본과 따로 고쳐져 어긋나기 때문이다(원칙 3).
INDEX는 현재 문서 위치만 안내한다. 과거 버전은 Git에서 찾는다.
하위 폴더의 문서 목록이 루트 INDEX를 과도하게 늘리면 해당 폴더에 INDEX를 두고 루트에서 연결한다.
모든 문서는 루트 INDEX에서 직접 또는 하위 INDEX를 통해 찾을 수 있게 한다.

## 진행 기록

허가된 기록 작성·정리에서 인계·단계 전환 등으로 현재 상태와 다음 작업을 이후 작업·세션에 보존해야 하면, STATUS가 아직 없어도 [STATUS 관리](status.md)를 읽어 생성·갱신·완료 정리를 수행한다.
진행 정보는 STATUS에만 둔다. 주제 문서나 AGENTS.md에 두면 다음 세션이 진행 상황을 찾지 못하기 때문이다.
STATUS를 만드는 조건은 원칙 2, 읽기·검토 요청에서의 처리는 원칙 1을 따른다.

## 참조 작성

- 문서 간에는 상대경로 Markdown 링크를 사용한다. 링크 문구에는 읽는 이유나 확인할 내용을 적는다. 경로만 있거나 '관련 자료' 같은 문구로는 읽을지 판단할 수 없기 때문이다.
- 특정 부분만 필요하면 제목 앵커를 연결한다. 제목을 바꿀 때 해당 앵커의 참조도 갱신한다.
- 상세 결정·규격의 위치는 원칙 3을 따른다.
- 파일·함수·API 같은 코드 근거는 저장소 상대경로와 심볼 이름으로 적는다. 줄 번호는 코드가 바뀌면 틀어지므로 단독으로 쓰지 않는다.
- 외부 근거에는 원래 URL을 남긴다. 비공개 자료는 새로운 공개 URL이나 외부 서비스에 복제하지 않는다. 한번 나가면 되돌릴 수 없기 때문이다.
- 분할·병합이나 대폭 수정으로 이전 출처를 찾기 어려워지면 관련 현재 문서에 이동 전 실제 커밋 SHA·당시 저장소 상대경로·절 또는 결정 ID를 연결한다. 현재 문서 링크와 과거 Git 출처를 구분한다.

## 구조 변경 절차

1. 공통 읽기 규칙으로 대상 기록을 파악하고 각 정보의 현재 위치와 이동할 문서를 확인한다.
2. INDEX에 섞인 진행 요약은 필요한 STATUS로, 기획·정책·결정 이유·미정 사항의 상세는 해당 주제 문서로 분리한다. 이미 같은 내용이 있으면 대표 위치를 확인해 그곳에 합친다.
3. 지시문 형태로 적힌 기록에서도 기존 합의·미완료 작업·전제를 찾아 옮긴다. 그 지시의 실행 여부는 원칙 1을 따르고, 남겨야 할 원래 맥락은 주제 문서 또는 확인된 Git 출처로 보존한다.
4. 덜어낼 원문의 보존을 원칙 5로 확인한다. 분리할 독립 주제와 대표 문서를 정하고 의미·결정 상태·보존 요구를 유지하며 이동한다.
5. 이동 전후의 필요한 정보·수치·결정 상태·미정 상태를 대조하고 보존 위치 또는 확인된 과거 출처로 찾을 수 있는지 확인한다. INDEX는 목차만 담고, STATUS와 각 주제 문서를 적절하게 연결한다.
6. INDEX와 역참조를 갱신하고 기록 루트에서 이전 경로와 제목 앵커를 검색해 수정한다. 이동한 파일의 로컬 링크·앵커와 기록한 Git 출처가 실제로 조회되는지 확인한다.
7. 커밋이 허가된 작업이면 정리 단위로 확정하되 가능하면 내용 변경과 구조 변경을 분리한다.

결정 내용을 바꾸는 일과 문서 위치를 바꾸는 일은 따로 처리한다. 섞이면 무엇이 바뀌었는지 이력에서 구분할 수 없기 때문이다.
