# 문서와 Git 이력의 읽기·보존·커밋

이 문서의 규칙은 [공통 원칙](../SKILL.md#공통-원칙)을 전제로 한다.

## 문서와 Git의 보존 경계

- 현재 주제 문서에는 요구사항과 설계에 관한 결정·배경·제약·미정 사항과 가정을 보존한다. 기록할 내용의 선별 기준은 [문서 역할과 기록 내용](organization.md#문서-역할과-기록-내용)을 따른다.
- 중요한 과거 결정·선택 이유·폐기한 대안과 이유·결정 변경의 이유와 영향·실제 검증 결과와 한계는 현재 판단에 필요한 요약과 근거를 문서에 남긴다. 과거의 일이라도 다음 판단에 영향을 주면 문서에 둔다. 형식은 [결정 기록 형식](organization.md#결정-기록-형식)을 따른다.
- 과거 문서 전체·대체된 상세 초안·단순 표현 수정·정확한 줄 단위 변경은 필요할 때 Git에서 조회한다. 사용자의 원문 보존 요구와 제출 양식이 우선한다.
- 변경 하나에만 해당하는 이유는 커밋 메시지에 둔다. 다음 판단에 영향을 주는 이유는 문서에 두고, 커밋 메시지에는 한 줄 요약만 쓴다. 에이전트는 문서는 매번 읽지만 커밋 메시지는 찾아볼 때만 읽기 때문이다.

## 과거 원문 조회

현재 상태를 읽는 절차는 [공통 읽기 규칙](reading.md)에 둔다. 여기서는 정확한 과거 내용이나 기록 충돌의 출처를 확인할 때만 조회 범위를 넓힌다.

1. 기록된 실제 커밋과 당시 경로부터 `git show <commit>:<path>`로 조회한다. 경로는 현재 위치가 아닌 해당 커밋 당시의 저장소 상대경로다.
2. 출처가 없으면 관련 파일의 `git log --follow -- <path>`나 결정 ID·고유 검색어를 사용한 `git log -S` 등으로 필요한 범위만 찾는다. `--follow`는 단일 파일의 이름 변경을 추적할 뿐이라 분할·병합까지 복원하지는 못한다.
3. 커밋·경로·절 또는 ID가 실제로 조회되는지 확인하고 원문과 이후 결정 요약을 구분해 답한다. SHA는 조회로 확인한 것만 적는다(원칙 4).
4. 이력이 없거나 현재 clone에서 조회되지 않으면 미확인으로 남기고 현재 원문을 보존한다. 원격 접근·fetch가 필요하면 해당 작업의 권한을 따른다.

## 원문 정리와 출처 보존

원칙 5의 확인 방법과 출처를 남기는 방법이다.

- 결정 ID는 원칙 2의 조건이 생겼을 때 붙인다. 붙인 ID는 이동·분할 후에도 유지한다.
- 원문을 축약·제거하기 전에 `git status`·diff와 과거 파일 내용을 대조해 보존할 원문이 해당 커밋에 실제로 들어 있는지 확인한다. HEAD가 있어도 커밋하지 않은 수정은 그 안에 없다.
- 아직 커밋되지 않은 보존 대상이 있으면 지우기 전에 스냅샷 커밋을 만든다. 커밋할 수 없으면 원문을 그 자리에 그대로 두고 커밋이 필요하다고 알린다.
- STATUS의 완료 내용을 비울 때도 같은 확인을 한다. 필요한 결정·근거는 주제 문서에 남기고 STATUS 파일 자체는 유지한다. 미완료 작업이 남았으면 완료 정리를 미룬다. 변경 확인용 파일 해시는 원문 보존의 증거가 되지 못한다. 보존의 증거는 커밋 SHA다.
- 단순 파일 이동은 기존 링크 갱신으로 충분할 수 있다. 분할·병합·대폭 수정처럼 추적이 모호해지는 경우에는 관련 현재 문서에 **이동 전 커밋 SHA + 당시 경로 + 절 또는 결정 ID**를 남긴다. 가능하면 전체 SHA를 사용한다.
- 참조는 실제로 존재하는 이전 커밋을 가리킨다. 지금 만드는 커밋의 SHA는 커밋한 뒤에야 정해지므로 그 커밋 안의 문서에는 넣을 수 없다.
- INDEX에는 문서 위치·역할을, 관련 주제 본문에는 필요한 과거 출처를 둔다(원칙 3).
- Git이 없는 프로젝트에서는 필요한 원문·변경 배경을 문서에 보존한다. 저장소 초기화는 원칙 7에 따라 범위 밖이다.

## 커밋 시점과 소유권

| 상황 | 기본 판단 |
| --- | --- |
| 읽기·과거 조회만 수행 | 커밋하지 않음 |
| 중요한 결정·설계·검증 기록 완료 | 의미 있는 논의 또는 작업 단위가 정리됐을 때 확정 |
| 원문을 축약하거나 구조를 재편하기 전 | 보존해야 할 미커밋 내용이 있다면 먼저 보존 |
| 파일 이동·분할·병합 완료 | INDEX·역참조·과거 출처를 확인한 뒤 구조 변경 단위로 확정 |
| 내용·결정 변경 | 가능하면 구조 변경과 분리해 이유가 드러나는 단위로 확정 |

커밋 권한과 소유는 원칙 7을 따른다. 한 번 받은 커밋 허가는 같은 작업 안에서 계속 유효하고, 커밋은 위 표의 단위가 정리됐을 때 한다.
다른 작업의 변경을 함께 커밋하지 않는 규칙과 방법은 전역 지침(`~/.claude/CLAUDE.md`) "커밋" 절에 있다. 여기서는 그 절이 말하지 않는 것만 적는다. 다른 변경을 reset·stash하지 말고 작업 소유자와 조정한다. 다른 사람의 작업을 잃을 수 있기 때문이다.
커밋 메시지에는 변경 목적과 구조 이동의 대응 관계를 필요한 만큼 남긴다. 결정 이유를 어디에 둘지는 위 [보존 경계](#문서와-git의-보존-경계)를 따른다.

참고: [git log](https://git-scm.com/docs/git-log), [git show](https://git-scm.com/docs/git-show).
