# 분석 단계: 모으기와 분석

점검 보고의 첫 단계다. 지난 점검 뒤 한 주 동안 규칙이 어떻게 바뀌었는지 모아 보고서 초안을 쓴다.
이 단계를 맡은 서브에이전트는 이 파일과 같은 폴더의 `draft.md`, 사서의 [글쓰기 규칙](../../librarian/references/writing.md)을 읽는다. `verify.md`와 `publish.md`는 읽지 않는다.

받는 것: 보고서 날짜.
내는 것: `/tmp/review-report-<보고서 날짜>/draft.md`.

## 1. 모으기

세 저장소의 위치는 [자가 발전 스킬](../../analyze-context/SKILL.md)의 "세 저장소" 절에 있다. 초안에서는 차례로 `claude`, `plugin`, `kb`라고 부른다.

1. **임시 폴더를 만든다.** `/tmp/review-report-<보고서 날짜>/`. 이미 있으면 안의 파일을 지우고 시작한다. 지난 시도의 초안이 섞이지 않게 하기 위해서다.
2. **지난 점검 태그를 찾는다.** 저장소마다 한다.
   ```bash
   git -C <저장소> tag --list 'review-2*' --sort=-refname | head -1
   ```
   아무것도 안 나오면 `review-baseline`을 쓴다. `review-baseline`도 없으면 시작점을 지어내지 않는다. 멈추고 어느 저장소에 태그가 없는지 보고한다.
3. **끝 커밋을 적어 둔다.** 저장소마다 `git -C <저장소> rev-parse --short main`. 이 뒤에 들어온 커밋은 다음 점검이 본다.
4. **그 사이의 커밋을 읽는다.**
   ```bash
   git -C <저장소> log --reverse --format='%h %ad %s' --date=short <태그>..<끝 커밋>
   git -C <저장소> show <해시>      # 메시지 전체와 바뀐 내용
   ```
   규칙을 바꾼 커밋을 가려낸다. 전역 설정 저장소에서는 `CLAUDE.md`, `output-styles/`, `hooks/`를 바꾼 커밋이다. 플러그인 저장소에서는 `plugins/` 아래 스킬·훅·서브에이전트를 바꾼 커밋이다. 상태 파일만 바꾼 커밋과 버전만 올린 커밋은 규칙 변경이 아니다.
5. **커밋 안 된 변경을 본다.** 저장소마다 `git status --short`와 `git diff`. 규칙 파일에 커밋 안 된 변경이 있으면 "기록 없이 바뀐 것"이다.
6. **그 기간의 기록을 읽는다.** 지난 태그 뒤에 지식 베이스에 더해진 사례·결정·맥락이다.
   ```bash
   git -C <지식 베이스> diff --name-only --diff-filter=A <태그>..<끝 커밋> -- raw/cases raw/decisions raw/context
   ```
   그 사례들의 규칙별 사례표(`wiki/rule-cases.md`) 줄도 읽는다.
7. **상태 파일을 읽는다.** 전역 설정 저장소의 `evolve/state.md`다. 형식은 자가 발전 스킬의 "상태 파일" 절에 있다. "사용자에게 올릴 것", "보류한 후보", "판정 못 한 것", "커밋 안 된 변경"을 본다.

## 2. 분석

초안을 `draft.md`의 형식으로 쓴다. 절마다 아래 내용을 담는다.

- **요약**
  - 규칙 추가, 수정, 삭제가 각각 몇 건인지. 규칙을 바꾼 커밋 하나가 한 건이다. 바뀐 내용을 읽고 가른다. 새 규칙 문장이 생겼으면 추가, 있던 문장이 바뀌었으면 수정, 문장이 없어졌거나 반대로 바뀌었으면 삭제다.
  - 전역 지침과 응답 양식의 줄 수가 태그 때 몇 줄에서 끝 커밋 때 몇 줄이 됐는지.
    ```bash
    git -C <전역 설정> show <태그>:CLAUDE.md | wc -l
    git -C <전역 설정> show <끝 커밋>:CLAUDE.md | wc -l
    ```
- **사용자가 정할 것**
  - 보안 규칙·점검 장치의 변경 제안. 이유와 변경안을 같이 쓴다. 상태 파일 "사용자에게 올릴 것"에서 온다.
  - 규칙을 둔 이유를 못 찾아 바꾸지 않은 것. 같은 절에서 온다.
- **사용자가 볼 것**
  - 지우거나 뒤집은 규칙.
  - 사용자가 정한 문장을 바꾼 것과 그 이유. 커밋 메시지에 "사용자가 정한 문장을 바꿈"이 있거나, 바뀐 줄을 그 전에 마지막으로 바꾼 커밋에 "사용자가 정함"이 있는 경우다.
  - 규칙을 넣은 뒤에도 또 어긴 것. 이 기간의 사례 중 사례표에서 `규칙을 뒷받침`이고, 사례가 난 날이 그 규칙이 생긴 날보다 뒤인 것이다. 규칙이 생긴 날을 구하는 방법은 자가 발전 스킬 순서 4단계에 있다.
  - 기록 없이 바뀐 것. 규칙 파일의 커밋 안 된 변경, 그리고 규칙을 바꾼 커밋인데 메시지에 왜 바꿨는지·근거 id·누가 정했는지 중 빠진 것이 있는 커밋이다.
- **변경 흐름**: 규칙을 바꾼 커밋마다 한 줄. 무슨 일이 있었나(근거가 된 사례 한 줄) → 무엇을 바꿨나(규칙 한 줄) → 어디에 넣었나(파일과 절). 만들기 단계가 이 줄로 도식을 그린다.
- **규칙 이력**: 이 기간에 바뀐 규칙마다 한 줄. 그 규칙이 언제 생기고 언제 고쳐졌는지를 처음부터 적는다. 날짜와 누가 정했는지는 그 줄을 바꿔 온 커밋에서 얻는다.
  ```bash
  git -C <저장소> log --format='%h %ad %s' --date=short -S'<규칙 문장의 핵심 구절>' -- <파일>
  ```
- **구조 점검**: 지식 베이스의 구조 변경 머지 커밋마다 무엇을 어디로 왜 옮겼는지 한 줄. 그런 커밋이 없으면 "이번 기간에 구조 변경 없음".
- **보류한 후보**: 상태 파일 "보류한 후보"의 항목마다 한 줄. "판정 못 한 것"에 항목이 있으면 여기에 같이 적는다.

쓰는 방법:

- 줄마다 근거를 단다. 근거를 열어 보면 그 줄이 맞는지 가릴 수 있어야 한다. 근거 없이 짐작한 줄은 쓰지 않는다.
- 사용자 말은 사례 원문 그대로 옮긴다. 다듬지 않는다.
- 커밋 메시지가 한 말과 실제 바뀐 내용이 다르면 실제 바뀐 내용을 쓴다. 다르다는 것은 "사용자가 볼 것"에 적는다.
- 글은 사서의 글쓰기 규칙을 따른다. 사용자가 훑어보는 문서라 한 줄을 짧게 쓴다.
- 비밀값, 자격 정보, 고객 인프라 식별자는 적지 않는다.

## 보고

두 줄.
- **완료**: 초안 경로, 줄 수, 기간(지난 태그와 저장소별 끝 커밋), "사용자가 정할 것" n줄과 "사용자가 볼 것" n줄.
- **확인할 것**: 태그가 없던 저장소, 읽지 못한 커밋이나 기록. 없으면 "없음".

## 하지 말 것

- 저장소의 파일을 고치거나 커밋하지 않는다. 이 단계는 읽기만 하고 임시 폴더에만 쓴다.
- 규칙을 고치거나 고치자고 제안하지 않는다. 있었던 일만 쓴다.
- HTML을 만들거나 태그를 달지 않는다. 뒤 단계의 일이다.
- 다른 서브에이전트를 부르지 않는다.
