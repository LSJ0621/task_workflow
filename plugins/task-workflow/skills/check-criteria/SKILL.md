# 기준 검수

작업 산출물이 지식 베이스의 기준 문서를 만족하는지 확인하고, 그 결과를 작업자에게 그대로 넘길 수 있는 형태로 부른 세션에 돌려준다. 작업자가 어떻게 만들었는지는 보지 않는다. 결과물만 본다. 그래야 작업자의 설명에 끌려가지 않는다.
그래서 가능하면 작업한 컨텍스트와 분리된 서브에이전트에서 이 스킬을 쓴다. 서브에이전트를 쓸 수 없으면 그 제약을 결과에 적고 같은 세션에서 한다.

## 지식 베이스 찾기

1. `$KNOWLEDGE_BASE_DIR`이 있으면 그곳.
2. 없으면 현재 폴더가 지식 베이스인지 본다. `INDEX.md`와 `raw/journal/`이 있는 git 저장소면 맞다.
3. 부른 세션이 지식 베이스 경로를 직접 넘겼으면 그곳.
4. 다 아니거나 `wiki/criteria/common.md`가 없으면 검수하지 않는다. "검수 불가: 지식 베이스 기준 문서 없음"과 함께 `setup-knowledge-base` 스킬을 안내한다.

## 받는 것

부르는 쪽이 넘겨야 하는 것:
- 작업 설명 한 줄과 완료 기준
- 산출물 위치 (경로, 브랜치, 커밋 해시)
- 적용할 기준. 기본은 지식 베이스의 `wiki/criteria/common.md`, 있으면 도메인 기준 `wiki/criteria/<domain>.md`
- 몇 번째 검수인지. 2회차 이상이면 이전 검수 결과(이 스킬이 돌려준 내용 그대로)

빠진 게 있으면 추측하지 말고 "검수 불가: <빠진 것>"으로 끝낸다.

## 순서

1. 기준 문서를 읽는다. 항목마다 "점검" 줄이 실제로 확인할 수 있는 것인지 본다.
2. 산출물을 읽는다. 완료 기준에 적힌 것부터.
3. 근거 수집과 검증 방법은 같은 플러그인의 `verify-work` 스킬 절차를 따른다. 기존 검사·테스트를 먼저 쓰고, 주장에 맞는 최소한의 검증만 실행한다. 검증만 하는 자리이므로 산출물·테스트·설계 파일을 고치거나 추가하지 않는다.
4. 기준 항목 하나씩 대조한다. 근거는 실행 결과나 파일 위치처럼 다시 찾을 수 있는 것으로 적는다.
5. 기준에는 없지만 문제인 것은 기준 칸을 "없음"으로 두고 따로 적는다. 취향이 아니라 완료 기준이나 사용자 피해와 연결되는 것만.
6. 판정한다.
   - **통과**: 모든 기준 항목 충족, 기준 없음 항목도 심각도 높음이 없다
   - **수정 필요**: 일부 항목 미충족이지만 구조는 유지된다
   - **재작업**: 완료 기준 자체를 못 맞췄거나 설계를 다시 짜야 한다
7. 수정이면 재지시 대상을 정한다. 기본은 원래 작업자다. 맥락을 이미 알고 있어서 싸다. 다음 중 하나면 새 작업자: 같은 지적이 두 번째로 돌아왔다(이전 검수 결과와 대조), 작업자 컨텍스트가 거의 찼다고 부른 쪽이 알렸다, 재작업 판정이다. 어느 쪽이든 이 결과만 넘기면 고칠 수 있게 쓴다. 상태는 작업자 머릿속이 아니라 결과에 있다.
8. 아래 "결과 형식"대로 부른 세션에 돌려준다. 파일로 저장하지 않는다. 글은 같은 플러그인 `librarian` 스킬의 `references/writing.md`를 따른다.

## 결과 형식

````markdown
# <작업 이름> 검수 (<n>회차)

## 대상
- 작업: 한 줄 설명
- 산출물: 경로, 브랜치, 커밋 해시
- 적용한 기준: `P-...`, `P-...`

## 판정
통과 | 수정 필요 | 재작업

## 발견 항목
| # | 위치 | 뭐가 틀렸나 | 기대 | 근거 | 기준 | 심각도 |
| :- | :- | :- | :- | :- | :- | :- |
| 1 | 파일:줄 | | | 실행한 명령·결과 | `P-...` 또는 없음(이유) | 높음/중간/낮음 |

## 재지시
- 누구에게: 원래 작업자 | 새 작업자
- 이유: (새 작업자면 어떤 교체 조건에 걸렸나)
- 몇 번째 수정 요청인가:

## 보고에 넣을 것
- **증거**: 실행한 명령과 결과 중 사용자 보고에 들어갈 것
- **확인할 것**: 위험한 변경과 사용자가 정할 것만. 없으면 "없음"
````

발견 항목이 없으면 표 대신 "없음"이라고 쓴다. 통과면 재지시 절은 "없음".

## 발견 항목 쓰는 법

항목마다 위치, 뭐가 틀렸나, 기대, 근거, 기준 id, 심각도. 작업자가 이 표만 보고 고칠 수 있어야 한다. "더 좋게"가 아니라 "무엇이 기준의 어느 항목에 어긋나나"로 쓴다. 기준에 없는 지적은 기준 칸을 "없음"으로 두고 이유를 한 줄 적는다.

## 하지 말 것

- 산출물을 고치지 않는다. 검수하는 쪽이 고치면 누가 뭘 했는지 섞인다.
- 작업자의 과정, 대화, 설명을 읽지 않는다. 결과물과 기준만.
- 기준에 없는 취향을 지적하지 않는다. "기준 없음"은 완료 기준이나 사용자 피해와 이어질 때만.
- 지식 베이스에 검수 결과나 다른 기록을 쓰지 않는다. 결과는 부른 세션에만 돌려준다.
- 비밀값이나 고객 인프라 식별자를 결과에 적지 않는다.
