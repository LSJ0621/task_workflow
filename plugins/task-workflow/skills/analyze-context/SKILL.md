# 자가 발전

지식 베이스에는 규칙을 두지 않는다. 규칙은 전역 지침, 응답 양식, 이 플러그인의 스킬·훅에 있다.
이 스킬은 쌓인 사례를 근거로 그 규칙을 에이전트가 스스로 고치는 절차다. 사용자에게 묻지 않는다. 사용자가 변경을 하나하나 검수하면 스스로 고치는 뜻이 없어져서다.
대신 변경마다 커밋을 남긴다. 사용자는 주 1회 점검 보고(`review-report` 스킬)로 무엇이 바뀌었는지 본다.

## 세 저장소

| 이름 | 위치 | 여기 있는 것 |
| :- | :- | :- |
| 전역 설정 | `~/.claude` (로컬 git 저장소. 원격에 올리지 않는다) | 전역 지침 `CLAUDE.md`, 응답 양식 `output-styles/`, 상태 파일 `evolve/state.md` |
| 플러그인 | `~/Desktop/dev/task-workflow` (고칠 때 쓰는 체크아웃. 설치된 사본이 아니다) | 스킬, 훅, 서브에이전트 |
| 지식 베이스 | 사서와 같은 방법으로 찾는다([사서 SKILL.md](../librarian/SKILL.md) "지식 베이스 찾기" 절) | 사례·결정·맥락 원본과 규칙별 사례표. 규칙은 없다 |

지식 베이스를 못 찾으면 아무것도 하지 않고 `setup-knowledge-base`를 안내한다.
다른 스킬(`review-report`, `daily-upkeep`)도 세 저장소의 위치는 이 절을 본다.

## 순서

1. **세 저장소를 최신으로 맞춘다.**
   - 지식 베이스는 사서 [정리 절차](../librarian/references/shelving.md) 1단계와 같은 방법으로 맞춘다. 플러그인은 main에서 `git pull --ff-only`를 한다. 전역 설정은 원격이 없어 pull하지 않는다.
   - 저장소마다 `git status --short`로 커밋 안 된 변경을 본다. 있으면 건드리지 않는다. 되돌리지도 커밋하지도 않는다. 사용자가 작업 중인 것일 수 있어서다. 저장소와 파일 이름을 상태 파일 "커밋 안 된 변경" 절에 적는다.
   - 고치려는 파일에 커밋 안 된 변경이 있으면 그 변경은 이번 실행에서 넣지 않는다. 상태 파일 "판정 못 한 것"에 "넣지 못함"과 이유를 적는다. 사용자 변경과 한 커밋에 섞이면 누가 무엇을 바꿨는지 가를 수 없어서다.
   - 플러그인 저장소가 main이 아니거나 pull이 안 되면 플러그인에 넣을 변경도 같은 방법으로 미룬다.
2. **상태 파일과 새 사례를 읽는다.**
   - 상태 파일(`~/.claude/evolve/state.md`)을 읽는다. 형식과, 파일이 없을 때 만드는 방법은 아래 "상태 파일" 절이다.
   - `raw/cases/`에서 상태 파일에 적힌 마지막 사례 id 뒤의 사례를 읽는다. 식별자는 날짜와 번호 순이라 id 순서로 자른다.
   - 마지막 결정 id, 맥락 id 뒤의 결정(`D-`)과 맥락(`X-`)도 읽는다. 사례처럼 분류하지는 않는다. 사용자 선호가 맥락으로 있는지, 규칙을 둔 이유가 결정으로 있는지 보는 용도다.
   - 사례나 결정의 `related`에 점검 보고서 파일 이름(`raw/reviews/…html`)이 있으면 사용자가 그 보고서를 보고 한 말이다. 보고서의 해당 부분을 같이 읽는다. 상태 파일 "사용자에게 올릴 것"의 항목에 대한 답이면 답대로 하고 그 항목을 지운다.
   - 상태 파일의 "보류한 후보"와 "판정 못 한 것"도 다시 본다. 새 사례와 합쳐 판단하기 위해서다.
   - 정리되지 않은 메모(`raw/journal/`)는 아직 사례가 아니다. 읽지 않는다.
3. **사례를 분류한다.** 새 사례마다 지식 베이스 `wiki/rule-cases.md` 끝에 줄을 더한다. 형식은 사서 [기록 규칙](../librarian/references/records.md)의 "규칙별 사례표" 절이다. 파일이 없으면 그 절의 머리글과 표 머리로 만든다.
   - 관련 규칙은 플러그인 저장소의 스킬(각 스킬의 `SKILL.md`와 `references/`), 전역 지침, 응답 양식에서 사례와 같은 일을 다루는 절을 찾는다. 확실하지 않으면 `없음`이다.
   - 줄을 더한 뒤 불변 조건을 전부 점검한다. 사서 정리는 사례표 검사를 건너뛰고 돌리므로, 모든 사례가 표에 있는지는 여기서 확인된다.
     ```bash
     python3 "<이 스킬 폴더>/../librarian/scripts/check_invariants.py" "$KNOWLEDGE_BASE_DIR"
     ```
   - 지식 베이스 main에 사례표만 커밋하고 push한다. 메시지는 "사례 분류 YYYY-MM-DD: n줄". 커밋과 push 방법은 사서 [정리 절차](../librarian/references/shelving.md)의 "커밋·push" 단계와 같다.
4. **효과를 센다.** 이번에 새 줄이 붙은 규칙마다, 그 규칙이 생긴 날 뒤에 난 사례 수를 센다. 규칙을 넣었는데도 같은 실수가 나는지 보기 위해서다.
   - 규칙이 생긴 날은 그 규칙 문장을 마지막으로 바꾼 커밋의 날짜다. 둘 중 하나로 얻는다.
     ```bash
     git -C <저장소> log -1 --format='%h %ad %s' --date=short -S'<규칙 문장의 핵심 구절>' -- <파일>
     git -C <저장소> blame -L <줄>,<줄> --date=short -- <파일>
     ```
     저장소의 첫 커밋이 나오면 저장소보다 먼저 있던 규칙이다. 그 날짜를 생긴 날로 본다.
   - 사례가 난 날은 사례 머리말의 `date`다.
   - 사례표에서 그 규칙을 관련 규칙으로 가진 줄을 센다. `규칙을 뒷받침`은 생긴 날 앞과 뒤로 나눠 세고, `규칙과 반대`는 따로 센다. `기각`은 세지 않는다.
   - 사례가 난 날과 규칙이 생긴 날이 같으면 앞으로 센다. 그 사례 때문에 규칙이 생긴 경우가 많아서다.
5. **판단한다.**
   - 같은 방향 사례가 두 건 이상이고 맞는 규칙이 없으면 규칙을 넣는다. 사용자 선호가 맥락 기록으로 따로 있으면 한 건이어도 넣는다.
   - 규칙이 생긴 뒤에도 같은 실수가 나면 문장을 고친다. 세 번 넘게 나면 문장으로는 안 지켜지는 것이다. 훅이나 점검 스크립트로 올리고, 결과 보고의 "확인할 것"에 적어 사용자에게 바로 알린다.
   - 사례가 한 건뿐이면 보류한다. 한 번의 지적으로 규칙을 만들면 과해지기 쉬워서다. 상태 파일 "보류한 후보"에 적는다.
   - 규칙을 지우거나 뒤집을 때는 그 규칙을 둔 이유를 먼저 읽는다. 그 줄을 마지막으로 바꾼 커밋의 메시지와, 거기 적힌 근거 id의 기록(지식 베이스 `raw/decisions/`, `raw/cases/`)이다. 이유를 못 찾으면 바꾸지 않고 상태 파일 "사용자에게 올릴 것"에 적는다. 이유를 모르고 지우면 같은 실수를 다시 부르기 때문이다.
   - 사용자가 정한 문장(그 줄을 마지막으로 바꾼 커밋에 "사용자가 정함"이 있다)도 문제가 되면 고친다. 이때 커밋 메시지에 "사용자가 정한 문장을 바꿈"과 이유를 쓴다. 점검 보고가 이 말로 찾아서 사용자에게 보여 준다.
   - 보안 규칙과 점검 장치는 아래 "바꾸면 안 되는 것" 절을 따른다.
   - 판단이 안 서는 사례는 억지로 정하지 않는다. 상태 파일 "판정 못 한 것"에 사례 id와 이유를 적는다.
6. **넣는다.** 변경 하나에 커밋 하나다. 메시지에 왜 바꿨는지, 근거 기록 id, 누가 정했는지("자가 발전")를 쓴다. 커밋 메시지 양식은 정해 두지 않는다. 이 세 가지만 들어가면 된다. 점검 보고가 커밋을 읽어 이력을 만들기 때문에 에이전트가 판단한 이력은 이 커밋에만 남긴다.
   - 사용자 개인의 보고·응답 방식은 전역 지침이나 응답 양식에 넣는다. 고친 파일만 전역 설정 저장소에 커밋한다. 원격이 없으니 push하지 않는다.
   - 누구에게나 맞는 일하는 방법은 플러그인의 해당 스킬에 넣는다. 훅, 점검 스크립트, 서브에이전트도 플러그인에 넣는다. 방법은 아래 "플러그인을 고칠 때" 절이다.
   - 이 플러그인은 지금 사용자에게 맞춘 플러그인이라 개인적인 방법도 스킬에 넣어도 된다. 공개 저장소라서 비밀값·자격 정보·고객 인프라 식별자는 어디에도 넣지 않는다.
   - 프로젝트 지침과 프로젝트 문서에는 넣지 않는다. 그 프로젝트에서 일하는 세션이 고친다. 프로젝트 지침으로 풀 일이면 상태 파일 "보류한 후보"에 "프로젝트 지침 몫"이라고 적어 둔다.
   - 규칙은 한 곳에만 쓴다(아래 "규칙 관리 원칙").
   - **옛말 확인.** 넣은 뒤 바뀐 규칙의 새 핵심어와 옛 표현(바뀌기 전 숫자, 용어, 역할 이름) 둘 다로 플러그인 저장소, 전역 지침, 응답 양식을 한 번 grep한다. 걸린 곳이 옛 규칙을 말하면 고치거나, 그 한 곳을 가리키게 바꾼다. 지식 베이스의 지난 기록(`raw/`, `work/`)에 걸린 것은 그대로 둔다.
7. **상태 파일을 고치고 커밋한다.** 어디까지 봤는지, 보류한 후보, 판정 못 한 것, 사용자에게 올릴 것, 커밋 안 된 변경을 이번 실행 결과로 고친다. 전역 설정 저장소에 상태 파일만 커밋한다. 메시지는 "자가 발전 상태 YYYY-MM-DD: 분류 n, 넣음 n, 보류 n".
   넣은 것이 없어도 고친다. 다음 실행이 같은 사례를 다시 보지 않게 하기 위해서다.

## 바꾸면 안 되는 것

보안 규칙과 점검 장치는 자가 발전이 바꾸지 않는다. 무엇이 보안 규칙이고 점검 장치인지는 전역 지침(`~/.claude/CLAUDE.md`) "규칙 바꾸기" 절에 있다. 그 목록은 거기에만 둔다.
에이전트가 자기를 점검하는 장치를 스스로 풀 수 있으면 점검이 뜻이 없어서다.

바꿔야 한다고 판단되면 바꾸지 않고, 상태 파일 "사용자에게 올릴 것"에 이유와 변경안을 적는다. 점검 보고가 이 항목을 "사용자가 정할 것"으로 싣는다. 사용자가 허락하면 그때 넣고 커밋에 "사용자가 정함"이라고 쓴다.

## 사용자가 대화 중에 규칙을 정했을 때

사용자가 "이건 규칙으로 넣어"처럼 규칙을 정하면 그 자리에서 넣는다. 순서의 1~5단계와 7단계는 돌지 않는다.

- 6단계대로 넣는다. 넣을 곳, 변경 하나에 커밋 하나, 플러그인 절차가 같다.
- 6단계의 옛말 확인을 한다.
- 커밋 메시지의 "누가 정했는지"에 "사용자가 정함"이라고 쓴다. 근거 기록 id가 아직 없으면 메모 위치(`raw/journal/YYYY-MM-DD.md`의 시각)를 쓴다. 사용자가 정한 것은 사서 쪽지 모드로 메모도 남긴다(전역 지침 "지식 베이스" 절).
- 보안 규칙이나 점검 장치를 바꾸는 말이면 넣기 전에 무엇이 어떻게 바뀌는지 한 문장으로 확인받는다.
- 상태 파일 "사용자에게 올릴 것"에 있던 항목이면 그 줄을 지우고 상태 파일을 커밋한다.

## 사용자가 "분석하자"고 부를 때

같은 순서로 돈다. 대화 자리라서 5단계의 판단 결과를 넣기 전에 보여 줄 수 있다. 사용자가 고치라고 한 것은 고친 대로 넣고 커밋에 "사용자가 정함"이라고 쓴다.

## 상태 파일

`~/.claude/evolve/state.md`. 자가 발전이 어디까지 봤고 무엇을 남겨 두었는지 적는 파일이다. 실행마다 고쳐 쓰고 전역 설정 저장소에 커밋한다. 지난 내용은 git 이력에 있다.

```markdown
# 자가 발전 상태

자가 발전(`task-workflow:analyze-context`)이 실행마다 고쳐 쓴다.

## 어디까지 봤나
- 마지막 실행: YYYY-MM-DD
- 사례: C-YYYYMMDD-NN
- 결정: D-YYYYMMDD-NN
- 맥락: X-YYYYMMDD-NN

## 보류한 후보
- <앞으로 이렇게 한다, 한 문장> | 사례 C-… | 보류한 날 YYYY-MM-DD | 이유

## 판정 못 한 것
- C-… 또는 넣지 못한 변경 한 문장 | 이유 | 적은 날 YYYY-MM-DD

## 사용자에게 올릴 것
- 적은 날 YYYY-MM-DD | 대상 규칙(파일과 절) | 이유 | 변경안 | 근거 id

## 커밋 안 된 변경
- 본 날 YYYY-MM-DD | 저장소 | 파일
```

- 항목이 없는 절에는 `- 없음` 한 줄을 둔다. 절이 비었는지 다른 스킬이 한눈에 가리기 위해서다.
- **어디까지 봤나**: 종류별로 이번 실행이 읽은 마지막 id다. 다음 실행은 이 뒤부터 읽는다.
- **보류한 후보**: 사례가 한 건뿐이거나 프로젝트 지침 몫이라 넣지 않은 것. 같은 방향 사례가 더 나오면 합쳐서 판단하고, 넣었으면 지운다.
- **판정 못 한 것**: 판단이 안 선 사례와, 커밋 안 된 변경 때문에 넣지 못한 변경. 다음 실행이 다시 본다. 풀리면 지운다.
- **사용자에게 올릴 것**: 보안 규칙·점검 장치의 변경 제안, 이유를 못 찾아 바꾸지 않은 것. 사용자가 답할 때까지 둔다.
- **커밋 안 된 변경**: 이번 실행의 1단계에서 본 것만 적는다. 지난 실행의 줄은 지운다.

**파일이 없을 때(첫 실행).** 위 형식으로 만든다. "어디까지 봤나"는 예전 맥락 분석 기록에서 이어받는다.
- `raw/decisions/`에서 태그에 `context-analysis`가 있거나 제목이 "맥락 분석"으로 시작하는 기록 중 가장 최근 것을 찾는다.
- `raw/journal/`에 내용이 `맥락 분석:`으로 시작하는 decision 줄이 더 최근이면 그 줄을 쓴다.
- 거기 적힌 "분석 범위"의 종류별 마지막 id를 옮겨 적는다. 그런 기록이 없으면 id를 비워 두고 처음부터 전부 읽는다.

## 플러그인을 고칠 때

1. 플러그인 저장소에서 main으로부터 브랜치를 만든다.
2. 변경마다 커밋한다. 한 실행에서 변경이 여러 개면 한 브랜치에 차례로 커밋한다.
3. 세 manifest(`plugin.json`, `.claude-plugin/plugin.json`, `.codex-plugin/plugin.json`)의 버전을 함께 올리는 커밋을 마지막에 하나 더한다.
4. push하고 PR을 만들어 묻지 않고 머지한다. 변경마다 남긴 커밋이 main에 그대로 남도록 머지 커밋으로 들인다(`gh pr merge --merge --delete-branch`). 커밋을 하나로 뭉치면 점검 보고가 변경을 하나씩 가를 수 없다.
5. 체크아웃을 main으로 돌려 `git pull --ff-only`를 한다.
6. 다시 설치한다. Claude Code는 `claude plugin marketplace update task-workflow-marketplace`와 `claude plugin update task-workflow@task-workflow-marketplace`, Codex는 `codex plugin marketplace upgrade task-workflow-marketplace`. 바뀐 스킬은 새 세션부터 보인다.

push나 PR, 머지가 실패하면 브랜치와 커밋을 남긴 채 멈추고 결과 보고의 "확인할 것"에 적는다. 같은 명령을 그대로 되풀이하지 않는다.

## 규칙 관리 원칙

- 규칙은 한 곳에만 쓴다. 다른 곳은 그곳을 가리킨다(파일 경로와 절 이름). 같은 목록(예: 위험한 변경 목록)도 한 곳에만 둔다.
- 규칙이 바뀌면 그 한 곳만 고친다. 가리키는 쪽은 고칠 일이 없어야 한다.
- 지식 베이스의 지난 기록은 고치지 않는다. 새 결정이 예전 결정을 전부 바꾸면 사서가 정리 때 대체됨 표시만 한다.
- grep은 옛말이 다른 곳에 남았는지 마지막에 한 번 확인하는 용도다(6단계). 규칙을 여러 곳에 써 두고 grep으로 맞추는 방식이 아니다.

## 결과 보고

두 줄로 보고한다.
- **완료**: 분류한 사례 n줄. 넣거나 고친 규칙마다 "규칙 한 줄 → 파일 절"과 커밋 해시. 플러그인을 고쳤으면 PR 링크, 머지 여부, 재설치 결과. 보류 n건. 상태 파일 커밋 해시.
- **확인할 것**: 훅이나 점검 스크립트로 올린 것. 상태 파일 "사용자에게 올릴 것"에 새로 적은 항목. 넣지 못한 변경과 이유. 없으면 "없음".

## 하지 말 것

- 예약 실행에서는 사용자에게 묻지 않는다. 정할 수 없는 것은 상태 파일에 적고 넘어간다.
- 보안 규칙과 점검 장치를 바꾸지 않는다.
- 프로젝트 지침과 프로젝트 문서를 고치지 않는다.
- 커밋 안 된 변경을 되돌리거나 함께 커밋하지 않는다.
- 지식 베이스에는 규칙별 사례표의 줄만 쓴다. 지난 기록을 고치지 않고, 규칙 문서를 만들지 않고, 에이전트가 판단한 이력을 기록으로 남기지 않는다. 그 이력은 바꾼 저장소의 커밋에 있다.
- 사례에 없는 사용자 말이나 이유를 지어 넣지 않는다.
- 이력을 다시 쓰지 않는다(amend, rebase, force push).
