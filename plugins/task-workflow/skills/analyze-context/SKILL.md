# 맥락 분석

지식 베이스에는 규칙을 두지 않는다. 규칙은 이렇게 만든다. 맥락이 쌓인다 → 사용자와 따로 분석한다 → 정한 규칙을 스킬이나 전역 지침에 넣는다 → 다시 분석해서 고친다.
이 스킬은 그 분석 시간이다. 사서는 사례를 기록하고 규칙별 사례표에 한 줄씩 적기만 한다. 규칙을 정하는 건 여기서 사용자가 한다.

## 순서

1. **지식 베이스 찾기.** 사서와 같은 방법이다([사서 SKILL.md](../librarian/SKILL.md) "지식 베이스 찾기" 절). 못 찾으면 아무것도 하지 않고 `setup-knowledge-base`를 안내한다.
   먼저 `git -C "$KNOWLEDGE_BASE_DIR" pull --ff-only`로 최신 상태를 맞춘다. 안 되면 그대로 읽고, 최신이 아닐 수 있다고 결과에 적는다.
2. **지난 분석 뒤의 재료 모으기.**
   - 마지막 분석 결정 기록을 찾는다. `raw/decisions/`에서 태그에 `context-analysis`가 있거나 제목이 "맥락 분석"으로 시작하는 기록 중 가장 최근 것이다. 아직 정리되지 않은 메모(`raw/journal/`)에 내용이 `맥락 분석:`으로 시작하는 decision 줄이 더 최근이면 그 줄을 쓴다.
   - 그 기록의 "분석 범위"에 적힌 종류별 마지막 id 뒤에 생긴 사례(`C-`), 결정(`D-`), 맥락(`X-`)을 모은다. 식별자는 날짜와 번호 순이라 id 순서로 자른다. 분석 기록이 없으면 첫 분석이라 전부 모은다.
   - 규칙별 사례표 `wiki/rule-cases.md`에서 모은 사례의 줄을 가져온다. 표에 없는 사례는 사례 원본을 읽고 관련 규칙을 직접 찾는다. 표 자체는 고치지 않는다(사서 몫이다).
   - 정리되지 않은 메모 줄은 아직 사례가 아니다. 참고만 하고, 분석 범위 id에는 넣지 않는다.
   - 지금 규칙을 읽는다. 표의 "관련 규칙"이 가리키는 스킬 파일의 절과 전역 지침(Claude Code는 `~/.claude/CLAUDE.md`, Codex는 `~/.codex/AGENTS.md`), 응답 양식 파일(`~/.claude/output-styles/`)이다.
3. **규칙별로 묶어 보여 주기.** 세 묶음으로 나눈다.
   - **새 규칙 후보**: 표의 규칙과 관계가 "규칙 없음"인 사례. 맞는 규칙이 없다는 뜻이다. 같은 이야기를 하는 사례끼리 묶는다.
   - **고칠지 버릴지 볼 규칙**: 규칙과 관계가 "규칙과 반대"인 사례가 쌓인 규칙. 규칙대로 했는데 사용자가 고쳤다는 뜻이다.
   - **근거가 쌓인 규칙**: 규칙과 관계가 "규칙을 뒷받침"인 사례가 쌓인 규칙. 사용자가 고친 방향이 그 규칙과 같다는 뜻이다. 같은 규칙을 에이전트가 거듭 어겼으면 그 횟수도 적는다. 규칙이 잘 안 지켜진다는 신호라서다.
   - "기각"인 사례는 근거로 세지 않는다.

   항목마다 이렇게 쓴다. 사용자 말로, 할 일 수준으로 쉽게 쓴다. 사례 원문을 길게 옮기지 않는다.
   ```
   1. <앞으로 이렇게 한다, 한 문장>
      - 사례: C-..., C-... (n건). 사용자 말 한마디: "..."
      - 넣을 곳 후보: <파일과 절>
      - 지금 규칙: <있으면 한 줄, 없으면 "없음">
   ```
   사례가 한 건뿐인 후보는 "한 건뿐"이라고 표시한다. 한 번의 지적으로 규칙을 만들면 과해지기 쉬워서다.
   마지막에 항목 번호마다 넣기·고치기·버리기·보류 중 무엇을 할지 묻는다.
4. **사용자가 정한 것만 넣기.** 답을 받은 항목만 넣는다. 보류한 항목은 넣지 않고 다음 분석으로 넘긴다.
   - 누구에게나 맞는 일하는 방법은 `task-workflow` 플러그인의 해당 스킬에 넣는다.
   - 사용자 개인의 보고·응답 방식은 전역 지침이나 응답 양식 파일에 넣는다.
   - 이 플러그인은 지금 사용자에게 맞춘 플러그인이라 개인적인 방법도 스킬에 넣어도 된다. 공개 저장소라서 비밀값·자격 정보·고객 인프라 식별자는 어디에도 넣지 않는다.
   - 넣는 방법은 아래 "규칙 관리 원칙"을 따른다.
5. **옛말 확인.** 넣기를 마치면 바뀐 규칙의 새 핵심어와 옛 표현(바뀌기 전 숫자, 용어, 역할 이름) 둘 다로 플러그인 저장소와 전역 지침, 응답 양식을 한 번 grep한다. 걸린 곳이 옛 규칙을 말하면 고치거나, 그 한 곳을 가리키게 바꾼다. 지식 베이스의 지난 기록(`raw/`, `work/`)에 걸린 것은 그대로 둔다.
6. **기록과 반영.**
   - 사서(`librarian`) 쪽지 모드로 decision 메모를 남긴다. 다음 분석이 이 메모(정리되면 결정 기록)에서 이어받는다. 내용은 `맥락 분석:`으로 시작하고 두 가지를 꼭 넣는다.
     ```
     HH:MM | decision | 맥락 분석 | 맥락 분석: 분석 범위 C-<마지막 사례 id>, D-<마지막 결정 id>, X-<마지막 맥락 id>까지. 넣은 곳 <규칙 한 줄> → <파일 절>; ... 버림·보류 <항목>. 사용자: "<정한 말>" | <넣은 규칙의 근거 사례 id들>
     ```
     넣은 것이 없어도 분석 범위는 남긴다. 다음 분석이 같은 사례를 다시 보지 않게 하기 위해서다.
     이 메모가 결정 기록이 되면 사서가 다음 정리 때 `wiki/context.md`나 프로젝트 카드의 결정 요약에도 반영한다. 여기서 요약 문서를 직접 고치지 않는다.
   - 스킬을 고쳤으면 플러그인 저장소에서 브랜치를 만들어 고치고, 세 manifest(`plugin.json`, `.claude-plugin/plugin.json`, `.codex-plugin/plugin.json`)의 버전을 함께 올린다. 커밋, push, PR을 만들고 묻지 않고 머지한다(`gh pr merge`). 사용자가 분석 자리에서 정한 내용이라 머지가 따로 승인받을 일이 아니라서다.
   - 머지한 뒤 다시 설치한다. Claude Code는 `claude plugin marketplace update task-workflow-marketplace`와 `claude plugin update task-workflow@task-workflow-marketplace`, Codex는 `codex plugin marketplace upgrade task-workflow-marketplace`. 새 세션부터 바뀐 스킬이 보인다고 알린다.
   - 전역 지침이나 응답 양식을 고쳤으면 그 파일만 고친다. 그 파일이 git 저장소 안에 있으면(Claude Code는 `~/.claude`) 고친 파일만 그 저장소에 커밋한다. 메시지에 어떤 규칙을 왜 바꿨는지 쓴다. 규칙이 언제 바뀌었는지 남아야 다음 분석에서 사례가 규칙이 생기기 전 일인지 뒤 일인지 가릴 수 있어서다. 원격이 없는 저장소면 push는 하지 않는다.

## 규칙 관리 원칙

- 규칙은 한 곳에만 쓴다. 다른 곳은 그곳을 가리킨다(파일 경로와 절 이름). 같은 목록(예: 위험한 변경 목록)도 한 곳에만 둔다.
- 규칙이 바뀌면 그 한 곳만 고친다. 가리키는 쪽은 고칠 일이 없어야 한다.
- 지식 베이스의 지난 기록은 고치지 않는다. 새 결정이 예전 결정을 전부 바꾸면 사서가 정리 때 대체됨 표시만 한다.
- grep은 옛말이 다른 곳에 남았는지 마지막에 한 번 확인하는 용도다(순서 5). 규칙을 여러 곳에 써 두고 grep으로 맞추는 방식이 아니다.

## 결과 보고

분석 자리는 대화라서 3단계의 묶음 목록이 곧 본문이다. 넣기까지 끝나면 두 줄로 보고한다.
- **완료**: 넣은 규칙마다 "규칙 한 줄 → 파일 절", PR 링크와 머지 여부, 재설치 결과, 남긴 메모 위치
- **확인할 것**: 전역 지침·응답 양식처럼 플러그인 저장소 밖 파일을 고쳤으면 그 파일과 커밋 해시. 없으면 "없음"

## 하지 말 것

- 사용자가 정하지 않은 규칙을 넣지 않는다. 보여 주는 것과 넣는 것은 다른 단계다.
- 지식 베이스의 지난 기록과 규칙별 사례표를 고치지 않는다. 지식 베이스에 쓰는 일은 사서가 한다.
- 지식 베이스에 규칙 문서를 만들지 않는다.
- 사례에 없는 사용자 말이나 이유를 지어 넣지 않는다.
