# 자가 발전

지식 베이스에는 규칙을 두지 않는다. 규칙은 전역 지침, 응답 양식, 이 플러그인의 스킬·훅에 있다.
이 스킬은 쌓인 사례를 근거로 그 규칙을 에이전트가 스스로 고치는 절차다. 사용자에게 묻지 않는다. 사용자가 변경을 하나하나 검수하면 스스로 고치는 뜻이 없어져서다.

고치는 방식은 추정을 세우고 확인해 가는 것이다. 실수를 뒤집은 문장을 넣지 않는다. 실수가 난 원인을 추정하고, 그 원인을 막는 방법을 얻는 것과 잃는 것을 따져 스스로 고르고, 추정이 맞았는지 뒤에 들어오는 사례로 확인한다. 틀렸으면 지난 사례를 다시 읽고 다른 방법을 찾는다.
대신 변경마다 커밋과 추정 기록을 남긴다. 사용자는 평일 아침에 달라고 할 때 아침 보고서로 에이전트가 어떻게 판단했는지를 보고, 주 1회 점검 보고(`review-report` 스킬)로 한 주를 확인한다. 사용자가 보는 것은 문장이 아니라 판단의 방향이다.

## 세 저장소

| 이름 | 위치 | 여기 있는 것 |
| :- | :- | :- |
| 전역 설정 | `~/.claude` (로컬 git 저장소. 원격에 올리지 않는다) | 전역 지침 `CLAUDE.md`, 응답 양식 `output-styles/`, 상태 파일 `evolve/state.md` |
| 플러그인 | `~/Desktop/dev/task-workflow` (고칠 때 쓰는 체크아웃. 설치된 사본이 아니다) | 스킬, 플러그인 훅(`plugins/task-workflow/hooks/hooks.json`), 서브에이전트 |
| 지식 베이스 | 사서와 같은 방법으로 찾는다([사서 SKILL.md](../librarian/SKILL.md) "지식 베이스 찾기" 절) | 사례·결정·맥락 원본과 규칙별 사례표. 규칙은 없다 |

지식 베이스를 못 찾으면 아무것도 하지 않고 `setup-knowledge-base`를 안내한다.
점검 보고(`review-report`)의 분석 단계도 세 저장소의 위치는 이 절을 본다.

## 순서

1. **세 저장소를 최신으로 맞춘다.**
   - 지식 베이스는 사서 [정리 절차](../librarian/references/shelving.md) 1단계와 같은 방법으로 맞춘다. 플러그인은 main에서 `git pull --ff-only`를 한다. 전역 설정은 원격이 없어 pull하지 않는다.
   - 저장소마다 `git status --short`로 커밋 안 된 변경을 본다. 있으면 건드리지 않는다. 되돌리지도 커밋하지도 않는다. 사용자가 작업 중인 것일 수 있어서다. 저장소와 파일 이름을 상태 파일 "커밋 안 된 변경" 절에 적는다.
   - 고치려는 파일에 커밋 안 된 변경이 있으면 그 변경은 이번 실행에서 넣지 않는다. 상태 파일 "판정 못 한 것"에 "넣지 못함"과 이유를 적는다. 사용자 변경과 한 커밋에 섞이면 누가 무엇을 바꿨는지 가를 수 없어서다.
   - 플러그인 저장소가 main이 아니거나 pull이 안 되면 플러그인에 넣을 변경도 같은 방법으로 미룬다.
2. **상태 파일과 새 사례를 읽는다.**
   - 상태 파일(`~/.claude/evolve/state.md`)을 읽는다. 형식과, 파일이 없을 때 만드는 방법은 아래 "상태 파일" 절이다.
   - `raw/cases/`에서 상태 파일에 적힌 마지막 사례 id 뒤의 사례를 읽는다. 식별자는 날짜와 번호 순이라 id 순서로 자른다.
   - 마지막 결정 id, 맥락 id 뒤의 결정(`D-`)과 맥락(`X-`)도 읽는다. 사례처럼 분류하지는 않는다. 사용자 선호가 맥락으로 있는지, 규칙을 둔 이유가 결정으로 있는지 보는 용도다.
   - 사례나 결정의 `related`에 점검 보고서 파일 이름(`raw/reviews/…html`)이 있으면 사용자가 그 보고서를 보고 한 말이다. 보고서의 해당 부분을 같이 읽는다. 상태 파일 "사용자에게 올릴 것"의 항목에 대한 답이면 답대로 하고 그 항목을 지운다.
   - 상태 파일의 "보류한 후보"와 "판정 못 한 것"도 다시 본다. 새 사례와 합쳐 판단하기 위해서다.
   - 추정 기록(`~/.claude/evolve/hypotheses.md`)에서 상태가 "지켜보는 중"인 추정을 읽는다. 새 사례가 그 추정의 "틀렸다고 볼 신호"에 맞는지 보기 위해서다. 파일이 없으면 7단계에서 만든다.
   - 사용자가 바라는 것을 분석한 맥락 기록을 읽는다. `raw/context/`에서 머리말 `tags`에 `analysis`와 `tacit`가 함께 있고 `status: active`인 가장 새 기록이다. 방법을 고를 때 잣대로 쓴다.
   - 사례의 "사용자가 고친 말"과 "에이전트 풀이"를 나눠 읽는다. 사용자 말이 근거이고, 풀이는 메모를 적은 에이전트의 추정이라 참고만 한다. "에이전트 풀이" 절이 없는 예전 사례는 따옴표 안의 말만 사용자 말로 본다.
   - 정리되지 않은 메모(`raw/journal/`)는 아직 사례가 아니다. 읽지 않는다.
3. **사례를 분류한다.** 새 사례마다 지식 베이스 `wiki/rule-cases.md` 끝에 줄을 더한다. 형식은 사서 [기록 규칙](../librarian/references/records.md)의 "규칙별 사례표" 절이다. 파일이 없으면 그 절의 머리글과 표 머리로 만든다.
   - 더하기 전에 표에 그 사례 id의 줄이 이미 있는지 본다. 있으면 다시 더하지 않고 있는 줄을 그대로 쓴다. 지난 실행이 중간에 멈췄거나 처음 실행이어도 같은 사례가 두 번 붙지 않게 하기 위해서다.
   - 관련 규칙은 플러그인 저장소의 스킬(각 스킬의 `SKILL.md`와 `references/`), 전역 지침, 응답 양식에서 사례와 같은 일을 다루는 절을 찾는다. 확실하지 않으면 `없음`이다.
   - 사용자가 지적을 거둔 사례(머리말 `tags`에 `retracted`, 또는 "사용자가 고친 말"에 자기 착각이나 자기 검수 탓이라고 한 말이 있다)는 `기각`으로 적는다. 근거로도 재발로도 세지 않는다.
   - 줄을 더한 뒤 불변 조건을 전부 점검한다. 사서 정리는 사례표 검사를 건너뛰고 돌리므로, 모든 사례가 표에 있는지는 여기서 확인된다.
     ```bash
     python3 "<이 스킬 폴더>/../librarian/scripts/check_invariants.py" "$KNOWLEDGE_BASE_DIR"
     ```
   - 지식 베이스 main에 사례표만 커밋하고 push한다. 메시지는 "사례 분류 YYYY-MM-DD: n줄". 커밋과 push 방법은 사서 [정리 절차](../librarian/references/shelving.md)의 "커밋·push" 단계와 같다.
4. **효과를 센다.** 이번에 새 줄이 붙은 규칙마다 날짜 둘을 구하고 사례를 센다. 규칙을 넣었는데도 같은 실수가 나는지 보기 위해서다.
   - **생긴 날**은 그 규칙이 처음 들어간 커밋의 날짜다. 문장이 그 뒤에 고쳐졌어도 처음 들어간 날을 쓴다. **마지막으로 고친 날**은 그 문장을 마지막으로 바꾼 커밋의 날짜다. 그 줄을 바꿔 온 커밋을 차례로 보면 둘 다 나온다. 맨 위가 처음, 맨 아래가 마지막이다.
     ```bash
     git -C <저장소> log --reverse -s --format='%h %ad %s' --date=short -L<줄>,<줄>:<파일>
     ```
     문장이 크게 바뀌어 줄 추적이 끊기면 바뀌기 전 문장의 핵심 구절로 다시 찾는다(`git -C <저장소> log --reverse --format='%h %ad %s' --date=short -S'<핵심 구절>' -- <파일>`).
     저장소의 첫 커밋이 나오면 저장소보다 먼저 있던 규칙이다. 그 날짜를 생긴 날로 본다.
   - 사례가 난 날은 사례 머리말의 `date`다. 사례가 난 날과 커밋 날짜가 같으면 그 커밋보다 앞으로 센다. 그 사례 때문에 규칙이 생기거나 고쳐진 경우가 많아서다.
   - **재발 횟수**: 사례표에서 그 규칙을 관련 규칙으로 가진 `규칙을 뒷받침` 줄 중 생긴 날 뒤에 난 사례 수다. 문장을 고쳤다고 다시 0부터 세지 않는다. 처음 생긴 날부터 이어서 센다. 고칠 때마다 새로 세면 고쳐도 안 지켜지는 규칙이 훅으로 올라가지 못해서다.
   - **고친 뒤 재발**: 그중 마지막으로 고친 날 뒤에 난 사례 수다. 고친 문장이 듣는지 볼 때만 쓴다.
   - `규칙과 반대`는 따로 센다. `기각`은 세지 않는다.
5. **판단한다.** 실수를 뒤집은 문장을 넣지 않는다. 원인을 추정하고 그 원인을 막는 방법을 고른다. 방법 전체는 [판단 방법](references/judging.md)에 있다. 이 단계에 들어가기 전에 읽는다. 뼈대는 이렇다.
   - **세운 추정부터 본다.** 새 사례가 "지켜보는 중"인 추정의 틀렸다고 볼 신호에 맞으면 그 추정은 틀린 것이다. 그 추정의 근거 사례와 새 사례를 다시 읽고, 무엇을 잘못 봤는지 정하고, 다른 방법을 찾는다. 꼭 기준을 바꾸는 것이 아니어도 된다.
   - **원인을 가른다.** 넷 중 하나다. 규칙이 있는데 그때 읽히지 않았다. 읽혔는데 문장이 판단할 기준을 주지 못했다. 규칙이 아예 없었다. 규칙의 문제가 아니다.
   - **방법을 고른다.** 있는 문장을 고쳐 쓰거나 읽히는 곳으로 옮겨서 풀 수 있으면 새 문장을 넣지 않는다. 안 되면 방법마다 얻는 것과 잃는 것을 따져 사용자가 바라는 것에 더 가까운 쪽을 고른다. 길어서도 짧아서도 지적받는 것처럼 양쪽으로 틀릴 수 있는 불만은 문장을 더하지 않고 두 방향을 가르는 기준 하나로 고쳐 쓴다.
   - **너무 추상적이지 않게 쓴다.** 기준 한 문장에 실제 사례에서 온 예를 한두 개 붙인다.
   - **지난 사례에 대어 본다.** 같은 원인으로 묶은 지난 사례도 막는지 본다. 근거 사례 하나만 막으면 겉모양을 적은 것이니 다시 쓴다.
   - 사례가 한 건뿐이고 원인을 정하기에 근거가 모자라면 보류한다. 상태 파일 "보류한 후보"에 적는다. 있는 규칙을 고쳐 쓰거나 옮기는 일이면 한 건이어도 한다.
   - 재발 횟수가 세 번을 넘으면 문장으로는 안 지켜지는 것이다. 원인을 다시 본 뒤 훅이나 점검 스크립트로 올리고(아래 "훅이나 점검 스크립트로 올릴 때"), 결과 보고의 "확인할 것"에 적어 사용자에게 바로 알린다.
   - 규칙을 지우거나 뒤집을 때는 그 규칙을 둔 이유를 먼저 읽는다. 그 줄을 마지막으로 바꾼 커밋의 메시지와, 거기 적힌 근거 id의 기록(지식 베이스 `raw/decisions/`, `raw/cases/`), 추정 기록의 그 묶음이다. 이유를 못 찾으면 바꾸지 않고 상태 파일 "사용자에게 올릴 것"에 적는다. 이유를 모르고 지우면 같은 실수를 다시 부르기 때문이다.
   - 사용자가 정한 문장도 문제가 되면 고친다. 이때 커밋 메시지에 "사용자가 정한 문장을 바꿈"과 이유를 쓴다. 점검 보고가 이 말로 찾아서 사용자에게 보여 준다. 사용자가 정한 문장인지는 아래 "사용자가 정한 문장" 절로 가린다.
   - 보안 규칙과 점검 장치는 아래 "바꾸면 안 되는 것" 절을 따른다.
   - 판단이 안 서는 사례는 억지로 정하지 않는다. 상태 파일 "판정 못 한 것"에 사례 id와 이유를 적는다.
6. **넣는다.** 커밋은 전역 지침(`~/.claude/CLAUDE.md`) "규칙 바꾸기" 절의 커밋 규칙대로 남긴다. 누가 정했는지에는 "자가 발전"이라고 쓴다. 메시지 양식은 따로 정해 두지 않는다. 점검 보고가 커밋을 읽어 이력을 만들기 때문에 에이전트가 판단한 이력은 이 커밋에만 남긴다.
   - 어디에 둘지는 [판단 방법](references/judging.md) "규칙을 두는 곳" 절로 가른다. 가르는 선은 그 규칙이 언제 읽혀야 하느냐다. 어떤 일에서든 지킬 것은 전역 지침, 말하는 방식은 응답 양식, 특정 분야나 종류의 일에서 따르는 방법은 플러그인의 해당 스킬이다. 특정 종류의 일에만 걸리는 방법을 전역 지침에 넣지 않는다.
   - 전역 지침과 응답 양식을 고쳤으면 고친 파일만 전역 설정 저장소에 커밋한다. 원격이 없으니 push하지 않는다.
   - 스킬, 훅, 점검 스크립트, 서브에이전트는 플러그인에 넣는다. 방법은 아래 "플러그인을 고칠 때"와 "훅이나 점검 스크립트로 올릴 때" 절이다. 플러그인을 고쳤으면 지식 베이스 상황판의 플러그인 프로젝트 묶음도 고친다(`leave-memo` 스킬 상황판 절).
   - 이 플러그인은 지금 사용자에게 맞춘 플러그인이라 개인적인 방법도 스킬에 넣어도 된다. 공개 저장소라서 비밀값·자격 정보·고객 인프라 식별자는 어디에도 넣지 않는다.
   - 프로젝트 지침과 프로젝트 문서는 전역 지침 "규칙 바꾸기" 절대로 건드리지 않는다. 한 프로젝트에만 걸리는 것은 지식 베이스 상황판의 그 프로젝트 묶음 "지침 후보"에 적는다(`leave-memo` 스킬 "프로젝트 지침 후보" 절). 그 프로젝트에서 일하는 세션이 가져간다. 상황판은 사서 정리와 같은 방법으로 커밋하고 push한다. 메시지는 "상황판: <프로젝트> 지침 후보 n건".
   - 규칙은 한 곳에만 쓴다(아래 "규칙 관리 원칙").
   - **옛말 확인.** 넣은 뒤 바뀐 규칙의 새 핵심어와 옛 표현(바뀌기 전 숫자, 용어, 역할 이름) 둘 다로 플러그인 저장소, 전역 지침, 응답 양식을 한 번 grep한다. 걸린 곳이 옛 규칙을 말하면 고치거나, 그 한 곳을 가리키게 바꾼다. 지식 베이스의 지난 기록(`raw/`, `work/`)에 걸린 것은 그대로 둔다.
7. **추정 기록, 아침 보고서, 상태 파일을 고치고 커밋한다.** 형식은 [추정 기록과 아침 보고서](references/reporting.md)와 아래 "상태 파일" 절이다.
   - 넣거나 고친 변경마다 추정 기록(`~/.claude/evolve/hypotheses.md`)에 묶음 하나를 더한다. 원인 추정, 고른 이유, 다른 방법, 틀렸다고 볼 신호, 지난 사례에 대어 본 결과다. 틀린 것으로 드러난 추정은 상태 줄을 고친다.
   - 아침 보고서(`~/.claude/evolve/reports/YYYY-MM-DD.md`)를 쓴다. 고친 것이 없어도 쓴다.
   - 상태 파일에 어디까지 봤는지, 보류한 후보, 판정 못 한 것, 사용자에게 올릴 것, 커밋 안 된 변경을 이번 실행 결과로 고친다.
   - 전역 설정 저장소에 이 세 파일만 커밋한다. 메시지는 "자가 발전 상태 YYYY-MM-DD: 분류 n, 넣음 n, 보류 n".
   - 넣은 것이 없어도 고친다. 다음 실행이 같은 사례를 다시 보지 않게 하기 위해서다.
   - 고쳤는데 파일이 달라지지 않았으면 커밋하지 않는다. 그것도 완료다.
   - 앞 단계가 중간에 멈춰도 이 단계는 한다. 그때까지 한 일을 적고 끝낸다. "어디까지 봤나"의 id는 5단계 판단까지 마친 기록까지만 올린다. 분류만 하고 판단하지 못한 사례는 다음 실행이 다시 읽는다. 표에는 이미 줄이 있으므로 3단계가 다시 더하지 않는다. 판단은 했는데 넣지 못한 변경은 "판정 못 한 것"에 적는다.

## 바꾸면 안 되는 것

보안 규칙과 점검 장치는 자가 발전이 바꾸지 않는다. 어느 파일과 절이 여기에 드는지는 전역 지침(`~/.claude/CLAUDE.md`) "규칙 바꾸기" 절의 목록에 있다. 목록은 거기에만 둔다. 실행마다 그 절을 읽고 시작한다.
에이전트가 자기를 점검하는 장치를 스스로 풀 수 있으면 점검이 뜻이 없어서다.

- 그 목록에 있는 파일과 절은 문장 하나도 고치지 않는다. 오타나 옛말을 고치는 것도 하지 않는다.
- 바꿔야 한다고 판단되면 상태 파일 "사용자에게 올릴 것"에 이유와 변경안을 적는다. 점검 보고가 이 항목을 "사용자가 정할 것"으로 싣는다.
- 사용자가 허락하면 그때 넣고 커밋에 "사용자가 정함"이라고 쓴다.

## 사용자가 정한 문장

- `review-baseline` 태그 때 이미 있던 규칙 문장은 모두 사용자가 정한 것으로 본다. 자가 발전이 돌기 전에 사용자와 정한 것이라서다. `git -C <저장소> show review-baseline:<파일>`에 그 문장이 있으면 여기에 든다.
- 그 뒤에 생기거나 바뀐 문장은 그 줄을 마지막으로 바꾼 커밋의 메시지로 가린다. "사용자가 정함"이 있으면 사용자가 정한 문장이다.

점검 보고도 이 절로 가린다.

## 사용자가 대화 중에 규칙을 정했을 때

사용자가 "이건 규칙으로 넣어"처럼 규칙을 정하면 그 자리에서 넣는다. 순서의 1~5단계와 7단계는 돌지 않는다.

- 6단계대로 넣는다. 넣을 곳, 커밋 규칙, 플러그인 절차가 같다.
- 6단계의 옛말 확인을 한다.
- 추정 기록에도 묶음을 더한다(`references/reporting.md`). "이 방법을 고른 이유"에 "사용자가 정함"과 사용자 말을 적는다. 그날 아침 보고서가 이미 있으면 그 끝에 이어 쓰고, 없으면 새로 쓴다.
- 커밋 메시지의 "누가 정했는지"에 "사용자가 정함"이라고 쓴다. 근거 기록 id가 아직 없으면 메모 위치(`raw/journal/YYYY-MM-DD.md`의 시각)를 쓴다. 사용자가 정한 것은 `leave-memo` 스킬로 메모도 남긴다(전역 지침 "지식 베이스" 절).
- 보안 규칙이나 점검 장치를 바꾸는 말이면 넣기 전에 무엇이 어떻게 바뀌는지 한 문장으로 확인받는다.
- 상태 파일 "사용자에게 올릴 것"에 있던 항목이면 그 줄을 지우고 상태 파일을 커밋한다.

## 사용자가 "분석하자"고 부를 때

같은 순서로 돈다. 대화 자리라서 5단계의 판단 결과를 넣기 전에 보여 줄 수 있다. 사용자가 고치라고 한 것은 고친 대로 넣고 커밋에 "사용자가 정함"이라고 쓴다.

## 사용자가 아침 보고서를 달라고 할 때

"아침 보고서 줘", "어제 뭐 고쳤어", "자가 발전 뭐 했어" 같은 말이다. 순서의 단계는 돌지 않는다.

1. `~/.claude/evolve/reports/`에서 가장 새 보고서를 읽는다. 사용자가 지난번에 본 뒤로 보고서가 여럿 쌓였으면 본 적 없는 것을 날짜순으로 모두 읽는다. 어디까지 봤는지 모르면 가장 새 것만 보여 주고 그 앞 날짜가 더 있다고 한 줄로 알린다.
2. 보고서 내용을 대화 안에서 보여 준다. 파일을 열라고 하지 않는다. 보고서에 없는 판단을 덧붙이지 않는다. "확인 결과"에 불일치나 해석이 갈림이 있으면 맨 앞에 먼저 보여 준다.
3. 사용자가 방향을 바로잡는 말을 하면 `leave-memo` 스킬로 메모한다. 관련 칸에 추정 번호(`H-…`)를 적는다. 다음 자가 발전이 그 메모에서 나온 사례를 보고 그 추정을 다시 본다.
4. 사용자가 그 자리에서 고치라고 하면 "사용자가 대화 중에 규칙을 정했을 때" 절대로 넣는다.

보고서가 없으면 자가 발전이 아직 돌지 않은 것이다. 상태 파일의 마지막 실행 날짜와 함께 그렇게 알린다.

## 상태 파일

`~/.claude/evolve/state.md`. 자가 발전이 어디까지 봤고 무엇을 남겨 두었는지 적는 파일이다. 실행마다 고쳐 쓰고 전역 설정 저장소에 커밋한다. 지난 내용은 git 이력에 있다.

```markdown
# 자가 발전 상태

자가 발전(`task-workflow:analyze-context`)이 실행마다 고쳐 쓴다.

## 어디까지 봤나
- 마지막 실행: YYYY-MM-DD
- 사례: C-YYYYMMDD-NN
- 결정: D-YYYYMMDD-NN
- 맥락: X-YYYYMMDD-NN

## 보류한 후보
- <앞으로 이렇게 한다, 한 문장> | 사례 C-… | 보류한 날 YYYY-MM-DD | 이유

## 판정 못 한 것
- C-… 또는 넣지 못한 변경 한 문장 | 이유 | 적은 날 YYYY-MM-DD

## 사용자에게 올릴 것
- 적은 날 YYYY-MM-DD | 대상 규칙(파일과 절) | 이유 | 변경안 | 근거 id

## 커밋 안 된 변경
- 본 날 YYYY-MM-DD | 저장소 | 파일
```

- 항목이 없는 절에는 `- 없음` 한 줄을 둔다. 절이 비었는지 다른 스킬이 한눈에 가리기 위해서다.
- **어디까지 봤나**: 종류별로 이번 실행이 읽은 마지막 id다. 다음 실행은 이 뒤부터 읽는다.
- **보류한 후보**: 사례가 한 건뿐이거나 프로젝트 지침 몫이라 넣지 않은 것. 같은 방향 사례가 더 나오면 합쳐서 판단하고, 넣었으면 지운다.
- **판정 못 한 것**: 판단이 안 선 사례와, 넣지 못한 변경(고칠 파일에 커밋 안 된 변경이 있었다, 플러그인 머지가 실패했다). 다음 실행이 다시 본다. 풀리면 지운다.
- **사용자에게 올릴 것**: 보안 규칙·점검 장치의 변경 제안, 이유를 못 찾아 바꾸지 않은 것. 사용자가 답할 때까지 둔다.
- **커밋 안 된 변경**: 이번 실행의 1단계에서 본 것만 적는다. 지난 실행의 줄은 지운다.

**파일이 없을 때(첫 실행).** 위 형식으로 만든다. "어디까지 봤나"는 예전 맥락 분석 기록에서 이어받는다.
- "분석 범위"와 종류별 마지막 id가 실제로 적힌 기록만 인정한다. 태그에 `context-analysis`가 있거나 제목에 "맥락 분석"이 있어도 분석 범위가 적혀 있지 않으면 쓰지 않는다.
- 찾는 곳은 둘이다. `raw/decisions/`의 결정 기록과, `raw/journal/`에서 내용이 `맥락 분석:`으로 시작하는 decision 줄이다. 둘 중 더 최근 것을 쓴다.
- 거기 적힌 종류별 마지막 id를 옮겨 적는다. 그런 기록이 없으면 id를 비워 두고 처음부터 전부 읽는다. 이때도 3단계는 표에 이미 있는 사례를 다시 더하지 않는다.

## 플러그인을 고칠 때

1. 플러그인 저장소에서 main으로부터 브랜치를 만든다.
2. 변경마다 커밋한다. 한 실행에서 변경이 여러 개면 한 브랜치에 차례로 커밋한다.
3. 세 manifest(`plugin.json`, `.claude-plugin/plugin.json`, `.codex-plugin/plugin.json`)의 버전을 함께 올리는 커밋을 마지막에 하나 더한다.
4. push하고 PR을 만들어 묻지 않고 머지한다. 변경마다 남긴 커밋이 main에 그대로 남도록 머지 커밋으로 들인다(`gh pr merge --merge --delete-branch`). 커밋을 하나로 뭉치면 점검 보고가 변경을 하나씩 가를 수 없다.
5. 체크아웃을 main으로 돌려 `git pull --ff-only`를 한다.
6. 다시 설치한다. Claude Code는 `claude plugin marketplace update task-workflow-marketplace`와 `claude plugin update task-workflow@task-workflow-marketplace`, Codex는 `codex plugin marketplace upgrade task-workflow-marketplace`. 바뀐 스킬은 새 세션부터 보인다.

push나 PR, 머지가 실패하면 플러그인에 넣는 일만 거기서 멈춘다. 같은 명령을 그대로 되풀이하지 않는다.
- 건너뛰는 것: 이 절의 남은 단계(머지, main으로 돌리기, 재설치). 브랜치와 커밋은 지우지 않고 남긴다.
- 건너뛰지 않는 것: 전역 설정에 넣을 변경, 순서 7단계(상태 파일).
- 머지되지 않은 변경은 상태 파일 "판정 못 한 것"에 브랜치 이름과 함께 적고, 결과 보고의 "확인할 것"에도 적는다.

## 훅이나 점검 스크립트로 올릴 때

- 훅은 플러그인의 `plugins/task-workflow/hooks/hooks.json`에 넣는다. Claude Code의 플러그인 훅 형식을 따른다. 파일과 폴더는 처음 올릴 때 만든다.
- 전역 설정의 훅과 설정 파일(`~/.claude/hooks/`, `~/.claude/settings.json`)에는 넣지 않는다. 보안 규칙이라 "바꾸면 안 되는 것" 절에 걸린다.
- 넣기 전에 플러그인 훅 형식을 Claude Code 공식 문서에서 확인한다. 확인할 수 없으면 올리지 않고 상태 파일 "사용자에게 올릴 것"에 이유와 변경안을 적는다. 형식이 틀린 훅은 조용히 안 돌거나 모든 세션을 막을 수 있어서다.
- 점검 스크립트는 그 규칙이 있는 스킬의 `scripts/`에 넣고, 스킬 본문에 언제 돌리는지 적는다.
- 올리는 것도 플러그인 변경이다. 위 "플러그인을 고칠 때" 절대로 커밋하고 머지한다.

## 규칙 관리 원칙

- 규칙은 한 곳에만 쓴다. 다른 곳은 그곳을 가리킨다(파일 경로와 절 이름). 같은 목록(예: 위험한 변경 목록)도 한 곳에만 둔다.
- 규칙이 바뀌면 그 한 곳만 고친다. 가리키는 쪽은 고칠 일이 없어야 한다.
- 지식 베이스의 지난 기록은 고치지 않는다. 새 결정이 예전 결정을 전부 바꾸면 사서가 정리 때 대체됨 표시만 한다.
- grep은 옛말이 다른 곳에 남았는지 마지막에 한 번 확인하는 용도다(6단계). 규칙을 여러 곳에 써 두고 grep으로 맞추는 방식이 아니다.

## 결과 보고

두 줄로 보고한다.
- **완료**: 분류한 사례 n줄. 넣거나 고친 규칙마다 "규칙 한 줄 → 파일 절", 추정 번호, 커밋 해시. 틀려서 다시 본 추정 번호. 아침 보고서 파일 경로. 플러그인을 고쳤으면 PR 링크, 머지 여부, 재설치 결과. 보류 n건. 상태 파일 커밋 해시(달라진 것이 없어 커밋하지 않았으면 그렇게 적는다).
- **확인할 것**: 훅이나 점검 스크립트로 올린 것. 상태 파일 "사용자에게 올릴 것"에 새로 적은 항목. 넣지 못한 변경과 이유. 없으면 "없음".

## 하지 말 것

- 예약 실행에서는 사용자에게 묻지 않는다. 정할 수 없는 것은 상태 파일에 적고 넘어간다.
- 보안 규칙과 점검 장치, 프로젝트 지침과 프로젝트 문서를 고치지 않는다(전역 지침 "규칙 바꾸기" 절).
- 커밋 안 된 변경을 되돌리거나 함께 커밋하지 않는다.
- 지식 베이스에는 규칙별 사례표의 줄과 상황판의 두 가지(플러그인을 고쳤을 때 그 프로젝트 묶음, 프로젝트에만 걸리는 것의 "지침 후보")만 쓴다. 지난 기록을 고치지 않고, 규칙 문서를 만들지 않고, 에이전트가 판단한 이력을 기록으로 남기지 않는다. 그 이력은 바꾼 저장소의 커밋에 있다.
- 사례에 없는 사용자 말이나 이유를 지어 넣지 않는다.
- 이력을 다시 쓰지 않는다(amend, force push, 이미 올린 커밋의 rebase). push 안 된 자기 커밋을 `git pull --rebase`로 원격 위에 올리는 것만 된다(전역 지침 "커밋" 절).
