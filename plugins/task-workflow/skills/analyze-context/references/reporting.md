# 추정 기록과 아침 보고서

자가 발전 순서의 7단계에서 읽는다. 규칙을 넣거나 고칠 때마다 무엇을 원인으로 봤는지 적어 두는 방법과, 그것을 사용자에게 보여 주는 아침 보고서의 형식이다.
추정을 적어 두지 않으면 다음 실행이 그 추정이 맞았는지 판단할 수 없다. 문장만 덧붙이게 된다.

두 파일 모두 지식 베이스에 있고 지식 베이스 main에 커밋한다. 언제 무슨 일로 어떤 규칙을 왜 고쳤는지도 에이전트가 모르는 맥락이라서다. 상태 파일은 전역 설정 저장소(`~/.claude`)에 있어 따로 커밋한다(자가 발전 스킬 순서 7단계).

## 추정 기록

지식 베이스 `wiki/hypotheses.md`. 상태 줄을 고쳐 쓰는 파일이라 원본(`raw/`)이 아니라 `wiki/`에 둔다. 규칙을 넣거나 고친 변경마다 묶음 하나를 파일 끝에 더한다. 파일이 없으면 아래 머리글로 만든다.

```markdown
# 추정 기록

자가 발전(`task-workflow:analyze-context`)이 규칙을 넣거나 고칠 때마다 무엇을 원인으로 봤는지 적는다.
추정이 맞았는지는 뒤에 들어오는 사례로 확인한다.

## H-YYYYMMDD-NN <무엇을 어떻게 고쳤나, 한 줄>
- 상태: 지켜보는 중
- 문제: <무슨 일이 있었나>. 사용자 말: "<그대로>" (C-…)
- 원인 추정: <무엇이 없어서 또는 무엇이 안 읽혀서 났다, 한 문장>
- 고친 것: <파일과 절>. 원래: "<고치기 전 문장. 없었으면 '없음'>" → 고친 뒤: "<고친 문장>" (<저장소 이름> <커밋 해시>)
- 이 방법을 고른 이유: <얻는 것과 잃는 것을 어떻게 따졌나>
- 다른 방법: <따져 본 다른 방법과 고르지 않은 이유>
- 틀렸다고 볼 신호: <어떤 사례가 들어오면 이 추정이 틀린 것인가>
- 확인: <대어 본 지난 사례 id와 결과>
```

- 번호 `NN`은 같은 날 안에서 01부터 올라간다.
- **상태**는 넷 중 하나다.
  - `지켜보는 중`: 넣은 뒤 아직 맞는지 모른다.
  - `맞는 것으로 봄 (YYYY-MM-DD)`: 토요일 점검이 정한다. 자가 발전은 이 값으로 바꾸지 않는다.
  - `틀림 → H-…`: 틀렸다고 볼 신호에 맞는 사례가 들어왔다. 다시 세운 추정의 번호를 적는다.
  - `되돌림 (YYYY-MM-DD)`: 확인에서 불일치가 풀리지 않아 변경을 되돌렸다.
- 묶음은 지우지 않는다. 상태 줄만 고친다. 다른 줄은 고치지 않는다.
- **문제**의 사용자 말은 사례의 `## 있었던 일`에 있는 사용자 말에서 그대로 옮긴다. `## 요지`나 `## 분석`의 글을 사용자 말로 옮기지 않는다. 사례에 없는 말을 지어 넣지 않는다. 사용자 말이 없는 사례면 "사용자 말 없음"이라고 적는다.
- **틀렸다고 볼 신호**는 사례 한 건을 보고 맞다 아니다를 가를 수 있게 적는다. "효과가 없으면"처럼 가를 수 없는 말을 쓰지 않는다.
- 사용자가 대화 중에 규칙을 정해서 넣은 변경도 묶음을 적는다. "이 방법을 고른 이유"에 "사용자가 정함"과 사용자 말을 적는다.
- 글은 사서의 [글쓰기 규칙](../../librarian/references/writing.md)을 따른다.

## 아침 보고서

지식 베이스 `raw/reports/YYYY-MM-DD.md`. 자가 발전이 돈 날마다 하나 쓴다. 사용자가 아침에 달라고 할 때 보여 주는 문서다. 머리말을 두지 않는다.
원본이라 쓰고 나면 본문을 고치지 않는다. 뒤에 하는 것은 둘뿐이다. 같은 날 다시 돌았을 때 끝에 이어 쓰기와, 확인이 끝난 뒤 "확인 결과" 절 채우기다. 확인에서 틀린 것으로 드러난 줄은 아래 "확인 결과를 받았을 때"대로만 고친다.
사용자는 이 보고서로 문장을 검수하지 않는다. 에이전트가 어떻게 판단했는지를 보고, 방향을 잘못 잡은 것만 말해 준다. 하루에 20분 넘게 쓰지 않는다. 그래서 짧게 쓰되 맥락을 빼지 않는다.

```markdown
# 아침 보고서 YYYY-MM-DD

정하실 것 n · 고친 규칙 n · 다시 본 추정 n · 보류 n
새로 확정된 기록 n건(사례 n, 결정 n, 맥락 n), 확정 못 한 기록 n건, 지식 베이스에 없는 것 n건.

## 사용자가 정할 것

### <무엇을 어느 파일의 어느 절에 넣거나 바꿀지, 한 줄>
- 계기: <언제, 어느 프로젝트에서, 무슨 작업 중에 무슨 일이 있었나>
- 넣으면: <에이전트의 행동이 어떻게 달라지나>
- 부작용: <그렇게 정해서 생기는 일>
- 직접 정해야 하는 이유: <보안 규칙이라서, 점검 장치라서, 규칙을 둔 이유를 못 찾아서 등>
- 사용자 말: "<그대로>"

## 지식 베이스에 없는 것
- <찾던 것 한 줄> (C-…). 찾아본 곳: <지식 베이스의 어디와 세션 기록 며칠 치>

## 고친 것

### 1. <무엇을 했나, 한 줄>
- 문제: <언제, 어느 프로젝트에서, 무슨 작업 중에 에이전트가 무엇을 했나>
- 원인: <무엇이 없어서 또는 무엇이 안 읽혀서 났나>
- 조치: <어느 파일의 어느 절에 무엇을 넣거나 바꿨나>
- 사용자 말: "<그대로>"

<details><summary>자세히</summary>

- 다른 방법: <따져 본 방법과 고르지 않은 이유>
- 틀렸다고 볼 신호: <신호>
- 추정 기록: H-… · 근거 사례: C-… · 커밋: <저장소 이름> <해시>
</details>

## 추정이 틀려 다시 본 것

### 1. <무엇을 다시 했나, 한 줄>
- 지난번 원인 추정: <한 문장>
- 틀렸다고 본 계기: <언제, 어느 프로젝트에서, 무슨 일이 다시 났나>
- 이번 조치: <어느 파일의 어느 절에 무엇을 넣거나 바꿨나>
- 사용자 말: "<그대로>"

<details><summary>자세히</summary>

- 추정 기록: H-… → H-… · 근거 사례: C-… · 커밋: <저장소 이름> <해시>
</details>

## 넣지 않고 지켜보는 것

### <앞으로 이렇게 한다, 한 줄>
- 상황: <언제, 어느 프로젝트에서, 무슨 일이 있었나>
- 보류 이유: <한 문장>
- 사용자 말: "<그대로>"

## 확정 못 한 기록
- <기록 id> <제목>: <판정>. <이유 한 줄>

## 기타
- 프로젝트 지침 후보: <프로젝트 이름> 대기 n건 (이번에 더한 것 n건)

<details><summary>어제 기록을 이렇게 이해함 (n건)</summary>

- <기록 id> <제목>: <요지 한 줄>
</details>

## 확인 결과
아직 확인 전.
```

쓰는 방법이다.

- 사용자가 결정할 것을 맨 위에 둔다. 사용자가 이 절만 보고 닫아도 되게 하기 위해서다.
- 항목마다 문제, 원인, 조치를 한 줄씩 개조식으로 쓴다. 한 줄은 한 문장이다. 이야기처럼 풀어 쓰지 않는다.
- 사용자는 그 사례가 무슨 일이었는지 기억하지 못한다고 보고 쓴다. "문제", "계기", "상황" 줄에는 사례를 모르고 읽어도 알 수 있게 언제, 어느 프로젝트에서, 무슨 작업 중이었는지를 넣는다. 사례 id나 "재발 3번" 같은 말만 적지 않는다.
  예: "시안 제목 아래 설명을 넣음" ✗ → "11/16 골프장 사이트의 매물 등록 시안에서 제목 아래마다 설명 문장을 넣음" ✓
- "조치"와 "사용자가 정할 것"의 제목에는 어느 파일의 어느 절인지를 적는다. 사용자가 어디가 바뀌는지 알 수 있게 하기 위해서다.
  예: "먼저 묻는 규칙을 넣을지" ✗ → "먼저 묻는 규칙을 전역 지침(`~/.claude/CLAUDE.md`) "보안" 절에 넣을지" ✓
- 사용자 말은 항목 맨 아래 줄에 따로 둔다. 사례의 `## 있었던 일`에 있는 사용자 말에서 그대로 옮긴다. 에이전트가 요약한 말을 따옴표에 넣지 않는다. 사용자가 읽고 "내가 그 뜻으로 한 말이 아닌데"를 바로 알 수 있게 하기 위해서다. 사용자 말이 없는 사례면 이 줄을 쓰지 않는다.
- 다른 방법, 틀렸다고 볼 신호, 추정 번호, 사례 id, 커밋 해시는 "자세히" 안에만 둔다. 펼치지 않아도 무슨 일이 있었고 무엇을 바꿨는지 알 수 있어야 한다. 확인 단계(`evolve-report-checker`)가 사례 id와 커밋을 찾으므로 "자세히"에서 빼지 않는다.
- 항목이 없는 절은 쓰지 않는다. 개수는 맨 위 두 줄에만 둔다. "확인 결과" 절만 늘 둔다.
- "기타"의 "프로젝트 지침 후보"는 지식 베이스 상황판(`wiki/board.md`)의 묶음마다 "지침 후보" 줄 아래 항목 수를 센다. 후보가 있는 프로젝트만 적는다. 없으면 이 줄을 쓰지 않는다.
- 첫 줄에는 절마다 항목 수를 적는다. 둘째 줄에는 이번에 읽은 새로 확정된 기록의 수와 종류별 수, "확정 못 한 기록" 절의 줄 수, "지식 베이스에 없는 것" 절의 줄 수를 적는다.
- "확정 못 한 기록"은 `status: draft`로 남은 기록이다. 메인 세션이 넘긴 판정(`범위 불일치`, `요지 불일치`, `스크립트 불일치`, `비밀값`)과 이유를 적는다. 상태 파일 "확정을 기다리는 기록"에 지난 실행부터 남아 있는 것도 같이 적고 며칠째인지 붙인다. 사용자가 그 일이 아직 기록되지 않았다는 것을 알게 하기 위해서다. `스크립트 불일치`는 스크립트를 고쳤으면 "고친 것"의 번호를 붙인다.
- "지식 베이스에 없는 것"은 `notfound` 사례 가운데 말한 적이 없다고 가른 것이다([판단 방법](judging.md) 10절). 사용자에게 묻는 절이라 "사용자가 정할 것" 바로 뒤에 둔다. 찾던 것을 사용자가 읽고 바로 답할 수 있게 한 줄로 적는다. 기록은 있는데 못 찾은 것과 대화에 있었는데 기록이 안 된 것은 여기 적지 않는다. 고쳤으면 "고친 것"에, 보류했으면 "넣지 않고 지켜보는 것"에 적는다.
- "어제 이렇게 이해한 것"은 "기타" 아래 접어 둔다. 이번에 읽은 새로 확정된 기록마다 한 줄이다. 사례, 결정, 맥락을 모두 적는다. 제목은 기록의 제목 그대로, 요지는 그 기록의 `## 요지`를 한 줄로 줄인다. `## 요지`에 없는 말을 더하지 않는다. 사용자가 읽고 "그런 뜻이 아닌데"를 말할 수 있게 하는 절이다. 낮에 세션이 말하는 "이렇게 이해했습니다"를 대신하지 않는다. 낮의 것은 그대로 하고 이 절은 따로 둔다.
- "확인 결과" 절은 "아직 확인 전." 그대로 둔다. 확인이 끝난 뒤 아래 "확인 결과를 받았을 때"대로 채운다.
- 같은 날 보고서가 이미 있으면 그 파일 끝에 `---`를 두고 이어서 쓴다. 사용자가 대화에서 "분석하자"고 불러 다시 돈 경우다.
- 글은 사서의 [글쓰기 규칙](../../librarian/references/writing.md)을 따른다.

## 확인 결과를 받았을 때

매일 정리(`daily-upkeep`)는 분석과 규칙 고치기, 정리가 끝난 뒤 보고서 확인 단계에서 서브에이전트(`evolve-report-checker`)를 띄운다. 분석과 규칙 고치기가 돈 날에만 띄운다. 그 서브에이전트는 읽기만 하고, 보고서의 고친 것마다 판정을 돌려준다. 판정은 셋 중 하나다. `일치`, `불일치`(근거 사례에 그 사용자 말이 없다, 또는 적은 변경과 실제 고친 내용이 다르다), `해석이 갈림`(사용자 말을 다르게도 읽을 수 있다).

기록이 세션과 다르다는 판정은 앞의 기록 확인 단계에서 끝난다. 여기서는 다루지 않는다.

메인 세션이 판정을 넘겨주면 이렇게 한다.

**처음 받았을 때**

- `일치`: 보고서 "확인 결과"에 "일치 n건"을 적는다.
- `해석이 갈림`: 확인하는 쪽과 다투지 않는다. 사용자 말을 어떻게 읽을지는 사용자만 답할 수 있다. 보고서 "확인 결과"에 `<번호>. 해석이 갈림: "<사용자 말>"을 고친 쪽은 <이렇게> 읽었고, 확인한 쪽은 <저렇게> 읽었습니다.`를 적는다. 변경은 그대로 둔다.
- `불일치`: 확인하는 쪽이 적은 내용을 실제 파일과 사례로 다시 본다.
  - 확인하는 쪽이 맞으면 바로잡는다. 보고서나 추정 기록이 틀린 것이면 그 줄을 고친다. 고친 규칙이 틀린 것이면 규칙을 다시 고쳐 커밋한다. 사례의 `## 분석`에 적은 것이 틀렸으면 지우지 않고 날짜와 함께 줄을 덧붙인다([판단 방법](judging.md) 9절).
  - 확인하는 쪽이 틀렸으면 고치지 않고, 왜 그렇게 했는지를 근거(파일 경로와 줄, 사례 id)와 함께 답한다.
  - 보고에 번호마다 "바로잡음"이나 "답함: <이유>"를 적는다. 메인 세션이 이것을 확인하는 쪽에 한 번 더 넘긴다.
- "확인 결과"를 채운 보고서와, 고친 것이 있으면 추정 기록을 지식 베이스 main에 커밋한다. 메시지는 "아침 보고서 YYYY-MM-DD: 확인 결과". 새벽 실행에서는 커밋만 하고 push하지 않는다. 정리 단계가 이미 돈 뒤라 메인 세션이 마지막에 올린다. 판정이 모두 `일치`거나 `해석이 갈림`뿐이면 여기서 끝난다.

**두 번째로 받았을 때(다시 확인한 결과)**

- 다시 확인해서 `일치`가 된 것은 "확인 결과"에 "불일치였다가 바로잡음"으로 적는다.
- 여전히 `불일치`인 것은 더 주고받지 않는다. 그 변경을 되돌린다.
  - 그 변경의 커밋을 `git revert`로 되돌려 새 커밋을 남긴다. 이력을 다시 쓰지 않는다. 플러그인 변경이면 "플러그인을 고칠 때" 절대로 브랜치를 만들어 되돌리고 머지한다.
  - 추정 기록의 그 묶음 상태를 `되돌림 (YYYY-MM-DD)`으로 바꾼다.
  - 상태 파일 "판정 못 한 것"에 근거 사례 id와 "확인에서 불일치가 풀리지 않아 되돌림"을 적는다. 다음 실행이 다시 판단한다.
  - 보고서 "확인 결과"에 `<번호>. 불일치 있음, 되돌림: 고친 쪽은 <…>, 확인한 쪽은 <…>.`으로 양쪽 말을 적는다.
- 보고서와 추정 기록은 지식 베이스 main에, 상태 파일은 전역 설정 저장소에 커밋한다. 메시지는 둘 다 "아침 보고서 YYYY-MM-DD: 확인 결과". 지식 베이스 커밋을 올리는 때는 처음 받았을 때와 같다.

주고받는 것은 이 한 번뿐이다. 세 번째 확인은 없다.
