# 협업 계획·실행

사용자와 논의한 서비스 설계를 실제로 수행 가능한 작업 구조로 구체화한다.
설계 방법·기술 스택·에이전트 수·모델을 고정하지 않는다. 커스텀 에이전트를 요구하지 않는다.

## 단계 선택

- 계획 요청 또는 Plan 모드: [협업 계획](references/planning.md)을 읽고 작업 분담·의존관계·통합 방법을 계획한다. 제품 코드·설정 수정이나 작업 에이전트 실행을 시작하지 않는다. 계획 저장도 현재 모드에서 허용되는 수단만 사용한다.
- 실행 요청과 확정된 계획이 있음: [협업 실행](references/execution.md)을 읽고 승인된 범위를 수행한다.
- 실행 여부나 중요한 설계가 미정: 필요한 결정을 사용자에게 묻는다. 스킬이 자동 선택됐다는 이유로 계획을 실행하지 않는다.
- 사용자가 이미 실행 방법과 범위를 정했으면 같은 확인을 반복하지 않는다. 현재 모드와 권한이 실제 실행을 허용하는지 확인한다.

## 공통 판단

- 공통 API·데이터 계약, 공유 파일, 의존성·설정 변경을 먼저 식별한다. 실제 파일이 다르더라도 공유 상태가 있으면 독립 작업으로 취급하지 않는다.
- 작업을 나누는 비용보다 병렬화 이득이 있는 독립 작업만 위임한다. 짧은 작업이나 긴밀하게 얽힌 수정은 메인이 하거나 직렬로 처리한다.
- 실행 환경의 내장 탐색·작업·범용 에이전트 중 사용 가능한 것을 선택한다. 특정 에이전트 이름이나 모델의 존재를 가정하지 않고 제공된 도구를 따른다.
- 서브에이전트 도구가 없거나 위임이 제한되면 그 사실을 알리고, 이미 허가된 실행 범위를 순차로 처리한다. 도구 설치·외부 모델 연결로 제한을 우회하지 않는다.
- 메인은 사용자 논의, 공통 계약, 작업 상태, 충돌 조정, 통합과 최종 판단을 소유한다. 하위 에이전트는 맡은 범위의 결과와 근거를 반환한다.
- 중요한 설계·범위 변경은 사용자와 논의한다. 승인된 설계 안의 일상적인 구현 판단 때문에 매번 작업을 멈추지 않는다.

## 맥락과 출력

작업별로 목표, 필요한 자료·결정, 수정 가능 범위, 의존 작업, 완료 기준과 검증 방법을 전달한다.
최소 맥락만 전달하되 전역 제약과 공유 계약을 누락하지 않는다.
상세 작업·결과는 필요한 경우 프로젝트 안 파일에 남기고, 메인에는 짧은 상태와 근거 위치를 반환하게 한다.
전체 대화·전체 계획·이전 작업 로그를 모든 작업자에게 반복 복사하지 않는다.

기록 스킬이 사용 가능하고 기록 요청 범위에 맞으면 이를 활용할 수 있다. 없어도 기존 기록을 활용하며, 진행의 지속적인 보존이 필요하면 짧은 STATUS와 관련 문서 링크를 유지한다. INDEX는 문서 위치·역할 안내에만 사용하고 계획·정책 상세는 해당 문서에서 관리한다.
동일한 기록 집합은 단일 작성자가 관리한다. 문서 정리를 위임한 동안 새로 나온 결정은 다음 기록 요청으로 전달한다.
최종 출력은 완료한 범위, 검증 결과, 남은 문제에 집중하고 구현 이해에 필요한 핵심 흐름을 짧게 연결한다.
