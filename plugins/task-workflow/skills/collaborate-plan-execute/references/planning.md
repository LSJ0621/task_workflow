# 협업 계획

## 입력

현재 대화·지정된 설계·요구사항·기존 코드에서 확정된 범위와 완료 기준을 확인한다.
과제 분석 스킬이나 특정 형식의 계획 문서를 전제하지 않는다.
설계 결정이 부족해 작업 경계가 정해지지 않으면 그 쟁점을 사용자에게 제시한다.

## 계획에 포함할 결정

- 공통 인터페이스와 먼저 확정해야 할 데이터·오류·응답 계약.
- 의미 있는 결과물 단위의 작업, 담당 역할, 실제 또는 예정 파일 범위.
- 각 작업이 소비·생성하는 계약과 선행 작업.
- 병렬 가능한 묶음과 직렬 처리할 작업, 그렇게 나눈 이유.
- 통합 담당, 합칠 순서, 통합 시 실행할 검증과 완료 기준.
- 주어진 제한시간·자원이 있으면 우선순위, 축소 가능한 부분, 검증·사용자 이해를 위한 여유.

표가 도움이 되면 `작업 | 역할 | 수정 범위 | 선행 조건 | 완료·검증 기준`을 사용한다.
이미 설계 문서에 있는 내용을 전부 복사하지 않고 관련 절을 연결한다.
계획을 코드 전체의 사전 작성이나 테스트 하나마다 별도 작업을 만드는 절차로 부풀리지 않는다.

## 충돌 방지

- 같은 파일·스키마·공유 설정을 수정하는 작업은 담당을 하나로 정하거나 직렬 처리한다.
- 공유 계약을 먼저 정할 수 있으면 그 확정 이후 독립 구현을 병렬 묶음으로 계획한다.
- 파일이 다르더라도 생성물·DB·공유 테스트 환경·lockfile을 함께 바꾸면 충돌을 고려한다.
- 메인과 작업자가 같은 범위를 동시에 수정하는 계획을 만들지 않는다.
- 작업별 환경 분리가 유용하고 허용된다면 제안할 수 있지만 worktree·브랜치·commit을 모든 작업에 강제하지 않는다.
- 파일이 아직 없으면 경로를 예정으로 표시하고 실행 시 기존 구조와 대조하게 한다.

## 반환

사용자가 설계와 협업 전략을 검토할 수 있는 계획을 제시한다.
역할은 정하되 실행 전에는 구현 작업자의 에이전트 ID를 미리 만들어 적지 않는다.
중요 미결정 사항이 있으면 드러낸다. 확정된 계획과 실행 허가가 준비될 때까지 구현 작업의 위임·구현을 시작하지 않는다. 계획에 필요한 읽기 전용 탐색은 허용한다.
