# 협업 실행

## 시작과 재개

확정된 계획, 현재 작업 트리, 관련 기록을 확인한다.
프로젝트 기록이 있으면 처음 탐색 시 INDEX로 문서 위치를 파악하고 STATUS가 있으면 진행 상황을 확인한 뒤 필요한 설계·계획 문서를 읽는다. 이후 요청의 문서 재확인과 STATUS 갱신·완료 정리는 [문서 변경 확인과 STATUS 운영 규칙](../../maintain-work-notes/references/status.md)을 따른다. INDEX에는 상태나 실행 지침을 쓰지 않는다.
완료·진행·대기 작업과 실제 변경 상태를 먼저 대조해 compact나 재개 뒤 같은 작업을 중복 위임하지 않는다.
기록과 실제 상태가 다르면 현재 파일·검증 근거를 확인하고 차이를 남긴다.
타인의 기존 변경을 덮어쓰거나 되돌리지 않는다.

## 위임

각 작업에 다음을 전달한다.

- 목표와 프로젝트에서의 역할.
- 읽을 자료·관련 결정·전역 제약·정확한 공유 계약.
- 수정 가능한 파일·영역과 함께 수정하면 안 되는 공유 영역.
- 선행 작업과 시작 조건, 관찰 가능한 완료 기준.
- 필요한 검사와 결과를 반환할 위치·형식.

전체 대화를 복사하지 않는다. 자료가 크면 관련 파일·절·심볼을 지정한다.
독립 작업만 동시에 시작하고, 의존 작업은 필요한 산출물이 준비된 뒤 시작한다.
하위 에이전트가 임의로 추가 작업자를 만들지 않게 하고, 필요하면 메인이 재분할한다.
특정 모델을 일괄 강제하지 않는다. 사용자·프로젝트·실행 환경의 모델 제한과 선택을 따른다.

## 진행 관리

- 메인은 의존성, 담당 범위와 주요 결정을 추적하고 독립적인 통합 준비를 진행한다.
- 에이전트가 반환할 내용은 상태, 변경 위치, 실제 검증 결과, 우려·질문이다. 큰 diff와 로그는 파일로 전달한다.
- 대기 중에는 가능한 작업을 하되 맡겨둔 영역을 중복 수정하지 않는다. 결과 조회는 환경이 제공하는 알림·적절한 대기 도구를 사용하고 잦은 짧은 폴링을 피한다.
- 공유 계약의 변경 필요가 드러나면 영향받는 작업을 조정하고 계약을 갱신한 뒤 전달한다. 중요한 설계 변경은 사용자와 논의한다.
- 실패·충돌은 원인을 확인해 해당 범위를 수정하거나 순차로 전환한다. 같은 실패를 무한히 재시도하지 않는다.
- 실행이 길어져 지속적인 진행 기록이 필요하면 STATUS에 짧은 작업 상태·다음 작업·진행 장애와 관련 문서 링크를 남긴다. 상세 설계·결정·검증 근거는 해당 문서가 관리하고 모든 중간 출력을 메인 대화에 복제하지 않는다.

## 통합과 완료

작업자의 완료 주장만으로 끝내지 않는다. 변경 범위·인터페이스 일치·계획 대비 누락을 확인한다.
작업별 검사와 별도로 실제 통합 경로의 핵심 검증을 수행한다.
검증 스킬이 제공되면 사용할 수 있지만 필수 의존성으로 만들지 않는다.
남은 문제가 있으면 완료와 구분해 보고하고, 코드 이해를 위해 주요 입력부터 결과까지의 실제 흐름을 짧게 설명한다.
commit, push, 배포, 외부 메시지 전송은 해당 작업에 주어진 권한 범위에서만 수행한다.
