# 매일 정리 순서

예약 작업 하나가 매일 새벽에 떠서 이 순서를 따른다. 메인 세션은 진행만 한다. 단계마다 서브에이전트 하나에 넘기고, 결과를 받아 다음 단계로 간다.
메인 세션은 이 파일만 읽으면 된다. 단계의 내용은 서브에이전트가 자기 지침 파일에서 읽는다.

- 메인 세션이 판단하지 않는 이유: 단계마다 맞는 모델이 다르고, 메인 세션이 내용을 읽기 시작하면 끝까지 갈 컨텍스트가 모자라기 때문이다.
- 메인 세션이 직접 돌리는 명령이 있다. 측정, 건너뛸지 보는 검사, 통과한 기록의 `confirm`, 스크립트 대조의 날수 올리기, 올릴 것이 없는 날의 점검, 마지막 push다. 판단이 아니라 이 파일에 정해진 명령이라서 메인 세션이 한다. 이 파일에 없는 명령은 돌리지 않는다.
- 작업 하나로 묶은 이유: 예약 작업은 앱이 꺼져 있으면 다음에 켤 때 돈다. 단계를 따로 예약하면 한꺼번에 떠서 순서가 깨진다.
- 사용자가 없는 실행이다. 질문하지 않는다. 정할 수 없는 것은 보고의 "확인할 것"에 적는다.

## 단계

| 순서 | 단계 | 건너뛰는 때 | 서브에이전트에 줄 지침 파일 | `model` | `effort` |
| :- | :- | :- | :- | :- | :- |
| 0 | 모으기: 어제까지의 대화 기록에서 메모 없는 지적, 다시 물어본 말, 만족한 말, 고른 선택을 골라 `evolve/signals/`에 날짜별 목록으로 쌓는다 | 모을 날이 없을 때 | `daily-upkeep/references/collect.md` | `opus` | `high` |
| 0 | 측정: 세션 기록과 저장소에서 주 단위 숫자를 뽑아 `evolve/metrics.md`와 `evolve/usage.md`를 고친다 | 없음 | 없음. 메인 세션이 `measure.py`를 직접 돌린다 | 메인 세션 | 메인 세션 |
| 1 | 기록: 메모 줄마다 세션 기록에서 그 일을 뽑아 원본 기록(`status: draft`)을 만든다 | 정리 안 된 메모 0줄이고 `draft` 0건 | `write-records/SKILL.md` | `fable` | `high` |
| 2 | 기록 확인: 만든 기록을 다른 눈으로 확인해 기록마다 판정을 낸다 | 1단계를 건너뛴 날 | 서브에이전트 `task-workflow:record-checker` (지침은 그 정의에 있다) | `opus` | `high` |
| 3 | 분석과 규칙 고치기: 확정된 사례와 측정값으로 규칙과 정리 방식을 고친다 | 새로 확정된 기록 0건이고 판정 조건에 걸린 측정값도, 볼 날짜가 된 시도도 없을 때 | `analyze-context/SKILL.md` | `fable` | `high` |
| 4 | 정리: 확정된 기록을 요약 문서·카드에 올리고, 대체된 기록을 찾고, 점검하고 push한다 | 올릴 것이 없으면 메인 세션이 점검과 push만 한다 | `librarian/SKILL.md`, `librarian/references/shelving.md` | `opus` | `high` |
| 5 | 구조 점검: 문서를 나눌지 합칠지 판단하고 점검 스크립트의 알림을 처리한다 | 토요일 단계를 안 돌리는 날 | `librarian/SKILL.md`, `librarian/references/structure.md` | `fable` | `high` |
| 6 | 사용자 분석 다시 보기: 그 주 사례를 지난 분석 기록에 대어 보고 달라졌으면 새로 쓰기 | 위와 같다 | `analyze-context/references/user-analysis.md` | `fable` | `high` |
| 7 | 점검 보고 분석: 일주일치를 모아 초안 쓰기 | 위와 같다 | `review-report/references/analyze.md` | `fable` | `xhigh` |
| 7 | 점검 보고 검증: 초안 줄마다 근거를 다시 열어 확인 | 위와 같다 | `review-report/references/verify.md` | `opus` | `high` |
| 7 | 점검 보고 만들기: HTML, 커밋, 태그 | 위와 같다 | `review-report/references/publish.md` | `opus` | `high` |

- 1~3단계가 자가 발전이다. 세션 기록을 읽는 것은 0~3단계뿐이다. 4단계(사서)는 확정된 기록을 올리는 정리 단계다.
- 지침 파일의 경로는 스킬 모음 폴더(이 스킬 폴더의 한 단계 위) 기준이다. 넘길 때는 절대 경로로 바꿔 준다.
- 단계마다 어느 지침 파일을 주는지는 이 표에만 둔다. 지침 파일이 더 읽으라고 한 파일(형식, 글쓰기 규칙 같은 것)은 서브에이전트가 그 파일을 보고 스스로 찾아 읽는다.
- **모델과 effort는 사용자가 정한 값이다.** Claude Code에서는 Agent 도구를 부를 때 `model`과 `effort`를 표의 값 그대로 지정한다. 서브에이전트 정의에 값이 있는 2단계도 호출에서 직접 지정한다. 어떤 값으로 돌렸는지 실행 기록에 남기기 위해서다. 다시 띄우는 단계도 처음과 같은 값으로 띄운다. 표의 값을 다른 값으로 바꾸지 않는다.
- 두 값을 지정할 수 없는 환경이면 지정 없이 돌리고, 어느 단계를 지정 없이 돌렸는지 보고에 적는다.
- 2단계는 범용 서브에이전트가 아니라 플러그인의 서브에이전트 정의(`agents/record-checker.md`)로 띄운다. Agent 도구의 `subagent_type`에 `task-workflow:record-checker`를 넣는다. 쓸 수 있는 도구(읽기와 검사 실행만)는 그 정의에 있다. 그 이름으로 띄울 수 없으면 범용 서브에이전트에 그 정의 파일(플러그인 폴더의 `agents/` 아래, 스킬 모음 폴더의 한 단계 위)을 지침 파일로 주고 표의 `model`과 `effort`로 돌린다. 그렇게 돌렸으면 보고에 적는다.

## 시작할 때 정하는 것

메인 세션이 처음에 한 번 정해 모든 단계에 같은 값을 넘긴다.

1. **오늘 날짜**(`date +%F`). 점검 보고의 보고서 날짜로도 쓴다.
2. **스킬 모음 폴더의 절대 경로.** 스크립트는 그 아래에 있다. 기록 스크립트는 `write-records/scripts/session_extract.py`, 점검 스크립트는 `librarian/scripts/check_invariants.py`, 측정 스크립트는 `analyze-context/scripts/measure.py`다.
3. **지식 베이스 위치.** `$KNOWLEDGE_BASE_DIR`이 있으면 그곳이다. 없으면 현재 폴더에 `INDEX.md`와 `raw/journal/`이 있는지 본다. 둘 다 아니면 아무 단계도 돌리지 않고 보고로 간다.
4. **스크립트 대조를 할지.** 상태 파일(`~/.claude/evolve/state.md`) `## 스크립트 대조` 절의 `매일 대조:` 줄을 읽는다.
   - `켬`이면 2단계에 "스크립트 대조: 켬"을 넘긴다. 상태 파일이나 그 절이 없어도 켬으로 본다.
   - `끔`이면 "스크립트 대조: 끔"을 넘긴다. 다만 토요일 단계를 돌리는 날에는 "스크립트 대조: 주간"을 넘긴다. 아래 "스크립트 대조 기간" 절에 있다.
5. **지난 점검 태그.** 점검 태그는 세 저장소에 같은 이름으로 달려 있다. 메인 세션은 위치가 정해진 전역 설정 저장소(`~/.claude`)에서 찾는다. 태그를 찾는 명령은 여기에만 둔다.
   ```bash
   git -C ~/.claude tag --list 'review-2*' --sort=-refname | head -1    # 이름이 review-YYYY-MM-DD 인 것 중 가장 뒤
   ```
   아무것도 안 나오면 `review-baseline`이 지난 점검 태그다.
6. **토요일 단계(5~7)를 돌릴지.** 아래 셋 중 하나라도 맞으면 돌린다.
   - 오늘이 토요일이다(`date +%u`가 `6`).
   - 지난 점검 태그가 7일 넘게 지났다. 토요일에 돌지 못했을 때 다음 실행이 대신 돌게 하기 위해서다. 날짜는 태그 이름에서 얻는다. `review-baseline`이면 그 태그가 가리키는 커밋의 날짜를 쓴다(`git -C ~/.claude log -1 --format=%cs review-baseline`).
   - 지시문에 "점검 보고도 돌린다"가 있다. 시험할 때 쓰는 말이다. 요일과 태그를 보지 않고 돌린다.

## 0단계 모으기와 측정

모으기를 먼저 서브에이전트에 넘기고(아래 "넘기는 방법"의 0단계 모으기), 끝나면 성공했든 실패했든 측정을 돌린다. 측정이 모아 둔 목록에서 다시 물어본 횟수를 세기 때문에 이 순서다.
모으기는 쌓아 두기만 하는 단계다. 그 결과와 보고는 뒤 단계에 넘기지 않는다. 3단계(자가 발전)도 그 목록을 읽지 않는다.

메인 세션이 측정 스크립트를 돌린다. 스크립트가 이번 주와 지난주를 다시 세어 지식 베이스의 `evolve/metrics.md` 표에서 그 줄을 고친다. 표는 주 순서이고 마지막 줄이 이번 주다. 쓰임 표(`evolve/usage.md`: 다시 물어본 횟수, 메모 없는 지적 수, 오래된 상황판 묶음 수, 스킬별 실행 횟수)도 같이 고친다. 그 밖의 인자는 `--help`에 있고 평소에는 주지 않는다.

```bash
python3 "<스킬 모음 폴더>/analyze-context/scripts/measure.py" "<지식 베이스>"
```

이 명령의 종료 코드가 0이 아니면 측정이 실패한 것이다. 0이면 두 파일만 커밋한다. 스크립트가 처음 만든 파일일 수 있어서 `git add`를 먼저 한다. 달라진 것이 없으면 커밋하지 않는다. 그것은 실패가 아니다.

```bash
git -C "<지식 베이스>" add evolve/metrics.md evolve/usage.md
git -C "<지식 베이스>" diff --cached --quiet -- evolve/metrics.md evolve/usage.md || git -C "<지식 베이스>" commit -m "측정 <오늘 날짜>" -- evolve/metrics.md evolve/usage.md
```

측정이 실패해도 다음 단계로 간다. 보고의 "확인할 것"에 적는다. 그날은 3단계를 건너뛰지 않는다. 측정값이 판정 조건에 걸렸는지 확인이 안 되기 때문이다.

## 넘기는 방법

단계마다 서브에이전트 하나를 새로 띄운다. 서브에이전트는 메인 세션의 대화를 모르므로 아래를 빠짐없이 적어 준다.

```
목표: <이 단계가 끝나면 무엇이 되어 있어야 하나, 한 문장>
읽을 파일: <지침 파일의 절대 경로>. 이 파일대로 한다. 이 파일이 더 읽으라고 한 파일도 읽는다.
범위: 지침 파일이 정한 일만 한다. 오늘 날짜 <YYYY-MM-DD>. <단계별로 더 주는 것>
완료 기준: <확인할 수 있는 것>
하지 말 것: 사용자에게 묻지 않는다. 다른 서브에이전트를 부르지 않는다. <단계별로 더할 것>
보고: 두 줄(완료 / 확인할 것). 완료 기준을 채우지 못했으면 "확인할 것"에 그렇게 적는다. <단계별로 더 적을 것>
```

2단계는 지침이 서브에이전트 정의에 있으므로 "읽을 파일" 줄을 빼고 넘긴다.

### 0단계 모으기

- 목표: 아직 목록이 없는 날(어제까지)마다 `evolve/signals/<날짜>.md`가 생겨 커밋된다.
- 더 주는 것: 지식 베이스 위치, 스킬 모음 폴더.
- 완료 기준: 아래 명령의 마지막 줄이 `합계 0일`이다. 띄우기 전에 메인 세션이 같은 명령으로 모을 날이 있는지 본다. `합계 0일`이면 건너뛴다.
  ```bash
  python3 "<스킬 모음 폴더>/analyze-context/scripts/collect_signals.py" candidates "<지식 베이스>" --today <오늘 날짜> | tail -1
  ```
- 하지 말 것에 더할 것: push하지 않는다. 메모, 기록, 규칙을 쓰거나 고치지 않는다. 대화 기록의 글을 보고에 옮기지 않는다. 지침 파일의 "하지 말 것"을 지킨다.

### 1단계 기록

- 목표: 정리 안 된 메모 줄과 `draft`로 남은 기록이 모두 원본 기록 파일이 되어 커밋된다.
- 더 주는 것: 지식 베이스 위치.
- 완료 기준: 처리한 메모 파일 끝에 `정리됨:` 줄이 있어 정리 안 된 메모 줄이 남지 않았다. 만든 기록이 모두 `status: draft`이고 발췌 파일(`raw/sessions/`)과 함께 커밋되어 있다.
- 하지 말 것에 더할 것: `confirm`을 돌리지 않는다. push하지 않는다. 요약 문서, 카드, 색인을 고치지 않는다. 지침 파일의 "하지 말 것"을 지킨다.
- 보고에 더 적을 것. 메인 세션이 이 줄들을 다음 단계에 그대로 넘긴다.
  - 만들거나 다시 만든 기록의 id와 파일 경로(지식 베이스 기준). 사례, 결정, 맥락으로 나눠 적는다.
  - `source: memo`로 만든 기록의 id와 이유.
  - 비밀값 때문에 뺀 줄 수.
  - `extract`가 종료 코드 3(모르는 형식)을 냈으면 그 사실과 종류 이름. 없으면 "종료 코드 3: 없음".

### 2단계 기록 확인

- 목표: 이번에 만든 기록마다 판정이 하나씩 나온다.
- 주는 것: 1단계 보고에 적힌 기록 id와 파일 경로, 지식 베이스 위치, 스크립트 위치, 스크립트 대조(켬, 끔, 주간 중 하나).
- 완료 기준: 넘긴 기록 id마다 판정이 한 줄씩 있다.
- 하지 말 것에 더할 것: 어떤 파일도 고치지 않는다. `confirm`을 돌리지 않는다. 세션 기록의 내용을 보고에 옮기지 않는다.
- 받는 보고: 기록 id마다 한 줄(`통과`, `범위 불일치`, `요지 불일치`, `스크립트 불일치`, `비밀값` 중 하나)과 건수. 스크립트 대조를 했으면 대조한 기록 수.
- 1단계의 보고 가운데 id와 파일 경로만 준다. `source: memo`로 만든 이유 같은 설명은 전하지 않는다. 확인하는 쪽이 만든 쪽의 설명을 미리 알면 기록을 새로 보지 않게 되기 때문이다.
- 판정을 다루는 방법은 아래 "기록 확인의 판정을 받았을 때"다.

### 3단계 분석과 규칙 고치기

- 목표: 새로 확정된 사례에 `## 분석`이 채워지고, 볼 날짜가 된 시도에 결과가 적히고, 고칠 규칙과 정리 방식이 고쳐져 커밋되고, 상태 파일이 이번 실행 결과와 맞다.
- 더 주는 것. 앞 단계의 보고 줄을 고쳐 쓰지 않고 그대로 붙인다.
  - 이번 실행에서 확정된(`status: active`가 된) 기록 id 목록. 없으면 "없음".
  - `draft`로 남은 기록 id와 그 판정 줄. 상태 파일 "확정을 기다리는 기록"에 쓰인다.
  - `스크립트 불일치` 판정 줄. 3단계가 스크립트를 고친다.
  - 스크립트 대조 결과: 대조했는지, 대조한 기록 수, 불일치 건수. 3단계가 상태 파일의 연속 일치 날수를 고친다.
  - 1단계 보고의 종료 코드 3 줄.
  - 판정 조건에 걸린 측정값 줄(아래 "건너뛸 때"에서 본 것). 없으면 "없음".
- 완료 기준: 상태 파일이 이번 실행 결과로 고쳐져 있다(달라진 것이 없어 커밋하지 않았어도 완료다). 불변 조건 점검이 `--skip-summary`로 통과한다. 새로 확정된 결정과 맥락은 4단계가 요약에 올리기 전이라 그 검사만 건너뛴다.
  ```bash
  python3 "<스킬 모음 폴더>/librarian/scripts/check_invariants.py" "<지식 베이스>" --skip-summary
  ```
- 하지 말 것에 더할 것: `draft` 기록과 메모 파일을 읽지 않는다. 요약 문서와 색인 파일을 직접 고치지 않는다(4단계가 고친다). 지침 파일의 "허락받고 바꾸는 것"과 "하지 말 것"을 지킨다.
- 보고에 더 적을 것.
  - 정리 방식(사서 스킬)을 고쳤는지. 고쳤으면 어느 파일의 어느 절을 어떻게 고쳤는지 한 줄. 메인 세션이 이 줄을 4단계에 넘긴다.
  - 구조 결정 기록을 남겼으면 그 id.
  - 상태 파일 `## 스크립트 대조` 절을 고쳤는지.
  - 플러그인을 다시 설치했는지.

### 4단계 정리

- 목표: 새로 확정된 결정과 맥락이 요약 문서와 카드에 올라가고, 대체된 예전 기록이 표시되고, 불변 조건 점검이 통과하고, 0~3단계가 커밋만 해 둔 것까지 push된다.
- 더 주는 것: 이번 실행에서 확정된 기록 id 목록. 3단계가 정리 방식을 고쳤으면 3단계 보고의 그 줄.
- 완료 기준: 정리 절차의 보고가 나오고 불변 조건 점검이 옵션 없이 전부 통과한다. push되어 있다. 3단계가 돌지 않은 날에 나오는 "규칙별 사례표에 없는 사례"만 남았으면 실패로 보지 않고 보고의 "확인할 것"에 옮긴다. 점검 스크립트의 "알림"도 실패가 아니다.
- 하지 말 것에 더할 것: 메모를 읽지 않는다. 원본 기록의 본문을 쓰거나 고치지 않는다. 규칙별 사례표를 고치지 않는다. `draft` 기록을 요약 문서에 올리지 않는다. 지침 파일의 "하지 말 것"을 지킨다.

### 토요일 단계

| 단계 | 목표 | 더 주는 것 | 완료 기준 | 하지 말 것에 더할 것 |
| :- | :- | :- | :- | :- |
| 5 구조 점검 | 문서 구조를 분석해 바꿀 것을 바꾸고, 점검 스크립트의 알림을 처리한다 | 없음 | 구조 점검 절차의 보고가 나온다 | 지침 파일의 "하지 말 것"을 지킨다 |
| 6 사용자 분석 | 지난 분석 기록이 그 주 사례와 맞는지 확인되고, 달라졌으면 새 분석 기록이 push된다 | 없음 | 지침 파일의 보고가 나온다. 새로 썼으면 불변 조건 점검이 통과한다 | 지침 파일의 "하지 말 것"을 지킨다 |
| 7 점검 보고 분석 | 보고서 초안이 임시 폴더에 생긴다 | 보고서 날짜(오늘 날짜), 지난 점검 태그 이름 | `/tmp/review-report-<보고서 날짜>/draft.md`가 있고 줄마다 근거가 있다 | 저장소 파일을 고치지 않는다 |
| 7 점검 보고 검증 | 초안의 번호마다 판정이 생긴다 | 초안 경로 | 같은 폴더의 `verdict.md`에 초안의 번호가 모두 있다 | 초안을 고치지 않는다. 지침 파일이 읽지 말라고 한 파일을 읽지 않는다 |
| 7 점검 보고 만들기 | 보고서가 지식 베이스에 올라가고 세 저장소에 태그가 달린다 | 초안과 판정 경로 | 보고서 커밋이 push되고 태그 세 개가 있다 | 초안과 판정에 없는 내용을 넣지 않는다 |

- 검증에는 분석의 보고 내용을 전하지 않는다. 초안 경로만 준다. 검증이 분석의 결론을 미리 알면 근거를 새로 보지 않게 되기 때문이다.
- 만들기에도 앞 단계의 보고를 옮기지 않는다. 초안과 판정의 경로만 준다.

### 플러그인이 다시 설치됐을 때

3단계 보고에 플러그인을 다시 설치했다고 나오면 스킬 모음 폴더를 다시 잡는다. 설치 폴더는 버전마다 따로 생겨서, 처음 잡은 폴더에는 고치기 전 지침이 남아 있다. 3단계가 정리 방식을 고친 날에 4단계가 고친 지침으로 돌게 하기 위해서도 필요하다.
스킬 모음 폴더에서 두 단계 위(버전 폴더들이 나란히 있는 곳)를 보고 가장 새 버전의 `skills` 폴더를 쓴다. 못 찾으면 처음 잡은 폴더를 그대로 쓰고 보고에 적는다.

## 건너뛸 때

새로 볼 것이 없는데 큰 모델을 돌리지 않기 위해서다. 조건은 메인 세션이 아래 명령으로 본다. 하나라도 확인이 안 되면 건너뛰지 않고 돌린다. 건너뛰었으면 보고에 "건너뜀"과 이유를 적는다.

**1·2단계.** 정리 안 된 메모 줄도 없고 `status: draft` 기록도 없으면 둘 다 건너뛴다. 정리 안 된 메모 줄은 메모 파일마다 마지막 `정리됨:` 줄 뒤에 있는 메모 줄이다. `정리됨:` 줄이 없는 파일은 메모 줄 전부다. 아래 명령의 마지막 줄이 `합계`, `메모 0`, `draft 0`이면 없는 것이다. 그 줄이 안 나오거나 수가 하나라도 0이 아니면 돌린다.

```bash
python3 "<스킬 모음 폴더>/write-records/scripts/session_extract.py" pending "<지식 베이스>" | tail -1
```

1단계가 돌았는데 만든 기록이 하나도 없으면 2단계만 건너뛴다. 확인할 기록이 없어서다.
스크립트 대조가 "주간"인 날은 확인할 기록이 없어도 2단계를 띄운다. 아래 "스크립트 대조 기간" 절에 있다.

**3단계.** 2단계의 판정을 다 다룬 뒤에 본다. 아래가 모두 맞을 때만 건너뛴다.

- 상태 파일(`~/.claude/evolve/state.md`)이 있다.
- 새로 확정된 기록이 없다. 이번 실행에서 `confirm`한 기록이 없고, 아래 명령이 낸 종류별 마지막 id가 상태 파일 "어디까지 봤나"의 사례, 결정, 맥락 id와 모두 같으면 없는 것이다. 결정과 맥락까지 보는 이유는 사용자가 점검 보고에 한 답이 결정으로 들어오기 때문이다.
  ```bash
  for d in cases decisions context; do grep -L '^status: draft' "<지식 베이스>"/raw/$d/*.md | sort | tail -1; done
  ```
- 판정 조건에 걸린 측정값이 없다. 상태 파일 "지켜보는 측정값" 절의 줄마다 `evolve/metrics.md` 표의 마지막 줄(이번 주)에서 그 이름의 칸을 찾아 줄에 적힌 조건(`이상`이나 `이하`와 숫자)에 맞는지 본다. 맞는 줄이 하나도 없거나 절이 `- 없음`이면 없는 것이다. 맞는 줄이 있으면 그 줄을 3단계에 넘긴다.
- 볼 날짜가 된 시도가 없다. 추정 기록에서 상태가 "지켜보는 중"이고 볼 날짜가 오늘이거나 지난 시도다. 아래 명령의 마지막 줄이 `합계 0`이면 없는 것이다. 있으면 3단계가 그 시도의 결과를 센다.
  ```bash
  python3 "<스킬 모음 폴더>/analyze-context/scripts/count_recurrence.py" due "<지식 베이스>" | tail -1
  ```
- 2단계가 `스크립트 불일치`를 내지 않았고 1단계 보고가 "종료 코드 3: 없음"이다. 둘 중 하나라도 나온 날은 3단계가 스크립트를 고쳐야 한다. 1단계가 돌지 않은 날은 없는 것으로 본다.

상태 파일 "보류한 후보"와 "판정 못 한 것"에 남은 항목은 조건이 아니다. 새 기록이 들어온 날의 3단계가 함께 본다.

**4단계.** 아래 셋 중 하나라도 맞으면 서브에이전트를 띄운다.

- 이번 실행에서 `confirm`한 기록이 있다.
- 3단계 보고에 정리 방식을 고쳤거나 구조 결정 기록을 남겼다고 적혀 있다.
- 점검 스크립트를 옵션 없이 돌렸을 때 "요약에 없는 유효한 기록" 문제가 나온다. 지난 실행의 4단계가 실패해 확정된 기록이 요약에 올라가지 못한 경우를 다음 날 잡기 위해서다. 아래 첫 수가 `0`이 아니면 나온 것이다. 수가 안 나오면 확인이 안 된 것이므로 띄운다.
  ```bash
  out="$(python3 "<스킬 모음 폴더>/librarian/scripts/check_invariants.py" "<지식 베이스>")"
  echo "$out" | grep -c '에 없는 유효한 기록'   # 요약에 없는 유효한 기록
  echo "$out" | grep -c '\[문제\]'              # 문제 전체
  echo "$out" | grep -c '\[알림\]'              # 알림
  ```

셋 다 아니면 올릴 것이 없는 날이다. 서브에이전트를 띄우지 않는다. 위 명령의 둘째와 셋째 수(문제와 알림의 건수)는 고치지 않고 보고의 "확인할 것"에 옮긴다. push는 아래 "마지막 push"대로 메인 세션이 한다.
3단계가 실패했거나 건너뛰어졌어도 첫째나 셋째 조건이 맞으면 4단계를 띄운다.

## 기록 확인의 판정을 받았을 때

2단계가 돌려준 판정은 메인 세션이 판단하지 않고 아래대로 다룬다. 횟수는 메인 세션이 센다.

1. **`통과`인 기록은 확정한다.** 스크립트의 `confirm`을 돌리고 바뀐 파일만 커밋한다. `confirm`은 `verify`를 다시 돌려 통과한 기록만 `status: active`로 바꾼다.
   ```bash
   python3 "<스킬 모음 폴더>/write-records/scripts/session_extract.py" confirm "<기록 파일>" ["<기록 파일>" ...]
   git -C "<지식 베이스>" commit -m "기록 확정 <오늘 날짜>: n건" -- <confirm한 기록 파일들>
   ```
   `confirm`이 바꾸지 않은 기록은 `draft`로 두고 보고에 적는다. 메인 세션이 `status` 줄을 손으로 바꾸지 않는다.
2. **`범위 불일치`, `요지 불일치`, `비밀값`인 기록은 1단계를 한 번 다시 띄워 고친다.** 그 기록의 판정 줄을 그대로 붙여 주고, 그 기록만 같은 id로 고쳐 쓰라고 한다. 새 메모는 처리하지 말라고 한다.
3. **고친 기록만 2단계를 한 번 더 돌린다.** 처음과 같은 것을 주고 기록 목록만 고친 기록으로 줄인다. 1단계가 어떻게 고쳤는지는 전하지 않는다.
4. **다시 받은 판정을 다룬다.** `통과`는 1번대로 확정한다. 여전히 통과 못 한 기록은 `draft`로 두고 보고에 적는다. 세 번째 확인은 하지 않는다. 남은 `draft`는 다음 새벽 1단계가 다시 만든다.
5. **`스크립트 불일치`인 기록은 다시 만들지 않는다.** `draft`로 두고 판정 줄을 3단계에 넘긴다. 3단계가 스크립트를 고치고, 다음 새벽 1단계가 다시 뽑는다. 두 번째 확인에서 나온 `스크립트 불일치`도 같다.

메인 세션은 판정이 맞는지 따지지 않는다. 판정 줄을 고쳐 쓰지 않고 그대로 옮긴다.
판정에 불일치가 나온 것은 2단계의 실패가 아니다. 판정이 빠진 기록이 있으면 그 기록은 `draft`로 두고 보고에 적는다.

## 스크립트 대조 기간

스크립트가 세션 기록을 빠짐없이 옮기는지 2단계가 세션 기록을 직접 읽어 대어 보는 기간이다. 상태 파일 `## 스크립트 대조` 절에 `연속 일치: n일`과 `매일 대조: 켬|끔` 두 줄이 있다. 두 줄을 고치는 규칙은 여기에만 둔다.

- 대조한 기록이 한 건 이상이고 `스크립트 불일치`가 0건이면 n을 1 올린다. `스크립트 불일치`가 나오면 0으로 돌린다. 다시 확인한 것까지 합쳐서 센다. 2단계가 안 돌았거나 대조한 기록이 없는 날은 그대로 둔다.
- n이 7이 되면 `매일 대조: 끔`으로 바꾼다.
- 1단계가 종료 코드 3을 냈다고 보고한 날은 `매일 대조: 켬`으로 돌리고 n을 0으로 한다.
- 꺼진 뒤로는 토요일 단계를 돌리는 날에만 "스크립트 대조: 주간"을 2단계에 넘긴다. 2단계가 지난 7일의 `source: session` 기록 중 세 건을 골라 대조한다. 그날 1단계가 만든 기록이 없어도 이 대조를 위해 2단계를 띄운다. 주간 대조에서 나온 `스크립트 불일치`도 3단계에 넘긴다. 이미 확정된 기록은 건드리지 않는다.
- 주간 대조에서 `스크립트 불일치`가 나오면 `매일 대조: 켬`으로 돌리고 n을 0으로 한다. 다음 날부터 다시 매일 대조한다. 주간 대조가 모두 일치한 날은 두 줄을 그대로 둔다.

3단계가 도는 날은 3단계가 이 규칙대로 고친다. 메인 세션은 대조 결과를 넘기기만 한다.
3단계가 안 도는 날(건너뛰었거나 실패한 날)에는 메인 세션이 두 줄을 고치고 전역 설정 저장소에 커밋한다. 숫자를 정해진 대로 바꾸는 일이라 판단이 아니다. 절이 없으면 `연속 일치: 0일`, `매일 대조: 켬`에서 시작해 절을 더한다.

```bash
git -C ~/.claude commit -m "스크립트 대조 <오늘 날짜>: 연속 일치 n일" -- evolve/state.md
```

## 마지막 push

4단계 서브에이전트가 돌면 그 단계가 지식 베이스를 push한다. 0~3단계가 커밋만 해 둔 것도 그때 함께 올라간다.
메인 세션은 모든 단계가 끝난 뒤, 보고 직전에 지식 베이스에 push 안 된 커밋이 남아 있는지 보고, 있으면 push한다. 4단계 서브에이전트를 띄우지 않은 날과 앞 단계가 실패해 4단계까지 가지 못한 날에 남는다. 지식 베이스 저장소 push는 미리 허락된 것이다.

```bash
git -C "<지식 베이스>" log --oneline @{u}..    # 아무것도 안 나오면 올릴 것이 없다
git -C "<지식 베이스>" push
```

- push가 거부되면 `git -C "<지식 베이스>" pull --rebase origin main`을 한 번 하고 다시 push한다. 리베이스가 충돌하거나 그래도 안 되면 커밋만 남기고 보고에 적는다.
- 4단계가 돌다가 실패한 날에는 메인 세션이 push하지 않는다. 정리가 중간에 멈춘 상태일 수 있어서다. 보고에 "push 안 됨"을 적는다. 다음 새벽의 4단계가 올린다.

## 멈출 때

- 실패: 서브에이전트가 오류로 끝났다. 보고가 없다. 보고에 완료 기준을 채우지 못했다고 적혀 있다.
- **0단계 모으기가 실패해도 측정과 뒤 단계를 모두 그대로 돌린다.** 뒤 단계가 그 목록을 쓰지 않기 때문이다. 보고의 "확인할 것"에 적는다. 목록이 없는 날은 다음 새벽의 모으기가 다시 모은다.
- **1단계나 2단계가 실패하면 뒤 단계를 모두 돌리지 않고 보고로 간다.** 토요일 단계도 돌리지 않는다. 확인되지 않은 기록 위에서 분석과 정리가 돌면 안 되기 때문이다. 판정을 받은 뒤 다시 띄운 1단계나 2단계가 실패한 것도 같다. 그때까지 확정한 기록은 그대로 두고 나머지는 `draft`로 둔다.
- **3단계가 실패하거나 건너뛰어도 4단계는 "건너뛸 때"의 조건대로 돌린다.** 확정된 기록은 3단계와 상관없이 요약 문서에 올라가야 하기 때문이다.
- 3단계나 4단계가 실패한 날에는 토요일 단계를 돌리지 않는다. 토요일 단계는 그 결과 위에서 돌기 때문이다.
- 토요일 단계(5~7) 안에서는 앞 단계가 실패하면 뒤 단계를 돌리지 않는다.
- 실패가 아닌 것: 조건에 따라 건너뜀. 2단계에서 `통과`가 아닌 판정이 나옴(위 절대로 다룬다). 3단계에서 상태 파일이 달라지지 않아 커밋이 없음. 5단계의 "바꿀 것 없음". 6단계의 "달라진 것 없음". 7단계 검증에서 틀린 줄이 나옴(만들기가 지침대로 표시해 싣거나 뺀다).
- 실패한 단계를 메인 세션이 대신 하거나 고쳐서 다시 돌리지 않는다. 다시 띄우는 것은 "기록 확인의 판정을 받았을 때" 절에 정해진 한 번뿐이다. 무엇이 어디서 멈췄는지 적는 것까지가 메인 세션의 일이다.
- 토요일 단계가 중간에 멈추면 태그가 달리지 않는다. 그래서 지난 점검 태그에서 7일이 넘으면 다음 실행이 토요일 단계를 다시 돈다.

## 보고

마지막에 두 줄로 보고한다.

- **완료**: 단계마다 한 줄. `<순서> <단계 이름> | model <값>, effort <값> | <결과 한 문장>` 꼴이다. 지정할 수 없어 못 넣었으면 "지정 못 함"이라고 적는다. 돌리지 않은 단계는 "건너뜀"이나 "토요일 아님", "앞 단계 실패로 안 돌림"으로 적는다. 다시 띄운 단계는 같은 줄에 "다시 띄움 1회"를 적는다. 2단계 줄에는 확정한 기록 수와 `draft`로 남은 기록 수를 적는다. 메인 세션이 직접 한 것(측정, 연속 일치 날수 올리기, 올릴 것이 없는 날의 점검, 마지막 push)도 한 줄씩 적는다.
- **확인할 것**: 멈춘 단계와 이유. 모으기가 실패했으면 그 사실. 단계 보고의 "확인할 것"에 있던 것. `draft`로 남은 기록의 id와 판정 이름. `스크립트 불일치` 건수. `source: memo`로 만든 기록 수. 4단계가 대체됨 표시를 한 쌍(예전 id → 새 id). 점검 스크립트의 알림 건수. push하지 못했으면 그 사실. 자가 발전이 남긴 구조 결정 기록 id. 사용자 분석이 새로 쓰였으면 새 기록 id. 점검 보고서가 나왔으면 파일 경로와 "사용자에게 올릴 것" 건수. 없으면 "없음".

세션 기록의 내용과 기록의 본문은 보고에 옮기지 않는다. id와 판정 이름, 건수만 적는다.

## 하지 말 것

- 메인 세션이 기록을 쓰거나, 기록을 확인하거나, 규칙을 고치거나, 요약 문서를 고치거나, 보고서를 쓰지 않는다. 전부 서브에이전트에 넘긴다.
- 메인 세션이 세션 기록이나 기록의 본문을 읽지 않는다. 이 파일에 적힌 명령만 돌린다.
- 서브에이전트의 결과를 메인 세션이 고쳐 쓰거나 판단을 덧붙이지 않는다.
- 2단계가 `통과`라고 하지 않은 기록에 `confirm`을 돌리지 않는다.
- 기록 확인에서 주고받는 횟수를 늘리지 않는다. 한 번 돌려보내고 한 번 다시 확인하는 것이 전부다.
- 단계 순서를 바꾸거나 여러 단계를 한꺼번에 띄우지 않는다. 한 단계가 끝난 뒤 다음 단계를 넘긴다.
- 사용자에게 질문하지 않는다.
