# 작업 점검

초기에는 에이전트끼리 검수한 것을 사용자가 직접 봐야 한다. 여기서 나오는 지적이 기준 문서의 재료라서, 초기에 꼼꼼할수록 나중에 덜 봐도 된다. 이 세션은 비서와 따로 연다. 산출물을 읽어야 해서 비서 컨텍스트에 넣으면 안 된다.

## 순서

1. 지식 베이스를 찾고(`$KNOWLEDGE_BASE_DIR` 또는 현재 폴더) `git pull --ff-only`.
2. 볼 범위를 정한다. 기본은 오늘. 사용자가 기간이나 작업을 지정하면 그것.
   - 초기(기준 문서에 도메인 기준이 거의 없을 때): 전부.
   - 그다음: "확인할 것"이 있는 작업 + 무작위 하나.
   - 기준이 쌓인 뒤: "확인할 것"이 있는 것만.
   어느 단계인지는 사용자에게 한 줄로 확인한다.
3. 목록을 만든다. `wiki/board.md`의 "오늘 끝난 작업", `raw/reviews/`의 해당 날짜 `R-` 문서, `raw/reports/`의 해당 날짜 `B-` 보고서(커밋 해시가 있다). 진행판과 `R-`·`B-` 문서가 어긋나면 `R-`·`B-` 쪽이 사실이다. 진행판은 요약 문서라서다.
4. 작업마다 보여 준다. 검수 결과의 판정과 발견 항목 표를 먼저, 원하면 산출물을 연다. 산출물은 로컬 커밋이므로 보고서에 적힌 커밋 해시로 `git show <해시>`를 보거나 파일을 연다. 요약은 짧게. 사용자가 판단할 수 있게 **기준 항목 id와 근거**를 같이 보여 준다.
5. 사용자가 지적하면 `librarian`으로 메모 한 줄(feedback). 사용자 말 그대로. 관련 `R-` id를 붙인다.
   - 검수자가 놓친 것이면 그 사실도 메모에 적는다. 그게 검수 기준을 고치는 재료다.
   - 다시 해야 할 작업이면 메모 끝에 `| urgent`. 비서가 다음에 읽고 새 팀장을 연다. 이 세션이 직접 시키지 않는다. 지시는 비서만 한다.
6. 끝나면 오늘 메모 전체를 한 번 보여 주고, 두 줄로 보고한다. 완료에 본 작업 수와 남긴 메모 수, 확인할 것에 urgent 메모가 있으면 그 작업 이름.

## 하지 말 것

- 산출물을 고치지 않는다. 지적만 메모한다.
- 재작업을 직접 띄우지 않는다. urgent 메모로 비서에게 넘긴다.
- 검수 결과를 다시 쓰지 않는다. 검수자가 틀렸으면 그게 사례다.
- 기준 문서를 고치지 않는다. 사서의 정리가 지식 베이스의 로컬 제안 브랜치로 올리고, 사용자가 비서에게 머지를 맡기면 승인된다.
