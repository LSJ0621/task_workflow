# 정리 절차 (사서 정리 모드)

메모를 정식 기록으로 옮기고, 카드를 갱신하고, 기준에 넣을 후보를 골라 제안한다. 하루 한 번 밤 예약 실행이 부르고, 급한 메모가 있으면 그 한 건만 즉시 한다.
정리는 비싸다. 그래서 한 세션에서 몰아 한다. 틀과 규칙을 한 번 읽고 여러 건을 처리하기 위해서다.

## 혼자 해도 되는 것과 제안만 하는 것

| 혼자 한다 (main에 커밋) | 제안만 한다 (브랜치 + PR) |
| :- | :- |
| 원본 추가(사례·결정·맥락), 카드 갱신, 회귀 질문 추가, 메모 파일에 "정리됨" 줄, `status`/`superseded_by` 표시 | 기준 문서 수정, 파일 이동·합치기·이름 바꾸기, 불변 조건 바꾸기 |

왼쪽은 추가거나 원본에서 다시 만들 수 있는 것이라 틀려도 복구된다. 오른쪽은 틀리면 맥락이 깨지거나 다음 작업의 판단이 바뀐다. 그래서 사용자가 PR을 머지하는 게 승인이다.

## 순서

1. **읽기.** `git pull --ff-only`. `wiki/conventions.md` 전체, `wiki/templates/`의 틀, `README.md`의 불변 조건을 읽는다. 형식은 전부 거기서 나온다.
2. **대상 고르기.** `raw/journal/`에서 끝에 `정리됨:` 줄이 없는 날짜 파일. 급한 한 건이면 그 줄만. 그리고 같은 날짜의 검수 결과(`raw/reviews/R-*`)에서 기준 칸이 "없음"인 발견 항목. 검수자가 기준 밖에서 잡아낸 문제는 사용자 피드백과 같은 재료다. 사용자가 보기 전에 기준이 되면 사용자가 볼 일이 줄어든다.
3. **줄마다 정식 기록 만들기.**
   - 식별자는 스크립트로 받는다. 손으로 세면 겹친다.
     ```bash
     python3 "${CLAUDE_PLUGIN_ROOT}/skills/librarian/scripts/next_id.py" "$KNOWLEDGE_BASE_DIR" C   # C|D|X|R
     ```
   - `feedback` → 사례(`C-`) 틀. 사용자 말은 그대로. `related`에 검수 결과 id.
   - `decision` → 결정(`D-`) 틀. 선택지가 메모에 없으면 "미확인"이라고 적는다. 이유를 지어내지 않는다.
   - `context` → 맥락(`X-`) 틀. 유효 기간은 메모에 없으면 "변할 수 있음".
   - 머리말의 `domain`은 `INDEX.md`의 도메인 목록에 있는 것만. 없는 도메인이 필요하면 목록에 먼저 추가하고 그 사실을 보고에 적는다.
4. **기준 반영 제안.** 사례마다 규칙 문서의 승격 절차 세 질문에 답해 사례 파일의 "승격 제안" 절을 채운다. 상태는 `제안됨`.
   - 이미 있는 원칙에 속하면 새 원칙을 만들지 않고 그 원칙에 점검 항목만 더한다. 비슷한 원칙이 열 개 쌓이는 걸 막기 위해서다.
   - 원칙은 실수에서 한 단계만 올라간다. 점검 항목은 검수자가 실제로 확인할 수 있는 것만.
   - 같은 지적이 사례 두 건 이상이면 우선순위를 올린다.
5. **카드 갱신.** 메모와 그날 검수 결과에 등장한 프로젝트마다 `wiki/projects/<slug>.md`를 원본에서 다시 쓴다. 20줄 안. 없던 프로젝트면 새로 만든다. 규칙 문서의 프로젝트 카드 절이 항목을 정한다.
6. **회귀 질문.** 새 결정마다 `tests/regression.md`에 질문 한 줄. "왜 X를 Y로 정했나?" 꼴이 기본이다.
7. **불변 조건 점검.**
   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/skills/librarian/scripts/check_invariants.py" "$KNOWLEDGE_BASE_DIR"
   ```
   문제가 나오면 커밋 전에 고친다. 고칠 수 없는 것(예: 출처 없는 기준)은 보고에 적고 넘어간다.
8. **메모 파일 마감.** 처리한 날짜 파일 끝에 `정리됨: <만든 id들>` 한 줄. 메모 줄은 건드리지 않는다.
9. **커밋·push.** main에 "사서 정리 YYYY-MM-DD: 사례 n, 결정 n, 맥락 n, 카드 n". 지식 베이스 저장소 push는 미리 허락된 것이다.
10. **기준 반영 PR.** 제안이 하나라도 있으면 브랜치 `librarian/criteria-YYYYMMDD`에서 기준 문서를 고쳐 커밋하고 PR을 연다. PR 설명에는 제안마다 세 질문의 답과 사례 id를 적고, 항목마다 머지/닫기로 답할 수 있게 한다. 파일 이동·합치기 제안도 같은 PR이 아니라 별도 PR로. 섞이면 무엇이 바뀌었는지 이력에서 못 가른다.
11. **지난 PR 정리.** `gh pr list --state merged`와 `--state closed`로 이전 기준 반영 PR의 결과를 보고, 해당 사례의 승격 상태를 `승인됨`(반영된 기준 id 기록) 또는 `기각`으로 바꾼다. 이 두 필드는 원본에서 고쳐도 되는 필드다.
12. **보고.** 아침에 사용자가 폰에서 볼 두 줄.
    - **완료**: 정리한 메모 n줄 → 사례 n, 결정 n, 맥락 n, 카드 n. 커밋 해시.
    - **확인할 것**: 기준 반영 제안 n건 → PR 링크. 없으면 "없음".

## 하지 말 것

- 기준 문서를 main에서 직접 고치지 않는다. 승인은 PR 머지다.
- 원본 파일의 본문을 고치지 않는다. `status`와 `superseded_by`만 예외.
- 파일을 옮기거나 합치지 않는다. 제안만 한다.
- 메모에 없는 이유·선택지·맥락을 지어 넣지 않는다. 없으면 "미확인".
- 한 번 실패한 push를 되풀이하지 않는다. 충돌이면 커밋만 남기고 보고한다.
