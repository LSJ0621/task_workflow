# 정리 절차 (사서 정리 모드)

메모를 정식 기록으로 옮기고, 카드를 갱신하고, 기준에 넣을 후보를 골라 제안한다. 하루 한 번 밤 예약 실행이 부르고, 급한 메모가 있으면 그 한 건만 즉시 한다.
정리는 비싸다. 그래서 한 세션에서 몰아 한다. 틀과 규칙을 한 번 읽고 여러 건을 처리하기 위해서다.

## 혼자 해도 되는 것과 제안만 하는 것

| 혼자 한다 (main에 커밋) | 제안만 한다 (브랜치 + PR) |
| :- | :- |
| 원본 추가(사례·결정·맥락), 카드 갱신, 회귀 질문 추가, 메모 파일에 "정리됨" 줄, 대체됨 표시(`status`/`superseded_by`, 12단계 보고에 적는다) | 기준 문서 수정, 파일 이동·합치기·이름 바꾸기. 규칙·틀·불변 조건 바꾸기는 플러그인 저장소에 PR |

왼쪽은 추가거나 원본에서 다시 만들 수 있는 것이라 틀려도 복구된다. 오른쪽은 틀리면 맥락이 깨지거나 다음 작업의 판단이 바뀐다. 그래서 사용자가 PR을 머지하는 게 승인이다.

## 순서

아래 명령의 `<사서 폴더>`는 이 파일의 한 단계 위 폴더(`skills/librarian`)다. 플러그인으로 설치된 환경이면 `${CLAUDE_PLUGIN_ROOT}/skills/librarian`, 플러그인 없이 저장소를 내려받은 환경(클라우드 밤 사서)이면 `<내려받은 저장소>/plugins/task-workflow-assistant/skills/librarian`이다.


1. **읽기.** 지식 베이스를 원격 main의 최신 상태로 맞춘다.
   - 로컬 main 브랜치에 있고 원격보다 뒤처지기만 했으면 `git pull --ff-only`.
   - HEAD가 브랜치에 붙어 있지 않거나(detached HEAD) 로컬 main이 원격과 갈라져 있으면 로컬 main은 건드리지 않는다. 클라우드 실행 환경이 저장소를 이렇게 받아 두는 일이 있다. `git reset --hard`로 맞추지 않는다. 되돌릴 수 없는 명령이라 권한 검사에도 막힌다. 대신 원격 main에서 작업 브랜치를 새로 만든다. 9단계 push는 이 브랜치에서 `HEAD:main`으로 한다.
     ```bash
     git fetch origin main && git switch -c shelve-YYYYMMDD origin/main
     ```
   그다음 이 파일과 같은 폴더의 `records.md` 전체, `templates/`의 틀, `writing.md`를 읽는다. 형식은 전부 거기서 나온다. 지식 베이스에는 규칙 문서가 없다.
2. **대상 고르기.** `raw/journal/`에서 끝에 `정리됨:` 줄이 없는 날짜 파일. 급한 한 건이면 그 줄만. 그리고 같은 날짜의 검수 결과(`raw/reviews/R-*`)에서 기준 칸이 "없음"인 발견 항목. 검수자가 기준 밖에서 잡아낸 문제는 사용자 피드백과 같은 재료다. 사용자가 보기 전에 기준이 되면 사용자가 볼 일이 줄어든다.
3. **줄마다 정식 기록 만들기.**
   - 식별자는 스크립트로 받는다. 손으로 세면 겹친다.
     ```bash
     python3 "<사서 폴더>/scripts/next_id.py" "$KNOWLEDGE_BASE_DIR" C   # C|D|X|R
     ```
     실행이 권한 검사에 거부되면 `records.md` 식별자 절의 방법으로 매긴다.
   - `feedback` → 사례(`C-`) 틀. 사용자 말은 그대로. `related`에 검수 결과 id.
   - `decision` → 결정(`D-`) 틀. 선택지가 메모에 없으면 "미확인"이라고 적는다. 이유를 지어내지 않는다.
   - `context` → 맥락(`X-`) 틀. 유효 기간은 메모에 없으면 "변할 수 있음".
   - 새 기록이 예전 기록을 바꾸면 `records.md` 승인 범위 절에 적힌 대로 한다. 전부 바꾸면 대체됨 표시를 하고, 일부만 바꾸면 표시 없이 새 기록에 "예전 기록 <id>의 이 부분을 바꾼다"고 적는다. 대체됨 표시를 한 쌍(예전 id → 새 id)은 12단계 보고용으로 적어 둔다.
   - 머리말의 `domain`은 `INDEX.md`의 도메인 목록에 있는 것만. 없는 도메인이 필요하면 목록에 먼저 추가하고 그 사실을 보고에 적는다.
4. **반영 대상 판단.** 사례마다 "왜 생겼나"를 먼저 묻고 세 갈래 중 하나로 보낸다. 실수를 보면 무조건 기준 문서에 넣고 싶어지는데, 원인이 절차에 있으면 기준을 아무리 더해도 또 생긴다.

   | 원인 | 고칠 곳 | 어떻게 |
   | :- | :- | :- |
   | 검수자가 확인하지 않았다 | 기준 문서 | `records.md` 승격 절차의 세 질문에 답해 사례의 "승격 제안" 절을 채운다. 기존 원칙에 속하면 점검 항목만 더하고, 원칙은 한 단계만 올린다. 같은 지적이 두 건 이상이면 우선순위를 올린다 |
   | 절차가 그렇게 시켰거나 막지 않았다 | 스킬·에이전트 정의 | 사례에 "스킬 수정 제안" 절을 만들어 어느 스킬(또는 에이전트 정의)의 어느 절을 어떻게 바꿀지 적는다. 플러그인 저장소에 쓸 수 있으면 브랜치 `librarian/skill-YYYYMMDD`에 고쳐 PR을 올린다. 못 쓰면 제안만 보고에 적는다 |
   | 지식 베이스와 플러그인 밖의 일 (전역 지침, 앱 동작, 외부 도구) | 손대지 않는다 | 보고의 확인할 것에 한 줄. 사용자가 정한다 |

   한 사례가 두 갈래에 걸칠 수 있다. 예: 검수자가 보고 형식을 확인해야 하고(기준), 브리핑 양식이 서문을 막지 않았다(스킬). 그때는 둘 다 적되 재발을 막는 쪽을 먼저 쓴다.
5. **카드 갱신.** 메모와 그날 검수 결과에 등장한 프로젝트마다 `wiki/projects/<slug>.md`를 원본에서 다시 쓴다. 20줄 안. 없던 프로젝트면 새로 만든다. `records.md` 프로젝트 카드 절이 항목을 정한다.
6. **회귀 질문.** 새 결정마다 `tests/regression.md`에 질문 한 줄. "왜 X를 Y로 정했나?" 꼴이 기본이다.
7. **불변 조건 점검.**
   ```bash
   python3 "<사서 폴더>/scripts/check_invariants.py" "$KNOWLEDGE_BASE_DIR"
   ```
   문제가 나오면 커밋 전에 고친다. 고칠 수 없는 것(예: 출처 없는 기준)은 보고에 적고 넘어간다.
   실행이 권한 검사에 거부되면 같은 점검을 하는 코드를 새로 짜서 돌리지 않는다. 권한 검사를 피해 가는 일이 되기 때문이다. 점검을 건너뛰고 12단계 보고의 확인할 것에 "불변 조건 점검 못 함: 스크립트 실행 거부"를 적는다.
8. **메모 파일 마감.** 처리한 날짜 파일 끝에 `정리됨: <만든 id들>` 한 줄. 메모 줄은 건드리지 않는다.
9. **커밋·push.** main에 "사서 정리 YYYY-MM-DD: 사례 n, 결정 n, 맥락 n, 카드 n". 지식 베이스 저장소 push는 미리 허락된 것이다. 1단계에서 작업 브랜치를 만들었으면 `git push origin HEAD:main`.
   정리하는 동안 원격 main이 앞서 가서 push가 거부되면 `git pull --rebase origin main`을 한 번 하고 다시 push한다. 리베이스가 충돌하면 멈추고 커밋만 남긴 채 보고한다.
10. **기준 반영 PR과 스킬 수정 PR.** 스킬 수정 제안은 플러그인 저장소에 별도 PR. 기준 반영 제안이 하나라도 있으면 브랜치 `librarian/criteria-YYYYMMDD`에서 기준 문서를 고쳐 커밋하고 PR을 연다. PR 설명에는 제안마다 세 질문의 답과 사례 id를 적고, 항목마다 머지/닫기로 답할 수 있게 한다. 파일 이동·합치기 제안도 같은 PR이 아니라 별도 PR로. 섞이면 무엇이 바뀌었는지 이력에서 못 가른다.
11. **지난 PR 정리.** `gh pr list --state merged`와 `--state closed`로 이전 기준 반영 PR의 결과를 보고, 해당 사례의 승격 상태를 `승인됨`(반영된 기준 id 기록) 또는 `기각`으로 바꾼다. 이 두 필드는 원본에서 고쳐도 되는 필드다. 머지 뒤 사례 상태와 카드의 반영 표시는 **이 단계에서만** 한다. 머지한 세션과 PR을 올린 세션이 저마다 하면 같은 파일을 두 곳에서 고쳐 push가 충돌한다(실제로 PR 두 번 연속 충돌했다).
12. **보고.** 아침에 사용자가 폰에서 볼 두 줄.
    - **완료**: 정리한 메모 n줄 → 사례 n, 결정 n, 맥락 n, 카드 n. 커밋 해시. 대체됨 표시를 했으면 쌍마다 무엇을 무엇으로 대체했는지 한 줄씩 적는다. 예: "D-20261108-08(두 줄 보고)을 D-20261109-05(보고서 파일)로 대체". 대체됨 표시는 승인 없이 하는 대신 이 보고가 사용자가 알 수 있는 유일한 곳이다.
    - **확인할 것**: 기준 반영 제안 n건과 스킬 수정 제안 n건. PR마다 **무엇이 어떻게 바뀌는지 한 문장씩** 쉬운 말로 적는다. 사용자는 GitHub에 가지 않고 이 보고만 보고 "머지해"라고 답한다. 없으면 "없음".

## 하지 말 것

- 기준 문서와 스킬을 main에서 직접 고치지 않는다. 승인은 PR 머지다.
- 지식 베이스와 플러그인 밖(전역 지침, 앱 설정)을 고치자고 제안하지 않는다. 그건 사용자 영역이다. 사실만 보고에 적는다.
- 원본 파일의 본문을 고치지 않는다. `status`와 `superseded_by`만 예외.
- 파일을 옮기거나 합치지 않는다. 제안만 한다.
- 메모에 없는 이유·선택지·맥락을 지어 넣지 않는다. 없으면 "미확인".
- 실패한 push를 그대로 되풀이하지 않는다. 9단계의 리베이스 한 번 뒤에도 안 되거나 충돌이면 커밋만 남기고 보고한다.
- 정리를 마친 뒤 PR 머지·닫힘 알림이 와도 사례 상태나 카드를 고치지 않는다. 다음 밤 정리의 11단계가 한다.
- 보고서(`raw/reports/B-*`)는 읽지도 고치지도 않는다. 비서가 이미 사용자에게 전달했고, 정리 대상은 메모와 검수 결과다.
