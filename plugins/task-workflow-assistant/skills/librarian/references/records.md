# 기록 규칙

지식 베이스에 정식 기록을 쓸 때 따르는 규칙이다. 사서 정리 모드가 처음에 한 번 읽는다. 틀은 같은 폴더의 `templates/`에 있고, 글쓰기 규칙은 같은 폴더의 `writing.md`에 있다.
지식 베이스에는 기록(맥락·데이터)만 두고, 기록을 어떻게 쓰는지는 이 파일에 둔다.

## 두 가지 문서

| 종류 | 폴더 | 성격 | 누가 언제 읽나 |
| :- | :- | :- | :- |
| 원본 | `raw/` | 추가만 한다. 고치지 않는다 | 판단이 애매할 때, 요약 문서를 다시 만들 때 |
| 요약 문서 | `wiki/` | 원본에서 만들어져서 언제든 다시 만들 수 있다. 기준, 프로젝트 카드, 진행판 | 작업 중 매번 |

새 정보는 **항상 원본에 먼저** 들어간다. 요약 문서에 직접 새 사실을 적지 않는다.
요약 문서의 모든 항목은 자기가 나온 원본을 가리킨다.

## 불변 조건

구조를 어떻게 바꾸든 이 다섯 가지는 지킨다. 리팩토링이 끝나면 이 목록으로 스스로 점검한다. 스크립트 점검은 `../scripts/check_invariants.py`.

1. 모든 기준은 원본(사례 또는 결정) 하나 이상을 가리킨다.
2. 모든 결정에는 날짜와 이유가 있다.
3. 기록은 지우지 않는다. `status: superseded`와 `superseded_by`만 표시하고 새 기록을 가리킨다.
   원본 파일에서 고쳐도 되는 건 이 두 필드뿐이다.
4. 같은 사실은 한 곳에만 있다. 두 문서가 다른 말을 하면 그게 할루시네이션의 시작이다.
5. 식별자와 파일명은 한 번 정하면 바꾸지 않는다.

## 승인 범위

- 원본에 추가하는 것은 에이전트가 알아서 한다. 정식 기록(사례·결정·맥락·검수 결과·보고서)은 main에 바로 커밋하고 push한다. 메모(`raw/journal/`)는 쪽지 모드 규칙을 따른다(main에 커밋만 하고 push는 훅이 한다).
- 실수를 기준으로 올리는 것(승격)은 에이전트가 제안하고 사용자가 승인한다. 아래 승격 절차를 따르고, 기준 문서 수정은 브랜치와 PR로 올린다. PR 머지가 승인이다.
- 파일을 옮기거나 합치는 **구조 변경**은 제안하고 승인받는다. 브랜치와 PR로 올리고, PR 머지가 승인이다.
- 대체됨 표시(`status: superseded`와 `superseded_by`)는 사서가 승인 없이 한다. 대신 보고에 무엇을 무엇으로 대체했는지 적는다. 이미 정한 결정의 뒤처리라 PR로 받으면 사용자 검토만 늘어나서다.
  - 새 기록이 예전 기록을 전부 바꿀 때만 표시한다. 예전 기록에 `status: superseded`와 `superseded_by: <새 id>`, 새 기록 머리말에 `supersedes: <예전 id>`.
  - 예전 기록의 일부만 바뀌었으면 대체됨 표시를 하지 않는다. 새 기록 본문에 "예전 기록 <id>의 이 부분을 바꾼다"고 적고 바뀐 부분을 쓴다.
- 스킬·에이전트 정의를 바꾸자는 제안은 플러그인 저장소에 PR로 올린다.
- 비밀값, 자격 정보, 고객 인프라 식별자는 어디에도 적지 않는다. 지식 베이스는 GitHub에 있고 다른 세션도 읽는다.

## 식별자

`<종류>-<YYYYMMDD>-<NN>` 형식. 같은 날 같은 종류 안에서 NN은 01부터 올라간다. 손으로 세지 말고 `../scripts/next_id.py <지식 베이스> <접두>`로 받는다.

| 종류 | 접두 | 폴더 |
| :- | :- | :- |
| 실수 사례 | `C` | `raw/cases/` |
| 결정 | `D` | `raw/decisions/` |
| 맥락 | `X` | `raw/context/` |
| 검수 결과 | `R` | `raw/reviews/` |
| 보고서 | `B` | `raw/reports/` |
| 기준 항목 | `P-<DOMAIN>-<NN>` | `wiki/criteria/<domain>.md` 안의 소제목 |

기준 항목은 파일이 아니라 소제목이다. 예: `P-COMMON-01`. 도메인 이름은 대문자로 쓴다.

## 파일명

`<식별자>-<짧은-영문-슬러그>.md`. 예: `D-20261108-01-storage-as-git-markdown.md`
한 번 정한 파일명은 바꾸지 않는다. 슬러그가 마음에 안 들어도 그대로 둔다. 링크가 깨진다.

## 머리말

모든 `raw/` 파일(메모 `raw/journal/` 제외)은 맨 위에 YAML 머리말을 둔다. 나중에 검색 색인과 필터가 되는 부분이라 빠뜨리지 않는다.

```yaml
---
id: D-20261108-01
type: decision          # case | decision | context | review | report
title: 지식 베이스 저장 방식
date: 2026-11-08
domain: common          # common 또는 도메인 이름. 소문자
status: active          # active | superseded | rejected
supersedes:             # 이 기록이 대체한 이전 기록의 id. 없으면 비움
superseded_by:          # 이 기록을 대체한 새 기록의 id. 없으면 비움
tags: [knowledge-base, storage]
related: []             # 관련 기록 id 목록
---
```

- `status`와 `superseded_by`는 원본 파일에서 고쳐도 되는 유일한 필드다.
- `domain`은 지식 베이스 `INDEX.md`의 도메인 목록에 있는 이름만 쓴다. 새 도메인은 목록에 먼저 추가하고 그 사실을 보고에 적는다.

## 기준 항목 형식

기준은 원칙과 점검 두 부분으로 쓴다. 한 줄 규칙이 아니다.

```markdown
## P-COMMON-01 비밀값은 공개되는 곳에 나가면 안 된다
- 점검
  - [ ] 환경 변수 파일이 gitignore에 있다
  - [ ] 커밋 전 diff에 키·토큰 패턴이 없다
  - [ ] 로그와 보고 문구에 비밀값이 없다
- 출처: C-20261108-01, D-20261108-05
```

- **원칙**(소제목)은 왜 안 되는지가 드러나게 쓴다.
- **점검**은 검수자가 실제로 확인할 수 있는 것만 쓴다. 확인 못 하면 더 구체적으로 쓴다.
- **출처**는 원본 id. 하나 이상 반드시 있다.

## 승격 절차: 실수를 기준으로 올리기

사용자 피드백이 들어오면 먼저 `raw/cases/`에 사례를 추가한다. 그다음 에이전트가 아래 세 질문에 답해서 **제안**하고, 사용자가 **승인**한다.

1. 이 실수가 속하는 원칙이 이미 있나?
   있으면 새 원칙을 만들지 않는다. 그 원칙에 점검 항목만 추가한다.
2. 없으면, 같은 이유로 생길 수 있는 다른 형태의 실수는 뭔가?
   그것들을 함께 점검 항목으로 적는다.
3. 이 점검 항목을 검수자가 실제로 확인할 수 있나?
   못 하면 더 구체적으로 쓴다.

원칙은 실수에서 **한 단계만** 올라간다. 환경 변수 파일 누락 → "비밀값 유출 방지"까지는 한 단계다. "보안 전체"는 두 단계라 점검할 수 없다.

사용자에게 보여 주는 건 세 질문의 답이다. 사용자는 "이 원칙에 이 점검을 붙인다"를 보고 예/아니오로 답한다. 폰에서 한 번 눌러 끝나야 한다.

## 문서를 나눌지 합칠지

기준은 책임이 아니라 **읽는 시점에 필요한가**다.

| 한 문서에 넣는다 | 링크로 뺀다 |
| :- | :- |
| 그 문서를 읽을 때마다 필요하다 | 특정 상황에서만 필요하다 |
| 짧다 | 길다 (예시, 절차 상세, 과거 사례) |
| 안 읽으면 작업이 틀어진다 | 안 읽어도 되고 읽으면 더 낫다 |
| 본문과 같이 바뀐다 | 바뀌는 주기가 다르다 |

규칙은 본문에, 상세는 링크에. 링크로 뺄 때는 "이럴 때 이 문서를 열어라"는 조건을 본문에 같이 쓴다.

## 프로젝트 카드

`wiki/projects/<slug>.md`. 프로젝트마다 한 장, 20줄 안. 요약 문서라 사서 정리 모드가 원본에서 만든다. 사람이 직접 쓰지 않는다.
들어가는 것: 뭐 하는 프로젝트인지 한 줄, 기간과 상태, 문서와 저장소 위치(경로·주소), 이 프로젝트에서 나온 결정과 사례 id, 지금 걸려 있는 일.
코드 저장소가 있는 프로젝트의 설계·경위 세부는 그 저장소 안 문서에 둔다. 카드는 위치만 가리킨다.
