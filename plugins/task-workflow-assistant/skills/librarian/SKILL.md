# 사서

지식 베이스에 쓰는 일은 전부 사서가 한다. 낮에는 **쪽지**(메모 한 줄, 가벼움), 밤에는 **정리**(메모 → 정식 기록, 무거움). 이 본문은 쪽지 모드다. 정리 모드는 [정리 절차](references/shelving.md)에 있고, 정리를 요청받았거나 급한 메모가 있을 때만 읽는다. 매번 읽으면 메모 한 줄에 정리 절차 전체가 딸려 와서 낭비라서다.

## 지식 베이스 찾기

1. `$KNOWLEDGE_BASE_DIR`이 있으면 그곳.
2. 없으면 현재 폴더가 지식 베이스인지 본다. `INDEX.md`와 `raw/journal/`이 있는 git 저장소면 맞다. 클라우드에서 지식 베이스 저장소로 연 세션(밤 사서)이 이 경우다.
3. 둘 다 아니고 브리핑에 지식 베이스 경로가 적혀 있으면 그곳.
4. 셋 다 아니면 쓰지 말고 `setup-knowledge-base` 스킬을 안내한다.

## 규칙이 있는 곳

규칙과 틀은 모두 이 스킬 폴더 안에 있다. 지식 베이스에는 기록만 있고 규칙은 없다. 클라우드 사서는 플러그인을 설치하지 않고 저장소를 내려받아 이 폴더의 파일을 경로로 읽으므로, 사서가 쓰는 규칙은 이 폴더 밖에 두지 않는다.

- 메모 형식: 이 파일 아래 쪽지 모드
- 정리 절차: `references/shelving.md`
- 기록 형식(두 가지 문서, 불변 조건, 승인 범위, 식별자, 파일명, 머리말, 기준 항목, 승격 절차, 카드): `references/records.md`
- 사례·결정·맥락 틀: `references/templates/`
- 글쓰기: `references/writing.md`

## 쪽지 모드

메모는 "나중에 사서가 정리할 재료"다. 지금 틀을 채우거나 기준을 고치지 않는다. 그 비용을 밤으로 미루는 게 이 설계의 핵심이다.

1. 메모 파일과 형식을 확인한다. 메모는 지식 베이스 `raw/journal/YYYY-MM-DD.md`에 날짜별 한 파일로 쌓는 원본이다. 한 줄 형식은 이렇다.
   ```
   HH:MM | feedback|decision|context | 작업 또는 맥락 | 내용 (사용자 말은 그대로) | 관련 id 또는 -
   ```
   메모에는 틀을 채우지 않는다. 정식 기록은 정리 모드가 만든다.
2. 종류를 정한다.
   - `feedback`: 사용자가 에이전트의 결과·행동·판단을 고쳤다. 사용자 말을 **그대로** 인용한다. 이 말이 나중에 기준 문서의 재료가 된다.
   - `decision`: 뭘 하기로 정했다. 결정과 이유를 한 줄에. 선택지가 있었으면 버린 쪽도 짧게.
   - `context`: 사용자 본인, 상황, 선호, 제약에 대한 새 사실.
3. 적는 때를 고른다. 프롬프트마다 적지 않는다. **주제 하나가 끝날 때 한 줄**이다. 고치는 말이 오가는 동안은 적지 않는다. 결론이 나면 결론과 사용자 말 한마디를 한 줄로 적는다. 같은 주제의 연속 피드백은 한 줄로 묶는다. "다음 답은 짧게 해 줘"처럼 그 답 하나에만 해당하는 말은 적지 않는다. 앞으로도 계속 적용할 말일 때만 남긴다. 예외로 바로 적는 것: 사용자가 "메모해"라고 했을 때, `urgent`일 때.
   오늘 날짜 파일이 없으면 만든다. 머리말 없이 줄만 쌓는 파일이다. 위 형식대로 **한 줄** 덧붙인다. 글은 `references/writing.md`를 따른다. 관련 작업이나 검수 결과 id가 있으면 넣고, 없으면 `-`.
4. 급한지 본다. 오늘 다음 작업이 이 결정에 바로 걸리면 줄 끝에 ` | urgent`를 붙이고, 정리 절차를 읽어 **그 한 건만** 즉시 정리한다. 아니면 밤 정리에 맡긴다.
5. 커밋한다. 메모는 추가만 하는 원본이라 main에 바로 간다. 먼저 `git pull --ff-only`. push 안 된 로컬 커밋이 있어 ff-only가 안 되면 `git pull --rebase`. 그다음 `git add` 해당 파일, 커밋 메시지는 "메모: <종류> <요지>". pull이 충돌하면 커밋만 남기고 보고에 적는다.
   push는 하지 않는다. 메모를 읽는 쪽은 밤 3시 클라우드 사서와 새로 여는 비서 세션뿐이라 push를 자주 할 필요가 없다. 훅이 밀린 메모가 있으면 30분에 한 번까지 한다. push는 플러그인 훅(`hooks/push-journal.sh`)이 한다. 지식 베이스에서 연 세션이나 `$KNOWLEDGE_BASE_DIR`가 설정된 세션이 응답을 끝낼 때마다 조건을 보고 알아서 한다. 클라우드 사서에는 플러그인이 없어 훅도 없지만, 클라우드 사서는 메모를 읽는 쪽이라 훅이 필요 없다.
   예외로 바로 push하는 것: `urgent` 메모, 사용자가 "메모해"라고 한 메모.
6. 한 줄로 알린다. "메모 남김: `raw/journal/YYYY-MM-DD.md` (종류)". 두 줄 보고는 쓰지 않는다. 메모는 작업이 아니라 작업의 부산물이라서다.

## 하지 말 것

- 메모 줄을 고치거나 지우지 않는다. 잘못 적었으면 정정 줄을 하나 더 쓴다. 원본은 추가만 한다.
- 메모 단계에서 틀을 채우거나, 기준 문서·카드·색인을 고치지 않는다. 정리 모드의 일이다.
- 한 사건에 두 줄 넘게 쓰지 않는다. 길어지면 정리할 때 기록이 된다.
- 비밀값, 자격 정보, 고객 인프라 식별자를 적지 않는다. 지식 베이스는 GitHub에 올라가고 밤 사서가 클라우드에서 읽는다.
- 사용자가 고친 말을 요약하거나 다듬지 않는다. 그대로가 재료다.
