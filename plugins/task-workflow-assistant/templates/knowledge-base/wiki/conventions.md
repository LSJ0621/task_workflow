# 기록 규칙

## 식별자

`<종류>-<YYYYMMDD>-<NN>` 형식. 같은 날 같은 종류 안에서 NN은 01부터 올라간다.

| 종류 | 접두 | 폴더 |
| :- | :- | :- |
| 실수 사례 | `C` | `raw/cases/` |
| 결정 | `D` | `raw/decisions/` |
| 맥락 | `X` | `raw/context/` |
| 검수 결과 | `R` | `raw/reviews/` |
| 보고서 | `B` | `raw/reports/` |
| 기준 항목 | `P-<DOMAIN>-<NN>` | `wiki/criteria/<domain>.md` 안의 소제목 |

기준 항목은 파일이 아니라 소제목이다. 예: `P-COMMON-01`. 도메인 이름은 대문자로 쓴다.

## 파일명

`<식별자>-<짧은-영문-슬러그>.md`. 예: `D-20261108-01-storage-as-git-markdown.md`
한 번 정한 파일명은 바꾸지 않는다. 슬러그가 마음에 안 들어도 그대로 둔다. 링크가 깨진다.

## 머리말

모든 `raw/` 파일은 맨 위에 YAML 머리말을 둔다. 나중에 검색 색인과 필터가 되는 부분이라 빠뜨리지 않는다.

```yaml
---
id: D-20261108-01
type: decision          # case | decision | context | review | report
title: 지식 베이스 저장 방식
date: 2026-11-08
domain: common          # common 또는 도메인 이름. 소문자
status: active          # active | superseded | rejected
supersedes:             # 이 기록이 대체한 이전 기록의 id. 없으면 비움
superseded_by:          # 이 기록을 대체한 새 기록의 id. 없으면 비움
tags: [knowledge-base, storage]
related: []             # 관련 기록 id 목록
---
```

- `status`와 `superseded_by`는 원본 파일에서 고쳐도 되는 유일한 필드다.
- `domain`은 `INDEX.md`의 도메인 목록에 있는 이름만 쓴다. 새 도메인은 목록에 먼저 추가한다.

## 기준 항목 형식

기준은 두 층으로 쓴다. 한 줄 규칙이 아니다.

```markdown
## P-COMMON-01 비밀값은 공개되는 곳에 나가면 안 된다
- 점검
  - [ ] 환경 변수 파일이 gitignore에 있다
  - [ ] 커밋 전 diff에 키·토큰 패턴이 없다
  - [ ] 로그와 보고 문구에 비밀값이 없다
- 출처: C-20261108-01, D-20261108-05
```

- **원칙**(소제목)은 왜 안 되는지가 드러나게 쓴다.
- **점검**은 검수자가 실제로 확인할 수 있는 것만 쓴다. 확인 못 하면 더 구체적으로 쓴다.
- **출처**는 원본 id. 하나 이상 반드시 있다.

## 승격 절차: 실수를 기준으로 올리기

사용자 피드백이 들어오면 먼저 `raw/cases/`에 사례를 추가한다. 그다음 에이전트가 아래 세 질문에 답해서 **제안**하고, 사용자가 **승인**한다.

1. 이 실수가 속하는 원칙이 이미 있나?
   있으면 새 원칙을 만들지 않는다. 그 원칙에 점검 항목만 추가한다.
2. 없으면, 같은 이유로 생길 수 있는 다른 형태의 실수는 뭔가?
   그것들을 함께 점검 항목으로 적는다.
3. 이 점검 항목을 검수자가 실제로 확인할 수 있나?
   못 하면 더 구체적으로 쓴다.

원칙은 실수에서 **한 단계만** 올라간다. 환경 변수 파일 누락 → "비밀값 유출 방지"까지는 한 단계다. "보안 전체"는 두 단계라 점검할 수 없다.

사용자에게 보여 주는 건 세 질문의 답이다. 사용자는 "이 원칙에 이 점검을 붙인다"를 보고 예/아니오로 답한다. 폰에서 한 번 눌러 끝나야 한다.

## 수정 재지시 규칙

검수에서 수정이 필요하면 기본은 **원래 작업자**에게 다시 시킨다. 맥락을 이미 알고 있어서 싸다.
다음 중 하나면 **새 작업자**로 바꾼다.

- 같은 지적이 두 번째로 돌아왔다
- 작업자의 컨텍스트가 거의 찼다
- 수정이 아니라 설계를 다시 짜야 한다

어느 쪽이든 검수 결과(`R-`)만 넘기면 되도록 검수 결과를 쓴다. 상태는 작업자 머릿속이 아니라 문서에 있다.

## 문서를 나눌지 합칠지

기준은 책임이 아니라 **읽는 시점에 필요한가**다.

| 한 문서에 넣는다 | 링크로 뺀다 |
| :- | :- |
| 그 문서를 읽을 때마다 필요하다 | 특정 상황에서만 필요하다 |
| 짧다 | 길다 (예시, 절차 상세, 과거 사례) |
| 안 읽으면 작업이 틀어진다 | 안 읽어도 되고 읽으면 더 낫다 |
| 본문과 같이 바뀐다 | 바뀌는 주기가 다르다 |

규칙은 본문에, 상세는 링크에. 링크로 뺄 때는 "이럴 때 이 문서를 열어라"는 조건을 본문에 같이 쓴다.

## 메모 (사서 쪽지 모드)

낮에 생긴 일을 한 줄씩 받아 적는 곳. `raw/journal/YYYY-MM-DD.md`, 날짜별 한 파일, 추가만 한다. 원본 층이다.

```
HH:MM | feedback|decision|context | 작업 또는 맥락 | 내용 (사용자 말은 그대로) | 관련 id 또는 -
```

- 급하면 줄 끝에 ` | urgent`를 붙인다. 오늘 다음 작업이 바로 걸리는 결정이 그렇다. 사서가 그 건만 즉시 정리한다.
- 메모에는 틀을 채우지 않는다. 정식 기록은 사서 정리 모드가 만든다.
- 정리가 끝난 날짜 파일 끝에 사서가 `정리됨: <만든 id 목록>` 한 줄을 덧붙인다. 메모 줄 자체는 고치지 않는다.

## 진행판

`wiki/board.md`. 비서가 작업 경계마다 갱신하는 정리 층 파일. 덮어써도 된다. 메모와 검수 결과에서 다시 만들 수 있다.
들어가는 것: 진행 중인 작업(이름, 팀장 세션, 상태), 검수 대기, 사용자 답 대기, 오늘 끝난 작업과 검수 결과 id.
새 비서 세션은 이 파일과 오늘 메모만 읽고 이어간다.

## 프로젝트 카드

`wiki/projects/<slug>.md`. 프로젝트마다 한 장, 20줄 안. 정리 층이라 사서 정리 모드가 원본에서 만든다. 사람이 직접 쓰지 않는다.
들어가는 것: 뭐 하는 프로젝트인지 한 줄, 기간과 상태, 문서와 저장소 위치(경로·주소), 이 프로젝트에서 나온 결정과 사례 id, 지금 걸려 있는 일.
코드 저장소가 있는 프로젝트의 설계·경위 세부는 그 저장소 안 문서에 둔다. 카드는 위치만 가리킨다.

## 산출물 (코드 저장소가 없는 일)

기획서, 조사 보고, 생활 문서처럼 코드 저장소가 없는 작업의 산출물은 `work/<YYYYMMDD>-<slug>/`에 둔다. 원본도 정리도 아닌 세 번째 자리다.
산출물은 사용자가 봐야 하는 것이라 브랜치와 PR로 올린다. PR 머지가 승인이다. 검수 결과(`R-`)는 산출물이 아니라 원본이므로 main에 바로 간다.
코드 저장소가 있는 작업의 산출물은 그 저장소에 두고, 지식 베이스에는 검수 결과와 카드만 남긴다.

## 보고서 (팀장 → 비서)

- 위치 `raw/reports/`. 식별자 `B-<YYYYMMDD>-<NN>`. 파일명 `<식별자>-<짧은-영문-슬러그>.md`. 머리말은 다른 원본과 같은 형식이고 `type: report`.
- 원본 층이다. 추가만 하고 main에 바로 커밋·push한다. PR은 올리지 않는다.
- 길이와 본문 형식은 자유다. 상한과 양식은 보고서가 쌓인 뒤 분석해서 정한다.
- 마지막 절은 반드시 `## 확인할 것`이다. 거기에는 위험한 변경과 사용자가 정할 것만 적는다. 없으면 "없음". 결정이 필요하면 예/아니오로 답할 수 있는 한 문장으로 쓴다. PR이 있으면 PR마다 무엇이 어떻게 바뀌는지 쉬운 말 한 문장을 넣는다.
- 본문에는 한 일과 증거(실행한 명령, 결과)를 쓴다. 세부는 검수 결과(`R-`)와 PR 경로로 가리킨다.
- 막혔을 때도 보고서를 쓴다. 확인할 것에 `막힘: <이유와 필요한 결정>`을 적는다.
- 팀장이 비서에게 보내는 세션 메시지는 `보고서: <경로> | <판정>` 한 줄뿐이다. 판정은 `통과` 또는 `막힘` 한 단어. 앞뒤에 다른 문장을 붙이지 않는다. 맥 앱은 팀장 세션의 마지막 응답이, 클라우드는 세션 메시지 도구로 보낸 것이 비서에게 간다.
- 비서는 이 보고서를 읽는다. "비서는 읽지 않는다" 원칙의 유일한 예외다. 산출물, 검수 결과 전문, 기준 문서는 여전히 읽지 않는다.
- 비서는 보고서를 사용자 말로 다시 써서 전달한다. 쉬운 한국어, 짧은 문장, 명사 나열 금지, 문서 번호(R-, PR 번호)만 쓰지 않고 내용을 같이 말한다. "확인할 것"은 하나도 빠뜨리지 않는다. 결정이 필요하면 예/아니오로 답할 수 있는 한 문장으로 만든다.

왜 파일인가: 세션 메시지는 앞부분만 전달되고, 그 길이에 맞추면 보고가 명사 나열로 압축되어 사용자가 이해하기 어려웠다. 보고서를 파일로 쓰고 경로만 보내면 이 한계와 상관없어진다.

```yaml
---
id: B-20261109-01
type: report
title: <작업 이름> 보고
date: 2026-11-09
domain: common
status: active
supersedes:
superseded_by:
tags: [report]
related: [R-20261109-01]   # 이 작업의 검수 결과 id
---
```
