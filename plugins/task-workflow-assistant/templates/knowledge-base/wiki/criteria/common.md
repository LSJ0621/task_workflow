# 공통 기준

도메인과 상관없이 모든 작업과 검수에 적용한다.
항목이 적은 건 의도다. 기준은 실제 작업의 피드백에서 나온다. 아래 네 개는 초안 기본값이다(D-{{DATE}}-01).

## P-COMMON-01 비밀값과 고객 인프라 식별자는 저장소·보고·로그 어디에도 나가지 않는다
- 점검
  - [ ] 커밋 전 diff에 키·토큰·접속 문자열 패턴이 없다
  - [ ] 환경 변수 파일이 gitignore에 있다
  - [ ] 보고 문구와 작업 노트에 비밀값, 계정 ID, 네트워크·DB 식별자, 프로필명이 없다
  - [ ] 지식 베이스(`raw/`, `wiki/`)에 위 항목이 없다
- 출처: D-{{DATE}}-01

## P-COMMON-02 보고는 사용자가 읽고 바로 판단할 수 있어야 한다
- 점검
  - [ ] 보고서가 `raw/reports/`에 `B-` 식별자로 있고, 마지막 절이 `## 확인할 것`이다
  - [ ] 보고서에 실행한 명령이나 결과 같은 증거가 있다
  - [ ] "확인할 것"에는 위험한 변경과 사용자가 정할 것만 있다. 없으면 "없음"이라고 적혀 있다
  - [ ] 승인을 요청한다면 예/아니오로 답할 수 있는 한 문장이다
  - [ ] 세부는 본문에 풀지 않고 검수 결과 문서(`R-`)와 PR 경로로 가리킨다
  - [ ] 팀장이 비서에게 보낸 세션 메시지는 `보고서: <경로> | <판정>` 한 줄뿐이다
  - [ ] "확인할 것"에 PR·브랜치가 있으면 PR마다 무엇이 어떻게 바뀌는지 쉬운 말 한 문장이 있다. 링크만 있으면 실패
  - [ ] 비서가 사용자에게 전달한 말에 보고서의 "확인할 것"이 모두 들어 있고, 문서 번호만이 아니라 내용이 쉬운 말로 적혀 있다
- 출처: D-{{DATE}}-01

## P-COMMON-03 검수 결과는 그 문서만 넘겨도 작업자가 수정할 수 있어야 한다
- 점검
  - [ ] 발견 항목마다 위치, 뭐가 틀렸나, 기대, 근거, 기준 id가 있다
  - [ ] 재지시 대상(원래/새 작업자)과 이유, 몇 번째 수정 요청인지 적혀 있다
  - [ ] 기준에 없는 지적은 기준 칸이 "없음"이고 `C-` 사례로 올릴 대상으로 표시되어 있다
- 출처: D-{{DATE}}-01

## P-COMMON-04 새 정보는 원본에 먼저 들어간다
- 점검
  - [ ] 사용자 피드백이 있었으면 `raw/cases/`에 `C-` 기록이 생겼다
  - [ ] 뭔가 정했으면 `raw/decisions/`에 `D-` 기록이 생겼고 이유가 있다
  - [ ] `wiki/`에 새로 들어간 항목은 모두 출처 id가 있다
  - [ ] 파일 옮기기·합치기가 있었으면 승인받은 기록이 있다
  - [ ] 대체됨 표시(`status`·`superseded_by`)를 했으면 보고에 무엇을 무엇으로 대체했는지 적혀 있다
- 출처: D-{{DATE}}-01
